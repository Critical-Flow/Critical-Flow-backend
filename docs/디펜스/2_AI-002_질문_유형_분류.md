# AI-002 질문 유형 분류 — 디펜스

> 관련 코드: `QuestionTypeRouter`, `QuestionTypeAdvisor`, `QuestionTypePromptProvider`, `QuestionType`  
> 관련 요구사항: REQ-AIV-006

---

## 1. 기능 개요

AI-001 응답 생성 요청 시 자동으로 선행 수행되는 기능이다. 학습자 노트의 특성에 맞는 질문 유형(TYPE_A~F 6종)을 선택해 AI-001에 전달한다.

**트리거:** AI-001 응답 생성 요청 시 자동 수행  
**액터:** AI 튜터 시스템 (학습자가 직접 호출하지 않음)

---

## 2. 질문 유형 정의 (6종)

| 유형 | 코드 | 적용 조건 | Bloom's 대응 |
|---|---|---|---|
| 유형 1 | TYPE_A | 새로운 용어나 개념이 처음 등장하며 설명이 부족한 경우 | Knowledge (기억) |
| 유형 2 | TYPE_B | 특정 방식이나 기술을 선택한 이유, 트레이드오프, 비교가 포함된 경우 | Evaluation (평가) |
| 유형 3 | TYPE_C | 이전에 학습한 개념과 현재 노트가 연결되는 경우 **(RAG 컨텍스트 필요)** | Comprehension (이해) |
| 유형 4 | TYPE_D | 기본 개념 이해 후 엣지케이스, 실패 케이스, 경계 조건 탐구 | Analysis (분석) |
| 유형 5 | TYPE_E | 코드 블록이 포함된 경우 **(최우선 적용)** | (별도) |
| 유형 6 | TYPE_F | 코드 없이 이론·개념만 설명된 순수 텍스트 노트 | Application (적용) |

---

## 3. 라우팅 흐름

```
QuestionTypeRouter.route(note, ragContext)
    │
    ├── [규칙 기반] 코드 블록(```) 존재?
    │       YES → TYPE_E 즉시 반환 (LLM 호출 없음)
    │
    └── [LLM 분류] NO → type-router.st 프롬프트로 gpt-4o 호출
                            │
                            ▼
                        parseType(raw, ragContext)
                            ├── TYPE_C 분류 + RAG 없음 → TYPE_A 폴백
                            ├── 6종 중 매칭 → 해당 유형 반환
                            └── 매칭 실패 → TYPE_A 반환 (기본값)
```

분류 결과는 `AiConversation.questionType` 컬럼(MySQL)에 저장된다.

## 4. QuestionTypeAdvisor — LLM 호출 전 프롬프트 교체

### Advisor란?

Spring AI에서 Advisor는 **LLM 호출을 가로채는 미들웨어**다. AOP의 `@Around`나 서블릿 필터와 같은 개념으로, 호출 전후에 프롬프트 수정·로깅·캐싱 등을 수행할 수 있다.

```
chatClient.prompt().call()
    → Advisor (전처리: 프롬프트 수정 등)
    → LLM 호출
    → Advisor (후처리: 응답 가공 등)
    → 결과 반환
```

`CallAdvisor`의 `adviseCall()` 안에서 `chain.nextCall(modifiedReq)`를 호출하는 시점이 LLM 호출 직전/직후의 경계가 된다. Spring AI 내장 Advisor로는 `MessageChatMemoryAdvisor`(대화 히스토리 자동 주입), `QuestionAnswerAdvisor`(RAG 자동 검색 주입) 등이 있다.

---

`CallAdvisor`를 구현해 LLM 호출 직전에 프롬프트를 가로채서 선택된 TYPE 설명만 주입한다.

```
chatClient.prompt() 호출
    → QuestionTypeAdvisor.adviseCall()
        → QuestionTypeRouter.route() → TYPE 결정
        → QuestionTypePromptProvider.inject() → 시스템 프롬프트의
          {selected_question_type} 자리에 해당 TYPE 설명만 삽입
    → LLM 호출
```

이 구조로 매 턴마다 6종 설명 전체(~200 토큰)가 아닌 선택된 1종 설명(~50 토큰)만 프롬프트에 포함되어 토큰을 절감한다.

## 5. Q&A — 분류 설계

### Q. REQ-AIV-006 — 정의되지 않은 유형이 출력되지 않음을 어떻게 보장하는가?

`parseType()`이 세 단계 폴백으로 보장한다.

1. **코드 블록 있음 → TYPE_E**: LLM 호출 없이 즉시 반환. LLM 오류 자체가 발생하지 않는다.
2. **TYPE_C + RAG 없음 → TYPE_A**: RAG 컨텍스트가 없으면 과거 연계 질문이 불가능하므로 기본 유형으로 폴백.
3. **매칭 실패 → TYPE_A**: LLM이 6종 외의 값을 반환하거나 응답이 없어도 `QuestionType.values()` 순회에서 매칭되지 않으면 TYPE_A를 기본값으로 반환.

```java
// QuestionTypeRouter.parseType()
for (QuestionType type : QuestionType.values()) {
    if (raw.contains(type.name())) {
        if (type == QuestionType.TYPE_C && ragContext.isEmpty()) {
            return QuestionType.TYPE_A;  // 폴백
        }
        return type;
    }
}
return QuestionType.TYPE_A;  // 기본값
```

---

### Q. TYPE_C를 선택했는데 RAG가 없으면 왜 TYPE_A로 폴백하는가?

TYPE_C는 DRD 정의상 "관련 노트 컨텍스트가 존재할 때만 선택 가능"하다. TYPE_C 질문은 "예전에 배운 X와 현재 배우는 Y가 어떻게 연결되는지"를 묻는 것인데, RAG 결과가 없으면 참조할 과거 노트 자체가 없어 질문의 전제가 성립하지 않는다. 따라서 TYPE_C + RAG 없음 조합은 의미가 없어 TYPE_A로 전환한다.

---

### Q. 노트 내용이 바뀌어야 question_type도 바뀌는 것 아닌가?

반드시 그렇지는 않다. `QuestionTypeRouter`는 **노트 내용 + RAG 결과** 두 가지를 보고 결정한다.

**노트 내용이 같아도 타입이 달라지는 경우:**
- 과거 노트가 새로 추가되면 RAG 결과가 바뀌어 TYPE_C가 선택될 수 있다. 처음 대화 시작 시 관련 노트가 없어 TYPE_A였다가, 이후 관련 노트가 생기면 같은 노트로 다시 시작해도 TYPE_C가 나올 수 있다.

**코드 블록이 있는 노트는 예외:** LLM 호출 없이 규칙 기반으로 TYPE_E를 즉시 반환하므로 항상 고정된다.

---

### Q. 같은 LLM을 호출하는데 동일한 입력에서 타입이 달라질 수 있는가?

`temperature: 0.3`으로 설정되어 있기 때문에 이론적으로는 달라질 수 있다. `temperature: 0`이면 항상 동일하지만, 0.3은 약간의 무작위성이 있다.

다만 질문 타입 분류는 출력이 `TYPE_A`~`TYPE_F` 중 하나로 단순하고 프롬프트가 명확해서 실제로 다른 타입이 나올 가능성은 매우 낮다. 실제 관찰에서도 코드 블록 없는 노트에서 분류가 불안정한 케이스는 발견되지 않았다.

---

### Q. question_type을 DB에 저장하는 이유는?

두 가지 목적이 있다.

1. **이중 라우팅 방지:** `generateFirstQuestion()`에서 이미 결정된 TYPE을 `AiConversation.questionType`에 저장하고, `QuestionTypeAdvisor`에서 `preSelectedType`이 있으면 LLM을 재호출하지 않고 재사용한다.

2. **Fine-tuning 학습 데이터 누적:** `(노트 내용 → TYPE)` 쌍이 쌓이면 향후 OpenAI Fine-tuning의 학습 데이터로 활용할 수 있다. 현재 LLM 분류로 시작하는 이유 자체가 이 데이터를 쌓기 위함이기도 하다.

---

### Q. RAG 결과를 기반으로 TYPE을 결정하는가?

아니다. `QuestionTypeRouter`는 RAG 결과의 **존재 여부**(`rag_available: true/false`)만 LLM에게 전달하며, 실제 검색된 청크 내용은 라우팅 판단에 사용되지 않는다.

```java
String prompt = routerPromptTemplate
        .replace("{note_content}", note.getContent())
        .replace("{rag_available}", String.valueOf(!ragContext.isEmpty()));
```

RAG 내용이 라우팅에 관여하는 유일한 지점은 `parseType()`의 폴백 규칙뿐이다. TYPE_C로 분류됐는데 `ragContext.isEmpty()`이면 TYPE_A로 전환한다. 이는 라우팅 입력이 아닌 후처리 규칙이다.

이 설계는 라우터를 의도적으로 가볍게 유지하기 위한 선택이다. 이유는 세 가지다.

1. **라우터의 역할이 아니다.** 라우터가 결정하는 건 "어떤 방식으로 질문할지(TYPE)"이지 "무슨 내용을 질문할지"가 아니다. RAG 청크 내용은 실제 AI 튜터 응답 프롬프트에 주입되는 것이고, 라우터는 그 전 단계의 분류기다.

2. **토큰 낭비.** RAG 청크는 수백~수천 토큰인데, 라우터가 필요한 정보는 "관련 과거 노트가 존재하는가(TYPE_C 가능 여부)"뿐이다. `true/false` 플래그 하나면 충분한 곳에 청크 전체를 넣으면 낭비다.

3. **분류 오염 위험.** 현재 노트는 "정렬 알고리즘"인데 RAG가 "OS 스케줄링" 청크를 가져왔다면, 그 내용이 라우터 프롬프트에 섞이면 LLM이 TYPE을 잘못 판단할 수 있다. 노트 내용만 보고 분류하는 것이 더 안정적이다.

### Q. `ChatModel`과 `ChatClient`의 차이는? `QuestionTypeRouter`가 `ChatModel`을 쓰는 이유는?

두 인터페이스의 계층이 다르다.

| | `ChatModel` | `ChatClient` |
|---|---|---|
| 수준 | 저수준 — 직접 `Prompt` 객체를 넘겨 호출 | 고수준 — fluent 빌더 API |
| Advisor 체인 | 없음 | 있음 (`CallAdvisor` 등록 가능) |
| 주요 용도 | 단순 1회 호출 | 메모리·RAG·Advisor 연결이 필요한 복합 호출 |

`QuestionTypeRouter`가 `ChatModel`을 사용하는 이유는 **무한 루프 방지**다. `ChatClient`를 사용하면 라우터 호출 자체가 `QuestionTypeAdvisor`를 다시 통과하게 되어 무한 루프가 발생한다. 라우터는 TYPE 분류만 하는 단순 1회 LLM 호출이므로 `ChatModel`이 적합하다.

```
[ChatClient 사용 시 문제]
QuestionTypeAdvisor.adviseCall()
    → router.route() → ChatClient 호출
        → QuestionTypeAdvisor.adviseCall() → 무한 루프 ❌

[ChatModel 사용 시]
QuestionTypeAdvisor.adviseCall()
    → router.route() → ChatModel 직접 호출 (Advisor 체인 우회) ✓
```

---

### Q. SemanticQuestionTypeRouter(임베딩 기반 라우팅)를 쓰지 않은 이유는?

노트 내용(도메인 지식 벡터 공간)과 TYPE 시드 문장(교육학 메타 설명 벡터 공간)이 **서로 다른 의미 공간**에 위치한다. 노트 "BFS 탐색"과 TYPE_A 시드 "새로운 개념이나 용어가 처음 등장한 노트"를 코사인 유사도로 비교하면 의미 없는 값이 나온다. 이 방식은 설계 단계에서 채택하지 않았다. 상세 논의는 `docs/설계/질문_타입_라우팅_전략.md` 참조.

## 6. 질문 유형 라우팅 전략 — 최종 결정

### 1단계 (현재 구현)

규칙 기반 전처리 필터 + LLM 분류 혼합.

```
노트 입력
    ↓
[규칙] 코드 블록 있음? → TYPE_E 즉시 반환 (LLM 호출 없음)
    ↓ (없으면)
[LLM] gpt-4o 분류 → TYPE 결정 + DB 저장
    ↓
[폴백] TYPE_C + RAG 없음 → TYPE_A
       매칭 실패 → TYPE_A
```

### 2단계 (데이터 200~300개 누적 후)

1단계에서 쌓인 `(노트 → TYPE)` 쌍을 PLOS ONE 데이터(Bloom's Taxonomy 16,584개)와 합쳐 OpenAI Fine-tuning 수행.

### 3단계 (운영 안정화)

Fine-tuned 모델로 교체 → LLM 분류 비용 절감 + 응답 속도 향상.

> LLM 분류로 시작하는 핵심 이유: LLM이 내리는 분류 결정 자체가 이 프로젝트 도메인(한국어, CS/개발 노트)에 특화된 학습 데이터가 되기 때문이다.
