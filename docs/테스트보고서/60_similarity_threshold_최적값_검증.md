## 1. 진행 이유

**1-1. 발견 경위**
`RagRetrievalService`의 Dense 검색에서 `similarity-threshold: 0.75`를 1차 필터 임계값으로 사용하고 있었다. 이 값은 경험적으로 설정한 초기값으로, `text-embedding-3-small` + 한국어 CS 노트 환경에서 실제로 최적인지 검증한 적이 없었다.

**1-2. 해결하지 않을 경우 영향**
- 임계값이 너무 높으면 Dense 검색 결과가 0건이 되어 RAG 컨텍스트 전체가 Sparse에만 의존
- TYPE_C(Spaced Recall) 질문의 의미 기반 연결이 불가능해짐
- 임계값이 너무 낮으면 토픽이 다른 노트가 1차 필터를 통과해 2차 필터에 과도한 부담

**1-3. 관련 요구사항**
- REQ-AIV-004 — 관련도 임계값 미만 항목은 검색 결과에서 제외되어야 한다.
- REQ-AIV-011 — 관련 노트 검색 재현율 목표.

## 2. 측정 방법

**2-1. 측정 방식**
- [x] 수동 실험 (threshold=0.0으로 전체 후보 조회 후 Java 단 임계값별 비교)

**2-2. 측정 조건**
서버를 5번 재시작하는 대신 `threshold=0.0`으로 상위 10건을 한 번에 조회하고 Java 단에서 각 임계값(0.55 / 0.60 / 0.70 / 0.75) 통과 여부를 비교.

**2-3. 테스트 데이터 구성**
- 데이터 출처: CS 개념·알고리즘·프레임워크 혼합 노트
- 데이터 건수: 20개 임베딩, 10개 쿼리 (noteId=1~10)
- 데이터 특성: HashMap, 스택, 큐, 이진탐색, 재귀, DP, 퀵정렬, BFS, DFS, 힙
- 정답 레이블 여부: 없음 (임계값별 반환 건수 비교 목적)

**2-7. 측정 API 호출 명령어**

`similarity-threshold=0.0`으로 설정 후 아래 curl 명령어를 실행해 상위 10건의 score를 수집했다.

```bash
# threshold=0.0으로 application.yml 임시 변경 후 서버 재시작
# rag.similarity-threshold: 0.0

for i in {1..10}; do
  echo "=== noteId=$i ==="
  curl -s -X POST http://localhost:8080/api/v1/conversations \
    -H "Content-Type: application/json" \
    -d "{\"noteId\": $i, \"type\": \"QUESTION\"}" | jq '.'
  sleep 1
done
```

임시 로그를 `RagRetrievalService.denseSearch()` 내부에 추가해 각 문서의 score를 수집:

```java
// [#60 임시 로그] threshold=0.0으로 전체 후보 수집 후 score 출력
results.forEach(doc ->
    log.info("[#60] noteId={} candidateTitle={} score={}",
        noteId, getMeta(doc, "title"), extractScore(doc)));
```

서버 로그 출력 형식:
```
[#60] noteId=1 candidateTitle=정렬 알고리즘 비교 score=0.5102
[#60] noteId=1 candidateTitle=힙(Heap) 자료구조 score=0.5163
[#60] noteId=1 candidateTitle=큐(Queue) 자료구조 score=0.5379
...
```

**2-4. 측정 기준 및 도구**
- 측정 지표: 각 임계값에서 Dense 평균 반환 건수
- 측정 도구: 대화 시작 API + 직접 로그 확인
- 성공 기준: Dense 평균 반환 건수 ≥ 4건 (topK=6 활용 가능 수준)

**2-5. 측정 반복 횟수**
1회 (임베딩 결과가 결정론적이므로 재현 가능)

**2-6. 이 방식을 선택한 이유**
서버를 4번 재시작하지 않고 `threshold=0.0`으로 전체 후보를 한 번에 조회해 Java 단에서 임계값별 통과 여부를 비교함으로써 측정 비용을 절감했다.

## 4. 조치

**4-1. 수정 방향 및 근거**
임계값을 0.75 → 0.55로 하향. 0.55 선택 근거:
- score 분포 중앙값이 0.58~0.62 구간
- 0.55 기준 평균 7.3건 반환 → topK=6 제한으로 상위 6건 활용 가능
- 0.60 대비 스택·힙 등 일부 노트에서 2건 추가 확보
- 0.55~0.60 구간 false positive는 `isTopicRelevant()` 2차 필터가 처리

**4-2. 변경 내역**

| 변경 대상 | 변경 전 | 변경 후 |
|---|---|---|

**① 왜 0.75가 이 환경에서 동작하지 않는가**

코사인 유사도는 두 벡터의 방향 일치도를 측정한다. `text-embedding-3-small`은 OpenAI 훈련 데이터에서 학습된 고차원 벡터 공간(1536차원)을 사용하며, 이 공간에서 한국어 CS 개념 노트들의 분포는 다음 특성을 가진다:

- CS 노트는 모두 "알고리즘", "자료구조", "시간복잡도", "구현" 같은 공통 한국어 어휘를 다수 포함해 벡터 방향이 어느 정도 유사해진다 (도메인 내 기반 유사도)
- 반면 서로 다른 주제(BFS↔DFS, HashMap↔힙)는 세부 개념이 달라 유사도가 그리 높지 않다
- 결과적으로 실제 CS 노트 쌍에서 코사인 유사도의 실용 범위는 0.26~0.71 수준

0.75는 이 범위를 벗어난 값으로, "모든 CS 노트가 100건 중 0건을 반환"하는 사실상 비활성화 임계값이었다.

**② 왜 0.55가 최적인가**

score 분포를 분석하면:
- score 범위: 0.26~0.71 (전체)
- score 중앙값: 0.58~0.62 구간
- 0.55 기준 통과 건수: 평균 7.3건 → topK=6 적용 후 상위 6건 활용
- 0.55~0.60 구간(false positive 위험 구간)은 `isTopicRelevant()` 2차 키워드 필터가 처리

0.55 아래로 낮추면 (예: 0.45): 완전히 다른 주제의 노트(BFS↔DB 인덱스, score 0.26~0.45)가 Dense 검색에 진입해 2차 필터 부담 증가.
0.55~0.60 사이를 선택하면: 2건 차이로 결과가 갈리는데, 0.55가 힙·HashMap 등 일부 노트에서 추가로 2건 더 확보할 수 있어 선택.

**③ 수정 후 하이브리드 검색 정상화**
