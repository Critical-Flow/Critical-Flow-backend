## 1. 진행 이유

**1-1. 발견 경위**
`feat/hybrid-search-bm25` 브랜치에서 Dense + Sparse + RRF 하이브리드 검색을 도입했지만, 도입 근거가 "Dense가 함수명·짧은 한국어 CS 용어를 놓친다"는 관찰이었을 뿐, 실제 Recall 향상 수치를 측정한 적이 없었다.

**1-2. 해결하지 않을 경우 영향**
- 하이브리드가 Dense-only 대비 실질적인 Recall 향상이 없다면 Sparse 검색 비용(ChromaDB 2회 호출)이 낭비
- 품질 측정 기준선이 없으면 향후 검색 로직 변경 시 개선/퇴보를 판단할 수 없음

**1-3. 관련 요구사항**
REQ-AIV-011 — 관련 노트 검색 재현율 목표.

**5-3. 하이브리드가 Dense-only보다 효과적인 이유 — 논리적 분석**

**① Dense 검색의 구조적 한계**

`text-embedding-3-small`은 의미 벡터 공간에서 노트를 표현하는데, CS 도메인 노트들은 다음 두 가지 이유로 Dense 검색에 불리하다:

1. **코사인 유사도 천장(0.71)**: 한국어 CS 노트들은 "알고리즘", "자료구조", "시간복잡도" 같은 공통 도메인 어휘 때문에 기반 유사도가 높아 주제별 세밀한 구분이 0.55 임계값 근처에 밀집된다.

2. **개념 연결의 특수성**: "이진 탐색 → 퀵정렬"의 연결은 "분할 정복"이라는 추상 개념을 공유하는데, 이는 텍스트 의미보다 개념 관계에 가깝다. 임베딩 모델은 텍스트 의미는 잘 포착하지만 개념 간 구조적 관계는 덜 포착한다.

**② Sparse 검색이 보완하는 메커니즘**

BM25(키워드 빈도 기반 검색)는 `put()`, `get()`, `O(log n)`, `Arrays.sort()` 같은 구체적 식별자와 기술 용어를 텍스트 매칭으로 찾는다. 이 두 검색 방식은 **서로 다른 유형의 관련성**을 포착한다:

| 검색 방식 | 포착하는 관련성 | 실제 예시 |
|---------|-------------|---------|
| Dense | 의미적 유사성 | BFS↔DFS (그래프 탐색 개념 동일) |
| Sparse | 어휘적/식별자 일치 | 이진탐색↔퀵정렬 ("O(log n)" 공유) |

카테고리 A(기술 식별자 노트)에서 +0.35 향상이 극대화된 이유: "HashMap.put()", "Arrays.sort()", "LinkedList.Node" 같은 식별자가 여러 노트에 등장해 Sparse 매칭이 정확하게 작동했다.

**③ 카테고리 B에서 개선이 제한적인 이유**

"스택↔재귀" 연결은 개념적 연결(재귀 호출 = 스택 사용)인데:
- Dense: 텍스트 의미가 달라 유사도 낮음
- Sparse: "스택" 키워드가 재귀 노트에 한 번 등장하지만 10% 오버랩 임계값 미달
- `isTopicRelevant()` 2차 필터가 이 연결을 차단

→ **개념적 연결은 키워드 오버랩으로 검증하기 어려운 구조적 한계**. 향후 2차 필터 조건 완화 또는 지식 그래프 기반 보완 필요.

**5-4. 개선 효과 해석**

카테고리 A에서 Recall 0.12 → 0.47, 3.9배 향상. Dense가 놓친 "이진 탐색↔시간복잡도", "퀵정렬↔이진 탐색" 연결을 Sparse가 "O(log", "정렬", "알고리즘" 키워드 매칭으로 보완.

카테고리 B에서 트리 순회(0.00→0.75)에서 두드러지지만 스택·큐(각 0.25 유지)에서는 개선 없음. `isTopicRelevant()` 2차 필터가 스택↔재귀, 큐↔힙 같은 개념적 연결을 키워드 기반으로 확인하지 못해 Sparse 후보가 제거됨.

**5-4. 부작용 및 회귀 여부**
noteId=10(힙) 0건: Sparse가 10건 후보를 찾았으나 `isTopicRelevant()` 2차 필터에서 전부 제거됨. 전문 용어 노트에서 2차 필터가 과도하게 작동하는 엣지 케이스 확인.
