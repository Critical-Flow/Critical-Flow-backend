## 1. ~~코드 블록 전처리~~ — 구현 후 제거 (#57)

### 원래 가설

코드+자연어 혼합 노트를 그대로 임베딩하면 두 도메인의 벡터가 평균화되어 의미론적 유사도가 희석된다. 코드 블록을 식별자 목록으로 압축하면 임베딩 품질이 올라갈 것이라 예상했다.

### 측정 결과 (Recall@4)

| 상태 | Recall@4 |
|------|----------|
| 전처리 적용 | 40% |
| 전처리 미적용 (원본 그대로) | **100%** |

전처리 적용 시 오히려 60%p 하락. 원인은 두 가지였다.

- **허브 오염 현상**: DP/메모이제이션 노트가 `HashMap`, `fibonacci` 같은 식별자를 포함하게 되어 10개 쿼리 중 6개의 top4에 잘못 등장
- **문맥 소실**: 식별자 목록으로 압축하면 함수 시그니처·자료 흐름 등 모델이 활용하는 문맥이 사라짐

`text-embedding-3-small`은 코드+자연어 혼합 문서를 원본 그대로 처리하도록 훈련된 모델이어서 전처리가 오히려 역효과를 냈다. **`NoteEmbeddingService`에서 전처리 호출을 제거하고 원본 마크다운을 그대로 임베딩하는 방식으로 전환.**

## 2. 메타데이터 자동 추출 ✅

언어·주제 정보를 저장 시점에 추출해 ChromaDB 메타데이터에 포함한다. 현재 `NoteMetadataExtractor`가 `languages`(코드 블록 언어 태그)와 `headers`(마크다운 헤더)를 추출한다.

현재 용도는 향후 필터 기능 확장을 위한 사전 준비다. "Java 노트만 검색" 같은 언어별 필터링은 아직 사용하지 않는다.

---

## 3. 하이브리드 검색 (Dense + Sparse + RRF) ✅

Dense 단독 검색의 한계 — 한국어 CS 노트 간 코사인 유사도가 대체로 낮아 threshold 기준에서 탈락하는 경우가 많다. 특히 정확한 식별자·함수명 매칭이 약하다.

**해결 방식:**
- Dense(의미 기반)와 Sparse(키워드 포함 여부 기반) 두 검색을 병렬 실행
- RRF(Reciprocal Rank Fusion)로 두 결과를 병합: `score = Σ 1/(60 + rank)`
- 양쪽 검색에서 모두 등장한 문서가 자동으로 상위로 올라오는 구조

`bm25-max-results: 0`으로 설정하면 Dense-only 모드로 전환되어 측정 비교용으로 사용 가능하다 (#62).

## 4. TYPE E 질문 타입 ✅

코드 블록이 포함된 노트에서 코드 동작 자체를 겨냥한 질문을 생성한다. 개념 설명 중심의 TYPE A~D와 달리, 실행 흐름·시간복잡도·엣지케이스 입력 시 동작을 묻는다.

`QuestionTypeRouter`에서 코드 블록(```` ``` ````) 존재 시 LLM 호출 없이 즉시 TYPE_E를 반환하는 규칙 기반 필터로 구현되어 있다. 불필요한 LLM 호출을 줄이는 효과도 있다.

---

## 5. 세션 종료 후 요약 임베딩 ⬜

### 배경

개별 노트만 임베딩되어 있어서 "이 학습자가 특정 개념을 얼마나 어려워했는가" 같은 학습 패턴 정보가 RAG에 없다.

### 방향

세션이 종료(요약 모드 진입)될 때 LLM으로 대화 전체 요약을 생성하고, 이를 별도 Document로 ChromaDB에 저장한다. 형식은 `[학습 주제] | [이해한 부분] | [아직 불명확한 부분]`.

이후 RAG 검색에서 일반 노트와 세션 요약을 함께 검색하되, 프롬프트에서 두 종류를 구분해 주입한다.

### 보류 이유

현재 세션 수가 적어 요약의 RAG 활용 가치가 낮다. 실사용 데이터가 충분히 쌓인 뒤 도입 여부를 재검토한다.

## 6. 텍스트 전용 노트 고도화

### 6-1. 한국어 단어 길이 기준 완화 ✅

기존 `isTopicRelevant()` 2차 필터는 4자 초과 키워드만 유효 단어로 인정했다. 영어는 4자 이하가 대부분 불용어지만, 한국어는 "스택"(2자), "큐"(1자), "재귀"(2자) 같은 핵심 CS 용어가 탈락하는 문제가 있었다.

현재는 한국어 포함 여부를 감지해 최소 길이를 동적으로 적용한다 (한국어: 2자 이상, 영어: 4자 이상).

### 6-2. 마크다운 헤더 기반 메타데이터 ✅

텍스트 전용 노트는 코드 대신 마크다운 헤더로 개념을 구조화한다. `NoteMetadataExtractor.extractHeaders()`가 `#`으로 시작하는 줄을 파싱해 `headers` 메타데이터로 저장한다.

현재 용도는 향후 주제 기반 필터링을 위한 사전 준비다.

### 6-3. TYPE F 질문 타입 ✅

코드 없는 순수 개념 노트에서 단순 정의 확인(TYPE A) 외에 실제 적용 맥락을 묻는 질문 타입을 추가했다. "이 개념이 실제 어떤 문제를 해결하는가", "어떤 상황에서 선택하는가"처럼 암기가 아닌 적용력을 검증한다.

`QuestionType.TYPE_F`로 정의되어 있으며, `QuestionTypePromptProvider`가 타입별 프롬프트 텍스트를 관리한다.

## 7. 질문 타입 사전 라우팅 — Custom Advisor ✅

### 해결한 문제

기존에는 시스템 프롬프트에 TYPE A~F 설명이 모두 포함되어 LLM이 매 턴마다 전체를 읽고 하나를 선택했다. TYPE 설명 전체 약 200 토큰 → 선택된 1개 약 50 토큰으로 절감하고, 선택 로직을 외부로 분리하는 구조로 개선했다.

### 구현 방식

Spring AI의 `CallAdvisor`를 활용해 LLM 호출 직전에 프롬프트를 가로채서 선택된 TYPE 설명만 주입한다. 기존 Spring AI 스택을 유지하면서 라우팅을 추가할 수 있다.

라우팅 로직은 두 단계다.
1. **규칙 기반 필터**: 코드 블록 존재 시 → TYPE_E 즉시 반환 (LLM 호출 없음)
2. **LLM 분류**: 코드 블록 없을 때 → `type-router.st` 프롬프트로 gpt-4o에 분류 요청

분류 결과는 `AiConversation.questionType`에 저장된다.

> `SemanticQuestionTypeRouter`(임베딩 기반 유사도 라우팅)는 설계 단계에서 채택하지 않았다. 노트 내용(도메인 지식)과 TYPE 시드 문장(교육학 메타 설명)이 다른 의미 공간에 위치해 유사도 비교가 의미 없는 값을 낸다는 점이 확인됐기 때문이다. 상세 논의는 `question-type-routing.md` 참조.

## 8. 질문 타입 학습 데이터 축적 ✅

`AiConversation.questionType` 컬럼에 라우팅 결정 결과를 저장해 (노트 내용 → TYPE) 쌍을 누적한다. 향후 Fine-tuning 시 이 데이터가 핵심 학습 데이터가 된다.

자세한 전환 전략은 `question-type-routing.md` 참조.
