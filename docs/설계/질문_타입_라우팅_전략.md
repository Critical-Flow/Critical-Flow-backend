# 질문 타입 라우팅 전략

## 배경

AI 튜터가 학습 노트를 분석해 TYPE A~F 중 가장 적합한 질문 유형을 선택하는 알고리즘에 대한 논의 및 최종 방향 결정.

### TYPE 정의

| TYPE | 특성 | Bloom's 대응 |
|------|------|-------------|
| A | 개념 정의/검증 — 새로운 용어나 개념이 등장한 노트 | Knowledge (기억) |
| B | 설계 의도 탐구 — 왜 그 방식을 선택했는지, 트레이드오프 | Evaluation (평가) |
| C | 스페이스드 리콜 — 이전 학습과 연결되는 내용 (RAG 필요) | Comprehension (이해) |
| D | 심층 사고 탐구 — 엣지케이스, 실패 케이스, 경계 조건 | Analysis (분석) |
| E | 코드 추적 — 코드 블록 포함, 알고리즘/구현 노트 | (별도) |
| F | 적용 탐구 — 이론만 있고 실제 맥락이 없는 순수 정의 노트 | Application (적용) |

---

## 논의한 방법들

### 1. 코사인 유사도 기반 라우팅 (SemanticQuestionTypeRouter)

각 TYPE마다 대표 시드 문장 3개를 정의하고, 앱 시작 시 임베딩해서 캐싱한 뒤 노트 임베딩 벡터와 코사인 유사도를 비교하는 방식.

```
노트 내용 → embed() → noteVec
각 TYPE 시드 문장 → averageEmbedding() → seedVec
cosineSimilarity(noteVec, seedVec) 최댓값 TYPE 선택
```

**문제점 — 채택 불가**

노트 내용("JWT는 Header.Payload.Signature 구조다")과 TYPE 시드("새로운 개념이나 용어가 처음 등장한 노트")는 **의미 공간 자체가 다르다.** 노트는 도메인 지식 벡터 공간에, TYPE 시드는 교육학 메타 설명 벡터 공간에 위치하므로 유사도가 의미 없는 값이 나온다.

---

### 2. 규칙 기반 분류

노트의 구조적 특징으로 TYPE을 판단하는 방식.

```
코드 블록(```) 존재? → TYPE E
"왜", "이유", "선택", "트레이드오프" 포함? → TYPE B
RAG 결과 있음? → TYPE C 후보
신규 용어 비율 높음? → TYPE A
```

**평가**

- 구현 간단, 비용 없음
- 도메인/언어에 무관하게 동작
- 단순한 케이스(TYPE E)는 정확하지만, 복합적인 노트에서 정확도 한계 존재
- 단독 사용보다 전처리 필터로 적합

---

### 3. LLM Chain-of-Thought 분류

TYPE A~F 정의와 few-shot 예시를 프롬프트에 포함해서 LLM이 직접 분류하도록 하는 방식.

```
[프롬프트]
노트 내용 + TYPE A~F 정의 + 5개 예시
→ "가장 적합한 TYPE은? 이유와 함께 답하라"
→ TYPE_X 반환
```

**평가**

- 노트 도메인과 교육학적 맥락을 동시에 이해 가능
- 한국어/영어 혼용 노트에도 동작
- 호출당 추가 레이턴시/비용 발생

---

### 4. Fine-tuned 분류 모델

(노트, TYPE) 쌍 데이터로 학습한 전용 분류기. 추론 시 추가 LLM 호출 없이 빠르게 동작.

**후보 데이터셋**

| 데이터셋 | 크기 | 접근 방법 |
|---------|------|----------|
| PLOS ONE 부록 데이터 | 16,584개 질문 | [공식 다운로드](https://doi.org/10.1371/journal.pone.0230442.s002) |
| BloomNet GitHub | 미상 | [github.com/macabdul9/BloomNet](https://github.com/macabdul9/BloomNet) |

**문제점**

- 모든 공개 데이터셋이 영어 기반
- 스리랑카 대학 시험 문제 도메인 → 한국어 개발자 노트와 도메인 불일치
- TYPE E(코드 추적)는 Bloom's Taxonomy에 없어 별도 데이터 필요
- 초기 도메인 특화 데이터 부족

## 정확도 비교

| 방법 | 정확도 | 구현 난이도 | 비용 |
|------|--------|------------|------|
| 코사인 유사도 | 낮음 (설계 결함) | 낮음 | 무료 |
| 규칙 기반 | 중간 | 낮음 | 무료 |
| LLM 분류 | 높음 | 중간 | 호출당 소액 |
| Fine-tuned 모델 | 최고 | 높음 | 학습 비용 |

---

## 최종 결정: 3단계 점진적 전환

### 1단계 — 현재 구현 상태 ✅

**규칙 필터 + LLM 분류 혼합**

- 코드 블록 존재 시 → TYPE_E 즉시 반환 (LLM 호출 없음)
- 그 외 → gpt-4o(`type-router.st` 프롬프트)로 TYPE 결정
- TYPE_C 분류 시 RAG 결과가 없으면 → TYPE_A로 폴백
- LLM 응답이 6종 외의 값이거나 매칭 실패 시 → TYPE_A로 폴백 (기본값)
- 라우팅 결정 결과를 `AiConversation.questionType`에 저장해 학습 데이터로 축적

```
노트 입력
    ↓
[규칙 필터] 코드 블록 있음? → TYPE E 즉시 반환
    ↓ (없으면)
[LLM 분류] gpt-4o에 TYPE 결정 요청
    ↓
[폴백] TYPE_C + RAG 없음 → TYPE_A / 매칭 실패 → TYPE_A
    ↓
결과를 AiConversation.questionType DB 저장
```

### 2단계 — 데이터 축적 후 (노트 200~300개)

**OpenAI Fine-tuning**

- 1단계에서 쌓인 (노트 → TYPE) 쌍을 학습 데이터로 활용
- PLOS ONE 데이터를 Bloom's → TYPE 레이블 변환 후 보강
- Fine-tuned 모델로 교체

```
PLOS ONE 데이터 (Bloom's → TYPE 매핑)
    +
서비스에서 축적된 실제 노트 데이터 (200~300개)
    ↓
OpenAI Fine-tuning
    ↓
ft:gpt-4o:... 모델 ID 발급
```

### 3단계 — 운영 안정화

- Fine-tuned 모델로 전면 교체
- LLM 분류 대비 비용 절감 + 응답 속도 향상
- 지속적으로 새 데이터 축적 → 주기적 재학습

---

## 핵심 판단 근거

> 1단계에서 LLM 분류로 시작하는 이유는 단순히 "지금 데이터가 없어서"가 아니다.
> LLM이 내리는 분류 결정 자체가 이 프로젝트의 도메인(한국어, CS/개발 노트)에 특화된
> 학습 데이터가 되기 때문이다. 이 데이터가 나중에 fine-tuning을 할 때 가장 값진 자산이 된다.
