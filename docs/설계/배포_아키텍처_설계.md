# Critical Flow 백엔드 배포 아키텍처 설계

> 작성일: 2026-05-22  
> 대상 환경: AWS EC2 + Docker + GitHub Actions  
> 배포 방식: 자동 CI/CD (main 브랜치 push 트리거)

---

## 1. 전체 아키텍처

```
개발자 PC
  └─ git push origin main
          │
          ▼
  [GitHub Actions]
    1) Gradle 빌드 & 테스트
    2) Docker 이미지 빌드
    3) GHCR(GitHub Container Registry)에 push
    4) EC2 SSH 접속 → 새 이미지 pull → 컨테이너 재시작
          │
          ▼
      [EC2 서버 - t2.small]
        ├── Nginx 컨테이너  :80, :443  ← 외부 진입점
        ├── Spring Boot 컨테이너  :8080  (외부 미노출)
        ├── MySQL 컨테이너  :3306  (외부 미노출)
        └── ChromaDB ← 팀원 외부 서버 (IP로 연결)
```

---

## 2. 인프라 구성 결정 근거

### 2-1. EC2 인스턴스

| 항목 | 결정 | 이유 |
|---|---|---|
| 인스턴스 타입 | **t2.small** (1 vCPU / 2GB RAM) | t2.micro(1GB)는 Spring Boot + MySQL 동시 실행 시 OOM 위험. t2.medium은 학습 프로젝트에 과함 |
| OS | **Ubuntu 22.04 LTS** | Docker 설치 자료·레퍼런스가 압도적으로 많음. Amazon Linux는 같은 문제도 자료 찾기 어려움. 팀원 간 명령어 통일성 확보. 2027년까지 LTS 보안 지원 |

### 2-2. 이미지 레지스트리

| 항목 | 결정 | 이유 |
|---|---|---|
| 레지스트리 | **GHCR** (GitHub Container Registry) | GitHub 조직과 자동 연동, `GITHUB_TOKEN`으로 별도 시크릿 없이 인증, private 이미지 팀 공유 무료 |
| 이미지 태그 | `latest` + `sha-{커밋해시}` | latest: 항상 최신 참조 / sha 태그: 특정 버전 롤백 가능 |

### 2-3. MySQL 배치

| 항목 | 결정 | 이유 |
|---|---|---|
| 배치 방식 | **EC2 내부 Docker 컨테이너** | AWS RDS 최저 스펙도 월 $15 추가 발생. 학습 프로젝트 수준에서 불필요 |
| 데이터 영속성 | **Docker Named Volume** | 컨테이너 교체/재시작과 완전히 독립적으로 데이터 유지 |

### 2-4. ChromaDB

팀원 서버에서 이미 독립적으로 운영 중. 우리 서버에서는 환경변수(`CHROMA_HOST`, `CHROMA_PORT`)로 외부 IP만 지정하여 연결. 데이터 관리 책임은 해당 서버에 있음.

### 2-5. HTTPS

| 항목 | 결정 | 이유 |
|---|---|---|
| SSL 인증서 | **Let's Encrypt (Certbot)** | 무료, 90일 자동 갱신, Nginx와 통합 용이 |
| 프록시 | **Nginx** | 80→443 리다이렉트, SSL 종료, Spring Boot 앞단 처리 |
| 전제 조건 | **도메인 필수** | IP 기반 SSL 인증서 발급 불가 |

## 3. EC2 내부 컨테이너 구성

```
┌─────────────────────────────────────────────────────┐
│                    EC2 (t2.small)                   │
│                                                     │
│  ┌──────────────────────────────────────────────┐  │
│  │            Docker 내부 네트워크               │  │
│  │            (criticalflow-net)                │  │
│  │                                              │  │
│  │  ┌──────────┐      ┌──────────────────────┐  │  │
│  │  │  Nginx   │─────▶│    Spring Boot       │  │  │
│  │  │  :80/443 │      │    :8080             │  │  │
│  │  └──────────┘      └──────────┬───────────┘  │  │
│  │                               │              │  │
│  │                    ┌──────────▼───────────┐  │  │
│  │                    │       MySQL          │  │  │
│  │                    │       :3306          │  │  │
│  │                    └──────────────────────┘  │  │
│  └──────────────────────────────────────────────┘  │
│                                                     │
│  볼륨                                               │
│  ├── criticalflow-mysql-data → MySQL 데이터         │
│  └── certbot-etc → SSL 인증서                       │
└─────────────────────────────────────────────────────┘
         │
         │ 외부 연결
         ▼
    ChromaDB (팀원 서버 IP:8000)
```

### 컨테이너 간 통신

| 출발 | 목적지 | 주소 |
|---|---|---|
| Nginx → Spring Boot | Docker 내부 | `http://app:8080` |
| Spring Boot → MySQL | Docker 내부 | `jdbc:mysql://db:3306/criticalflow` |
| Spring Boot → ChromaDB | 외부 네트워크 | `http://[팀원서버IP]:8000` |

## 4. 보안그룹 설정

| 포트 | 허용 대상 | 용도 |
|---|---|---|
| 22 (SSH) | 관리자 IP만 | 서버 접속 + GitHub Actions 배포 |
| 80 (HTTP) | 0.0.0.0/0 | HTTPS 리다이렉트 수신 |
| 443 (HTTPS) | 0.0.0.0/0 | 실제 API 트래픽 |
| 8080 | **미오픈** | Nginx 뒤에 숨김 |
| 3306 | **미오픈** | 컨테이너 내부 통신만 |

## 5. GitHub Actions CI/CD 흐름

### 트리거
- `main` 브랜치에 push 될 때만 실행
- `develop` 브랜치는 개발용, 배포 대상 아님

### Job 구성

```
Job 1: build-and-push
  ├── actions/checkout
  ├── JDK 17 설정
  ├── Gradle 의존성 캐시 복원
  ├── ./gradlew build (테스트 포함)
  ├── GHCR 로그인 (GITHUB_TOKEN 자동 사용)
  └── Docker 이미지 빌드 & push (latest + sha 태그)

Job 2: deploy  ← Job 1 성공 시에만 실행
  ├── EC2 SSH 접속
  ├── .env 파일 갱신 (GitHub Secrets → EC2)
  ├── docker compose pull app
  ├── docker compose up -d
  └── /health 엔드포인트 헬스체크
```

### GitHub Secrets 목록

| Secret | 설명 |
|---|---|
| `EC2_HOST` | EC2 퍼블릭 IP 주소 |
| `EC2_USER` | EC2 접속 유저명 (`ec2-user`) |
| `EC2_SSH_KEY` | EC2 .pem 키 파일 전체 내용 |
| `DB_USERNAME` | MySQL 유저명 |
| `DB_PASSWORD` | MySQL 비밀번호 |
| `JWT_SECRET` | JWT 서명 키 (32자 이상 랜덤) |
| `OPENAI_API_KEY` | OpenAI API 키 |
| `GITHUB_CLIENT_ID` | GitHub OAuth App Client ID |
| `GITHUB_CLIENT_SECRET` | GitHub OAuth App Client Secret |
| `CHROMA_HOST` | ChromaDB 서버 주소 (예: `http://x.x.x.x`) |
| `CHROMA_PORT` | ChromaDB 포트 (기본 `8000`) |
| `FRONTEND_CALLBACK_URL` | 프론트 OAuth 콜백 URL |

## 6. Dockerfile 설계

멀티스테이지 빌드 방식 채택.

```
Stage 1 (builder): eclipse-temurin:17-jdk-alpine
  목적: JAR 파일 생성
  작업: Gradle 의존성 설치 → bootJar 빌드

Stage 2 (runtime): eclipse-temurin:17-jre-alpine
  목적: 경량 운영 이미지
  작업: builder에서 생성된 app.jar만 복사
  보안: root 아닌 spring 전용 유저로 실행
```

최종 이미지 크기: ~200MB (JDK 포함 시 ~500MB 대비 60% 절감)

## 7. 데이터 영속성 보장

### 원칙
> 컨테이너가 교체되어도 데이터는 절대 초기화되지 않는다.

### MySQL

- Docker Named Volume (`criticalflow-mysql-data`) 사용
- 실제 데이터 저장 위치: EC2의 `/var/lib/docker/volumes/criticalflow-mysql-data/`
- `docker compose up -d` 배포 시 MySQL 컨테이너는 설정 변경이 없으면 **재시작하지 않음**
- app 컨테이너만 교체됨

### 절대 사용 금지 명령어

```bash
# ❌ 볼륨까지 삭제됨 → DB 데이터 전부 소실
docker compose down -v

# ✅ 안전 (볼륨 유지)
docker compose down
docker compose up -d
```

GitHub Actions 배포 스크립트에서 `down -v` 는 사용하지 않으며, `docker compose pull` + `docker compose up -d` 조합만 사용한다.

### ChromaDB

팀원 서버에서 관리. 우리 측 코드/컨테이너 배포와 완전히 독립적.

## 8. HTTPS 인증서 관리

- 발급 주체: Let's Encrypt (Certbot)
- 인증서 저장: Docker Named Volume (`certbot-etc`) → `/etc/letsencrypt/`
- 갱신 주기: 90일마다 자동 갱신 (Certbot 내장 cron)
- 갱신 시 동작: `nginx -s reload` (다운타임 없음)
- 최초 발급: 서버 최초 세팅 시 1회 수동 실행 필요

## 9. 배포 타임라인

| 단계 | 소요 시간 | 비고 |
|---|---|---|
| Gradle 빌드 & 테스트 | 1~3분 | 캐시 있으면 1분대 |
| Docker 이미지 빌드 | 1~2분 | 레이어 캐시 활용 |
| GHCR push | 30초~1분 | |
| EC2 배포 | 30초~1분 | app 컨테이너 교체 시 약 10~20초 다운타임 |
| **전체** | **약 5~8분** | |
