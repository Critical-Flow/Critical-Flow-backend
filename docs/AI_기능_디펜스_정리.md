## 1. RAG 기능 — AI-003 노트 임베딩 및 관련 노트 검색

### Q. 제외 노트 식별자 입력이 실제 코드에 존재하는가?

존재한다. `RagRetrievalService.retrieve(String queryText, Long userId, Long excludeNoteId)` 시그니처로 정의되어 있으며, dense·sparse 두 검색 모두 Chroma 필터 조건 `note_id != '...'`으로 해당 노트를 결과에서 제외한다.

호출 지점은 `AiTutorService`이며, `note.getNoteId()`를 그대로 전달한다. 별도 DTO로 외부에 공개된 형태는 아니고, 서비스 내부 메서드 파라미터로 존재한다.

---

### Q. 출력 구조가 DRD 명세와 일치하는가?

`RagContext.RetrievedChunk`가 명세와 완전히 일치한다.

| DRD 명세 필드 | 실제 코드 필드 | 타입 |
|---|---|---|
| 관련 노트 컨텍스트 항목 목록 | `List<RetrievedChunk> chunks` | 객체 목록 |
| ↳ 제목 | `String title` | 문자열 |
| ↳ 세션 식별자 | `String sessionId` | 문자열 |
| ↳ 본문 내용 | `String content` | 문자열 |
| ↳ 관련도 점수 | `double score` | 실수 |

빈 목록 처리는 `RagContext.isEmpty()` 메서드가 담당한다.

---

### Q. "본문 내용"이 전체인가, 일부인가?

**전체 본문이 들어간다.** `NoteEmbeddingService.embed()`에서 `note.getContent()` 전체를 단일 Document로 저장하며, 검색 시 `doc.getText()`로 그 전체를 `content`에 넣는다. 청킹(분할) 로직은 없다.

---

### Q. 왜 노트 전체 본문을 임베딩하는가? 코드 블록을 따로 처리하지 않는 이유는?

**#57 측정 실험 결과에 근거한 결정이다.**

원래 `NotePreprocessor`로 코드 블록을 식별자 목록 형태(`[java: HashMap containsKey fibonacci ...]`)로 변환한 뒤 임베딩했다. 그러나 `text-embedding-3-small` 모델에서 실제 측정해보니 전처리 적용 시 Recall@4가 **100% → 40%로 60%p 하락**했다.

**하락 원인 두 가지:**

1. **qnote-7 허브 오염 현상**: DP/메모이제이션 노트가 `HashMap`, `containsKey`(HashMap 노트 식별자), `fibonacci`(재귀 노트 식별자)를 동시에 포함하게 되어, 10개 쿼리 중 6개의 top4에 잘못 등장했다.

2. **문맥 소실**: `extractIdentifiers`는 코드를 단어 단위로 쪼개 순서 없이 나열한다. 함수 시그니처·자료 흐름 등 모델이 활용하는 문맥 정보가 소실된다. `text-embedding-3-small`은 코드+자연어 혼합 문서를 원문 그대로 처리하도록 훈련되어 있어 원문 유지가 더 정확하다.

---

### Q. 측정 테스트 노트가 모두 코드 블록을 포함한 것이었는데, 코드 없는 개념 노트에도 동일 결론이 적용되는가?

**적용된다고 단정할 수 없다.** 측정에 사용된 10개 노트는 모두 코드 블록이 포함된 CS 주제(HashMap, 이진탐색, BFS 등)였다. 코드 블록 없이 개념 설명만 있는 노트에 대한 검증은 이번 실험에 포함되지 않았다. 현재 결론은 코드 블록 포함 노트에 한정된 측정 결과다.

---

### Q. ChromaDB를 2회 호출하는 이유는?

Dense 검색과 Sparse 검색을 각각 별도로 실행하기 때문이다.

| 호출 | 방식 | 목적 |
|---|---|---|
| 1회차 (Dense) | 벡터 유사도 검색 (similarity threshold 0.55) | 의미적으로 유사한 노트 검색 |
| 2회차 (Sparse) | threshold 0.0으로 넓게 후보 수집 후 키워드 포함 여부 필터 | 핵심 키워드가 포함된 노트 검색 |

두 결과를 **RRF(Reciprocal Rank Fusion)**로 병합해 최종 top-4를 반환한다. RRF는 각 순위 리스트의 순위값을 `1/(k+rank)` 점수로 변환해 합산하는 방식이다.

Dense 검색은 "비슷한 느낌의 노트"를 찾는 방식이고, Sparse 검색은 특정 키워드가 실제로 포함된 노트를 직접 찾아오는 방식이다. Dense만으로는 threshold를 아슬아슬하게 못 넘겨 탈락하는 관련 노트가 생기는데, Sparse가 이를 키워드 기반으로 보완한다.

**#62 측정으로 확인한 효과:**

| 검색 방식 | 전체 평균 Recall@4 |
|---|---|
| Dense-only | 0.18 (10번 검색 중 2번 꼴로 관련 노트 발견) |
| 하이브리드 | 0.43 (10번 검색 중 4번 이상 관련 노트 발견) |

특히 "BFS", "DFS"처럼 코사인 유사도가 0.26으로 낮게 측정되는 대립 개념 쌍은 Dense만으로 서로를 찾지 못하지만, Sparse가 "BFS", "DFS" 키워드로 연결해준다.

### Q. REQ-AIV-003 — 현재 노트를 검색 결과에서 제외하는 이유는?

RAG 검색 쿼리가 현재 노트의 **원문 전체**이기 때문이다. 현재 노트를 제외하지 않으면 벡터 유사도가 사실상 1.0에 가까워 자기 자신이 항상 1위로 반환되고, 실제로 필요한 과거 관련 노트들이 밀려난다.

RAG의 목적은 "현재 노트와 연관된 다른 과거 노트를 찾는 것"이므로, 이미 컨텍스트에 포함된 현재 노트를 다시 가져오는 것은 기능적으로 의미가 없다.

## 2. RAG 설정값

### Q. ChromaDB 컬렉션 설정값(ef_construction, ef_search, max_neighbors 등)을 이렇게 선택한 이유는?

컬렉션명(`criticalflow-notes`)만 직접 지정했고, 나머지 설정은 Spring AI / ChromaDB 기본값을 그대로 사용한 것이다.

| 항목 | 값 | 선택 주체 |
|---|---|---|
| 컬렉션명 | `criticalflow-notes` | 직접 지정 (application.yml) |
| 유사도 공간 | cosine | Spring AI 기본값 |
| ef_construction / ef_search | 100 / 100 | ChromaDB 기본값 |
| max_neighbors | 16 | ChromaDB 기본값 |

**cosine을 사용하는 이유:** cosine 유사도는 벡터의 방향(의미)을 기준으로 비교하기 때문에 텍스트 임베딩 유사도 측정에 적합하다. 크기가 아닌 방향을 보므로 노트의 길이에 영향을 받지 않는다.

**HNSW 파라미터를 조정하지 않은 이유:** `ef_construction`, `ef_search`, `max_neighbors`는 수십만 건 이상의 대규모 데이터에서 조정 효과가 나타난다. 현재 학습 노트 규모(수백 건)에서는 기본값으로 충분하고, #60·#62 측정 실험에서 검색 품질을 직접 확인했기 때문에 별도 조정이 불필요하다고 판단했다.

---

### Q. ChromaDB 메타데이터에 해당 필드들을 넣은 이유는?

메타데이터는 두 가지 목적으로 구성했다.

**현재 실제로 사용하는 필터용:**

| 필드 | 사용 목적 |
|---|---|
| `note_id` | 현재 노트 자신을 검색 결과에서 제외 (`note_id != excludeNoteId` 필터) |
| `user_id` | 다른 학습자의 노트가 검색되지 않도록 사용자 격리 (`user_id == userId` 필터) |
| `session_id` | 검색 결과를 AI 튜터 프롬프트에 주입할 때 출처 정보 표시 |
| `title` | 동일하게 프롬프트 출력 시 노트 제목 표시 |

**향후 확장 대비로 사전 저장:**

| 필드 | 향후 활용 방안 |
|---|---|
| `created_at` | "최근 N일 이내 노트만 검색" 같은 시간 기반 필터 |
| `languages` | "Java 노트만 검색" 같은 언어 필터 |
| `headers` | 주제 기반 필터 |

`created_at`, `languages`, `headers`는 현재 검색 필터로 사용하지 않지만, 노트를 재임베딩하지 않아도 나중에 언어별·시간별·주제별 검색을 추가할 수 있도록 미리 준비해 둔 것이다.

---

### Q. question_type도 ChromaDB 메타데이터에 넣을 수 있는가?

기술적으로는 가능하지만 적합하지 않다.

`question_type`은 노트가 아니라 **대화 단위**로 결정된다. 노트 하나에 대화가 여러 개 생길 수 있고, 각 대화마다 다른 question_type이 부여된다.

```
노트 1개 → 대화 A: TYPE_E
          → 대화 B: TYPE_A
          → 대화 C: TYPE_D
```

ChromaDB 메타데이터는 노트 단위로 저장되므로 어떤 대화의 타입을 기준으로 저장할지가 모호하다. 잘못된 타입이 고정되면 노트를 재임베딩해야 하는 문제도 생긴다.

**현재 설계가 올바른 이유:** `question_type`은 `AiConversation.questionType` 컬럼(MySQL)에 대화별로 저장한다. 이렇게 해야 타입이 대화마다 독립적으로 기록되고, 향후 fine-tuning 학습 데이터로도 누적할 수 있다.

---

### Q. 노트 수가 많아지면 현재 임계값 설정을 수정해야 하는가?

맞다. 두 가지 설정이 데이터 증가에 따라 재검토가 필요하다.

**재검토 필요:**

| 설정 | 이유 |
|---|---|
| `similarity-threshold: 0.55` | 노트 20개 기준으로 측정한 값. 노트가 늘어나면 벡터 공간 분포가 달라져 0.55에서 통과하는 노이즈 문서가 증가할 수 있음 → 임계값 상향 검토 |
| `isTopicRelevant` 키워드 오버랩 10% | 노트 10개 환경 기준. 노트가 많아지면 2차 필터가 걸러야 할 노이즈도 늘어남 → 임계값 상향 검토 |

**데이터 양과 무관한 설정:**

| 설정 | 이유 |
|---|---|
| `max-results: 4` | 프롬프트 길이 기준으로 결정된 값, 데이터 양과 무관 |
| `bm25-max-results: 10` | 쿼리 특성에 의존, 데이터 양보다 키워드 히트 확률이 기준 |
| HNSW 파라미터 (ef_construction 등) | 수십만 건 이상에서 조정 효과 발생, 수백~수천 건 수준은 무관 |

재검토 시점은 노트 수가 크게 늘었을 때 `#62` 측정과 동일하게 Recall@4를 다시 측정해서 판단한다.

---

### Q. bm25-max-results는 어떤 역할을 하는가?

Sparse 검색에서 후보를 몇 개까지 가져올지 정하는 값이다.

Sparse 검색은 두 단계로 이루어진다.

```
1단계: threshold=0.0으로 ChromaDB에서 상위 10건 수집  ← bm25-max-results=10
2단계: 수집된 10건 중 키워드가 실제로 포함된 것만 통과
```

`0`으로 설정하면 Sparse 검색 자체를 건너뛰어 Dense-only 모드가 된다. #62 측정 실험에서 Dense-only vs 하이브리드를 비교하기 위한 스위치로 사용했다.

---

### Q. Dense topK=6, Sparse topK=10으로 설정한 이유는? 왜 하필 6과 10인가?

**Dense topK=6:** `max-results + 2 = 4 + 2 = 6`으로 코드에 명시되어 있다. 최종 반환 수 4개에 2차 필터 탈락 여유분 2개를 더한 값이다. `+2`는 "몇 개 정도면 충분하겠다"는 판단이며 측정으로 최적화한 값은 아니다.

**Sparse topK=10:** `bm25-max-results: 10`에서 온다. #60 측정 실험에서 상위 10건을 기준으로 실험했고, 해당 값이 충분한 후보를 확보했기 때문에 그대로 운영값으로 사용했다.

두 값 모두 엄밀하게 최적화된 것은 아니며, 노트 수가 늘어나면 Recall@4 재측정을 통해 조정이 필요할 수 있다.

---

### Q. topK는 벡터 DB 크기에 따라 달라지는가?

직접적이라기보다 **간접적**으로 영향을 받는다. topK 자체는 "몇 개를 가져올지"이므로 DB 크기와 무관하게 동작하지만, DB가 커지면 topK로 가져온 결과의 **품질**이 달라진다.

| DB 규모 | 상황 |
|---|---|
| 노트 20개 (현재) | topK=6이면 전체의 30%를 가져옴. 관련 없는 노트도 상위권에 오를 가능성 높음 |
| 노트 1000개 | topK=6이면 전체의 0.6%만 가져옴. 벡터 공간이 조밀해져 상위 6개의 유사도가 더 의미 있음 |

DB가 커질수록 `similarity-threshold`를 높여도 충분한 후보가 확보되므로 임계값을 올릴 수 있다. 결국 노트 수가 크게 늘면 `similarity-threshold`와 `topK`를 함께 재검토해야 한다.

## 3. AI 기능 — AI-001 튜터 응답 생성 / AI-002 질문 유형 분류

### Q. REQ-AIV-006 — 정의되지 않은 유형이 출력되지 않음을 어떻게 보장하는가?

`QuestionTypeRouter.parseType()`이 두 단계 폴백으로 보장한다.

```
LLM 응답 수신
  → QuestionType.values() 순회하여 매칭 시도
    → TYPE_C 매칭 + RAG 없음 → TYPE_A 폴백
    → 정의된 유형 매칭 → 해당 유형 반환
    → 매칭 실패 (정의되지 않은 값) → TYPE_A 반환 (기본값)
```

코드 블록이 있는 노트는 LLM 호출 없이 규칙 기반으로 즉시 TYPE_E를 반환하므로 LLM 오류 자체가 발생하지 않는다.

| 상황 | 결과 |
|---|---|
| 코드 블록 포함 | TYPE_E 즉시 반환 (규칙 기반, LLM 호출 없음) |
| TYPE_C 분류 + RAG 없음 | TYPE_A로 폴백 |
| LLM 응답이 6종 외의 값 | TYPE_A로 폴백 (기본값) |

---

### Q. 노트 내용이 바뀌어야 question_type도 바뀌는 것 아닌가?

반드시 그렇지는 않다. `QuestionTypeRouter`는 **노트 내용 + RAG 결과** 두 가지를 보고 타입을 결정하기 때문이다.

**RAG 결과가 달라질 때:** 과거 노트가 새로 추가되면 RAG 검색 결과가 바뀌어 TYPE_C(과거 학습 연계)가 선택될 수 있다. 처음 대화 시작 시 관련 과거 노트가 없어서 TYPE_A였다가, 이후 관련 노트가 생기면 같은 노트로 대화를 다시 시작해도 TYPE_C가 나올 수 있다.

**코드 블록이 있는 노트는 예외:** LLM 호출 없이 규칙 기반으로 TYPE_E를 즉시 반환하므로 항상 고정된다.

---

### Q. REQ-AIV-010 — 요약 응답 모드 전환이 어떻게 구현되어 있는가?

`AiTutorService`의 `MAX_QUESTIONS = 5` 상수로 제어된다. 응답 반환 시 `questionCount + 1 >= MAX_QUESTIONS`를 계산해 `summaryMode` 필드에 담는다. 이 값은 코드 상수에 의해 결정론적으로 동작하므로 LLM 출력과 무관하다.

무의미 발화 판정은 두 기준으로 구성된다.
- 길이 기준: `message.trim().length() < 5`
- 어휘 목록 기준: `"아", "어", "음", "몰라", "idk", "?"` 등 FILLER_WORDS 집합 포함 여부

무의미 발화 감지 시 LLM 호출 없이 직전 AI 질문을 재제시한다.

---

### Q. REQ-AIV-007 — LLM 빈 응답·오류 시 재시도 안내가 구현되어 있는가?

**미구현 상태다.** 현재 `chatClient.prompt()...call()` 호출에 try-catch가 없어, LLM 오류 발생 시 예외가 `GlobalExceptionHandler`로 전달되어 500이 반환된다. DRD 명세(LLM 타임아웃·오류 → 502, 빈 응답 → 200 재질문 안내)와 다르게 동작한다.

---

### Q. REQ-AIV-005 — 프롬프트 인젝션 방어가 어떻게 이루어지는가?

별도의 인젝션 탐지·차단 코드는 없다. 방어는 프롬프트 구조 수준에서 이루어진다. 학습자 메시지는 시스템 프롬프트와 분리된 `user` 역할 메시지로 전달되고, 시스템 프롬프트는 `resolvePrompt()`에서 템플릿 치환으로 고정된다.

검증은 인젝션 시도 패턴 테스트셋 발화를 전송해 행동 규약(REQ-AIV-008, REQ-AIV-009) 위반율이 임계값 이하인지 확인한다. 임계값은 `[TBD]`로 미확정 상태다.

### Q. 위반율 임계 기반 모니터링이란 무엇이며 왜 이 방식을 선택했는가?

외부 LLM의 출력은 확률적이기 때문에 "항상 100% 준수"를 보장할 수 없다. 따라서 다음과 같은 통계적 검증 방식을 사용한다.

1. 테스트셋 N개 발화를 실제 API에 전송
2. 위반 횟수 / N = 위반율 계산
3. 위반율이 임계값 이하이면 통과, 초과 시 프롬프트 정책 재검토

| 요구사항 | 성격 | 검증 방식 |
|---|---|---|
| REQ-AIV-010 (요약 모드 전환) | 결정론적 — `MAX_QUESTIONS` 상수로 제어 | 일반 통합 테스트 |
| REQ-AIV-008 (정답 미포함) | 확률적 — LLM 출력에 의존 | 위반율 임계 기반 (수동 검수) |
| REQ-AIV-009 (질문 1개) | 확률적 — LLM 출력에 의존 | 위반율 임계 기반 (의문문 카운팅 자동화 가능) |

현재 임계값 수치는 전부 `[TBD]`로 미확정 상태다.

## 4. AI 설정값

### Q. 같은 LLM을 호출하는데 동일한 입력에서 타입이 달라질 수 있는가?

`temperature: 0.3`으로 설정되어 있기 때문에 이론적으로는 달라질 수 있다. `temperature: 0`이면 항상 동일한 출력이 나오지만, 0.3은 약간의 무작위성이 있어 같은 입력이어도 다른 결과가 나올 수 있다.

다만 질문 타입 분류는 프롬프트가 명확하고 출력이 `TYPE_A`~`TYPE_F` 중 하나로 단순하기 때문에 실제로 다른 타입이 나올 가능성은 매우 낮다.

---

### Q. AI 튜터 응답시간 목표를 15초로 잡은 근거는?

RAG 검색(ChromaDB 2회 호출) 약 500ms + gpt-4o API 호출 약 3–10초를 합산하면 P90 기준 15초가 현실적이다. gpt-4o는 프롬프트·응답 길이와 OpenAI 서버 부하에 따라 변동이 크므로 10초 목표는 달성이 어렵다.

---

### Q. 처리량 목표의 상한이 코드가 아닌 OpenAI Rate Limit인 이유는?

시스템 자체에 Rate Limit 로직이 없다. AI 기능 요청 1건마다 OpenAI API를 1회 이상 호출하므로, 사실상 처리량 상한은 가입한 OpenAI 요금제의 RPM(Requests Per Minute) 한도가 결정한다.

---

### Q. ChromaDB 장애 시 빈 컨텍스트 폴백이 구현되어 있는가?

**미구현 상태다.** `RagRetrievalService`에 try-catch가 없어 ChromaDB 오류 발생 시 예외가 전파되어 500이 반환된다. DRD 명세(빈 컨텍스트 반환 후 AI-001 계속 수행)와 다르게 동작한다.

마찬가지로 `NoteService.saveNote()`에서 `noteEmbeddingService.embed()`가 예외를 던지면 트랜잭션이 롤백되어 노트 저장도 실패한다. DRD 명세(노트 저장 성공, 임베딩 실패 로깅)와 다르게 동작한다.

---

### Q. RPO 복구 수단이 있는가?

임베딩 손실 시 `POST /api/notes/reembed` 엔드포인트로 전체 재임베딩이 가능하다. 노트·대화 기록 원본은 MySQL에 저장되므로 DB 백업이 있으면 데이터 복구 후 재임베딩으로 ChromaDB를 재구성할 수 있다.
