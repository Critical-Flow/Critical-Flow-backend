# AI-003 노트 임베딩 및 관련 노트 검색 — 디펜스

> 관련 코드: `NoteEmbeddingService`, `NoteMetadataExtractor`, `RagRetrievalService`, `RagContext`  
> 관련 요구사항: REQ-AIV-002, 003, 004, 011

---

## 1. 기능 개요

학습자가 노트를 저장·수정할 때 해당 노트를 벡터로 변환해 ChromaDB에 저장하고, AI 튜터 응답 생성 시 현재 노트와 관련된 과거 노트를 검색해 컨텍스트로 제공하는 기능이다.

**트리거 두 가지:**
- 노트 저장/수정 → 임베딩 갱신
- AI 튜터 응답 생성 요청 → 관련 노트 검색

---

## 2. 임베딩 저장 흐름

```
NoteService.saveNote() / updateNote()
    │
    ▼
NoteEmbeddingService.embed(StudyNote)
    ├── vectorStore.delete("note-{noteId}")      ← 기존 벡터 먼저 삭제 (버전 일관성)
    ├── NoteMetadataExtractor.extractLanguages() ← 코드 블록 언어 추출
    ├── NoteMetadataExtractor.extractHeaders()   ← 마크다운 헤더 추출
    └── vectorStore.add(Document)               ← 원본 content + 메타데이터 저장

NoteService.deleteNote()
    └── NoteEmbeddingService.delete(noteId)
            └── vectorStore.delete("note-{noteId}")
```

## 3. Q&A — 임베딩 설계 결정

### Q. 왜 노트 전체 본문을 임베딩하는가? 코드 블록을 따로 처리하지 않는 이유는?

**#57 측정 실험 결과에 근거한 결정이다.**

원래 `NotePreprocessor`로 코드 블록을 식별자 목록 형태(`[java: HashMap containsKey fibonacci ...]`)로 변환한 뒤 임베딩했다. 그러나 `text-embedding-3-small` 모델에서 실제 측정해보니 전처리 적용 시 Recall@4가 **100% → 40%로 60%p 하락**했다.

| 상태 | Recall@4 |
|---|---|
| 전처리 적용 (NotePreprocessor 호출) | 40% |
| 전처리 미적용 (원본 그대로) | **100%** |

**하락 원인:**

1. **허브 오염 현상**: DP/메모이제이션 노트(qnote-7)가 `HashMap`, `fibonacci` 같은 식별자를 포함하게 되어 10개 쿼리 중 6개의 top4에 잘못 등장. 식별자 목록으로 압축하면 여러 주제에서 공통으로 쓰이는 변수명이 노트 간 거짓 유사도를 만든다.

2. **문맥 소실**: `extractIdentifiers`는 코드를 단어 단위로 쪼개 순서 없이 나열한다. 함수 시그니처·자료 흐름 등 `text-embedding-3-small`이 활용하는 문맥 정보가 사라진다. 이 모델은 코드+자연어 혼합 문서를 원문 그대로 처리하도록 훈련되어 있어 원문 유지가 더 정확하다.

**현재:** `NotePreprocessor.java` 파일은 존재하지만 `NoteEmbeddingService`에서 호출하지 않는다.

---

### Q. 측정 테스트 노트가 모두 코드 블록을 포함한 것이었는데, 코드 없는 개념 노트에도 동일 결론이 적용되는가?

**적용된다고 단정할 수 없다.** 측정에 사용된 10개 노트는 모두 코드 블록이 포함된 CS 주제(HashMap, 이진탐색, BFS 등)였다. 코드 블록 없이 개념 설명만 있는 노트에 대한 검증은 이번 실험에 포함되지 않았다. 현재 결론은 코드 블록 포함 노트에 한정된 측정 결과다.

---

### Q. 출력 구조가 DRD 명세와 일치하는가?

`RagContext.RetrievedChunk`가 명세와 완전히 일치한다.

| DRD 명세 필드 | 실제 코드 필드 | 타입 |
|---|---|---|
| 관련 노트 컨텍스트 항목 목록 | `List<RetrievedChunk> chunks` | 객체 목록 |
| ↳ 제목 | `String title` | 문자열 |
| ↳ 세션 식별자 | `String sessionId` | 문자열 |
| ↳ 본문 내용 | `String content` | 문자열 |
| ↳ 관련도 점수 | `double score` | 실수 |

DRD 명세의 "본문 일부"라는 표현과 달리 실제로는 **노트 전체 본문**이 들어간다. 청킹(분할) 로직이 없기 때문이다.

---

### Q. "본문 내용"이 전체인가, 일부인가?

**전체 본문이 들어간다.** `NoteEmbeddingService.embed()`에서 `note.getContent()` 전체를 단일 Document로 저장하며, 검색 시 `doc.getText()`로 그 전체를 `content`에 넣는다.

## 4. Q&A — 검색 파이프라인

### Q. ChromaDB를 2회 호출하는 이유는?

Dense 검색(의미 기반)과 Sparse 검색(키워드 기반)을 각각 별도로 실행하기 때문이다.

| 호출 | 방식 | 목적 |
|---|---|---|
| 1회차 (Dense) | 벡터 유사도 검색 (threshold 0.55) | 의미적으로 유사한 노트 검색 |
| 2회차 (Sparse) | threshold 0.0으로 넓게 수집 후 키워드 포함 여부 필터 | 정확한 키워드가 포함된 노트 검색 |

**Dense는 "비슷한 느낌"을 찾고, Sparse는 "특정 단어"가 들어있는지를 본다.** 두 방식은 서로 보완 관계다.

두 결과를 **RRF(Reciprocal Rank Fusion)**로 병합한다.
- RRF 점수 공식: `score = Σ 1/(k + rank)`, k=60
- Dense와 Sparse 양쪽에 등장한 문서는 두 점수를 합산받아 자동으로 상위에 오른다
- 어느 한쪽에만 등장해도 결과에 포함되므로 두 방식 모두 커버한다

**#62 측정 결과:**

| 검색 방식 | 전체 평균 Recall@4 |
|---|---|
| Dense-only | 0.18 |
| 하이브리드 (Dense + Sparse + RRF) | **0.43** |

카테고리 A(기술 식별자 포함): +0.35 / 카테고리 B(한국어 CS 용어): +0.15 — 두 카테고리 모두 10%p 기준 초과.

특히 BFS↔DFS처럼 코사인 유사도가 0.26으로 낮은 대립 개념 쌍은 Dense만으로 서로를 찾지 못하지만, Sparse가 키워드로 연결한다.

### Q. REQ-AIV-003 — 현재 노트를 검색 결과에서 제외하는 이유는?

RAG 검색 쿼리가 현재 노트의 **원문 전체**이기 때문이다. 현재 노트를 제외하지 않으면 벡터 유사도가 사실상 1.0에 가까워 자기 자신이 항상 1위로 반환되고, 실제로 필요한 과거 관련 노트들이 밀려난다.

구현: `RagRetrievalService.retrieve()`의 필터 조건 `note_id != '...'`으로 제외.

---

### Q. REQ-AIV-002 — 다른 학습자의 노트가 검색되지 않음을 어떻게 보장하는가?

Dense·Sparse 두 검색 모두 `filterExpression: "user_id == '{userId}' && note_id != '{excludeNoteId}'"` 조건을 적용한다. ChromaDB 단계에서 필터링되므로 다른 사용자의 노트는 벡터 유사도 계산 자체가 수행되지 않는다.

---

### Q. REQ-AIV-004 — 관련도 임계값 미만 항목이 결과에서 제외되는가?

두 단계 필터로 처리된다.

1. **1차 필터 (Dense)**: `similarityThreshold=0.55` — ChromaDB 수준에서 유사도 0.55 미만 문서 제거
2. **2차 필터 (`isTopicRelevant`)**: RRF 병합 후 키워드 오버랩 10% 미만 문서 제거

Sparse 검색은 `threshold=0.0`으로 넓게 수집하므로 2차 필터가 더 중요한 역할을 한다.

## 5. Q&A — ChromaDB 설정

### Q. ChromaDB 컬렉션 설정값을 이렇게 선택한 이유는?

컬렉션명만 직접 지정했고, 나머지는 Spring AI / ChromaDB 기본값이다. `application.yml`의 `initialize-schema: true`로 앱 시작 시 자동 생성된다.

| 항목 | 값 | 선택 주체 |
|---|---|---|
| 컬렉션명 | `criticalflow-notes` | 직접 지정 |
| 유사도 공간 | cosine | Spring AI 기본값 |
| ef_construction / ef_search | 100 / 100 | ChromaDB 기본값 |
| max_neighbors | 16 | ChromaDB 기본값 |

**cosine 이유:** 벡터의 방향(의미)을 기준으로 비교해 노트 길이에 영향받지 않는다.

**HNSW 파라미터 조정 불필요 이유:** 수십만 건 이상에서 조정 효과가 나타난다. 현재 규모(수백 건)에서는 기본값으로 충분하고, #60·#62 측정 실험에서 검색 품질을 직접 확인했다.

---

### Q. ChromaDB 메타데이터에 해당 필드들을 넣은 이유는?

| 필드 | 현재 용도 | 향후 용도 |
|---|---|---|
| `note_id` | `note_id != excludeNoteId` 자기 참조 방지 필터 | — |
| `user_id` | `user_id == userId` 사용자 격리 필터 | — |
| `session_id` | RagContext 포맷 출력 시 출처 정보 | — |
| `title` | RagContext 포맷 출력 시 노트 제목 | — |
| `created_at` | 현재 미사용 | 시간 기반 필터 |
| `languages` | 현재 미사용 | 언어별 필터 (Java 노트만 등) |
| `headers` | 현재 미사용 | 주제 기반 필터 |

`created_at`, `languages`, `headers`는 노트를 재임베딩하지 않아도 나중에 필터를 추가할 수 있도록 사전 저장한 것이다.

---

### Q. question_type도 ChromaDB 메타데이터에 넣을 수 있는가?

기술적으로는 가능하지만 적합하지 않다.

`question_type`은 **대화 단위**로 결정된다. 노트 하나에 대화가 여러 개 생길 수 있고, 각 대화마다 다른 타입이 부여된다.

```
노트 1개 → 대화 A: TYPE_E
          → 대화 B: TYPE_A
          → 대화 C: TYPE_D
```

ChromaDB 메타데이터는 노트 단위로 저장되므로 어떤 대화의 타입을 기준으로 저장할지가 모호하다. `AiConversation.questionType` 컬럼(MySQL)에 대화별로 저장하는 현재 방식이 올바르다.

## 6. Q&A — RAG 설정값

### Q. bm25-max-results는 어떤 역할을 하는가?

Sparse 검색에서 후보를 몇 개까지 가져올지 정하는 값이다.

```
1단계: threshold=0.0으로 ChromaDB에서 상위 10건 수집  ← bm25-max-results=10
2단계: 수집된 10건 중 키워드가 실제로 포함된 것만 통과
```

`0`으로 설정하면 Sparse 검색을 건너뛰어 Dense-only 모드가 된다. #62 측정에서 비교 스위치로 사용했다.

---

### Q. Dense topK=6, Sparse topK=10으로 설정한 이유는?

**Dense topK=6:** `max-results + 2 = 4 + 2 = 6`. 최종 반환 수 4개에 2차 필터 탈락 여유분 2개를 더한 값. 측정으로 최적화한 값은 아니다.

**Sparse topK=10:** #60 측정 실험에서 상위 10건 기준으로 실험했고, 충분한 후보가 확보됐기 때문에 그대로 운영값으로 사용했다.

두 값 모두 엄밀하게 최적화된 것은 아니며, 노트 수가 크게 늘면 Recall@4 재측정을 통해 조정이 필요할 수 있다.

---

### Q. 노트 수가 많아지면 임계값 설정을 수정해야 하는가?

맞다. 두 설정이 데이터 증가에 따라 재검토 필요하다.

| 설정 | 재검토 이유 |
|---|---|
| `similarity-threshold: 0.55` | 노트 20개 기준 측정값. 노트 증가 시 벡터 공간 분포가 달라져 노이즈 문서 증가 가능 |
| `isTopicRelevant` 오버랩 10% | 노트 10개 환경 기준. 노트 증가 시 2차 필터가 더 많은 노이즈 처리 필요 |

**데이터 양과 무관한 설정:**

| 설정 | 이유 |
|---|---|
| `max-results: 4` | 프롬프트 길이 기준, 데이터 양 무관 |
| `bm25-max-results: 10` | 쿼리 특성에 의존 |
| HNSW 파라미터 | 수십만 건 이상에서 효과 발생 |

---

### Q. topK는 벡터 DB 크기에 따라 달라지는가?

간접적으로 영향을 받는다. topK 값 자체는 고정이지만, DB 크기에 따라 가져오는 결과의 품질이 달라진다.

| DB 규모 | 상황 |
|---|---|
| 노트 20개 (현재) | topK=6이면 전체의 30% → 관련 없는 노트도 상위권에 오를 가능성 |
| 노트 1000개 | topK=6이면 전체의 0.6% → 상위 6개의 유사도가 훨씬 의미 있음 |

노트 수가 크게 늘면 `similarity-threshold`와 `topK`를 함께 재검토해야 한다.

## 7. REQ-AIV-011 — 검색 품질 임계

**요구사항:** 관련 노트 검색 재현율은 정의된 테스트 데이터셋 기준 목표치 이상을 유지하여야 한다. 관련도 임계값 또는 검색 정책 변경 시 회귀 재현율 측정을 수행하여야 한다.

**현재 측정 결과:**

| 이슈 | 측정 내용 | 결과 |
|---|---|---|
| #57 | NotePreprocessor 전처리 전후 Recall@4 비교 | 전처리 미적용 100%, 적용 40% → 전처리 제거 |
| #60 | similarity-threshold 최적값 측정 | 0.75 → 0.55 변경 (0.75에서 Dense 평균 0건 반환) |
| #62 | Dense-only vs 하이브리드 Recall@4 비교 | Dense 0.18 → 하이브리드 0.43 |

목표치 수치는 `[TBD]`로 미확정이나, 측정 실험에서 하이브리드 검색의 효과를 정량적으로 확인했다.
