# 2.3 알고리즘 및 수식 명세

## 2.3.1 청킹 전략 비교 및 선택 근거

임베딩이란 텍스트의 의미를 수백 개의 숫자로 이루어진 벡터로 변환하는 과정으로, 의미가 비슷한 텍스트일수록 벡터가 서로 가깝게 위치한다. 노트를 임베딩할 때 텍스트를 어떤 단위로 처리하느냐에 따라 벡터의 품질과 검색 정확도가 달라진다.

초기 설계에는 코드 블록을 식별자 목록으로 변환하는 전처리 로직이 포함되어 있었다. 전처리가 임베딩 품질을 향상시킬 것이라는 가설 아래 도입됐으나, `text-embedding-3-small` 기반에서 실제 검색 정확도를 수치로 확인한 적이 없었다. 이 가설을 검증하여 전처리 유지 또는 제거를 결정하기로 했다.

| 방식 | 설명 | 기대 장점 | 위험 |
|---|---|---|---|
| 전체 청킹 | 노트 원문 전체를 하나의 단위로 임베딩 | 모델의 문맥 이해를 최대한 활용 | 노트가 길수록 임베딩 벡터에 정보가 희석될 가능성 |
| 설명·코드 분리 청킹 | 설명 텍스트와 코드 블록을 별도 단위로 분리 후 임베딩 | 코드와 설명을 독립적으로 검색 가능 | 임베딩 모델이 문맥 정보를 활용하지 못하고 식별자 단위로 처리 |

**전처리 수도코드**

```
PROCEDURE 전처리(마크다운):
    결과 ← 빈 문자열
    커서 ← 0

    FOR 각 코드블록 IN 코드블록찾기(마크다운):  // 정규식: ```언어\n코드```
        결과 ← 결과 + 마크다운[커서 ~ 코드블록.시작]  // 코드블록 앞 일반 텍스트 그대로 유지
        언어 ← 코드블록.언어태그  // java, python, sql 등 (없으면 "code")
        식별자목록 ← 식별자추출(코드블록.내용)
        결과 ← 결과 + "[" + 언어 + ": " + 식별자목록 + "] "  // 코드블록 → 식별자 요약으로 대체
        커서 ← 코드블록.끝

    결과 ← 결과 + 마크다운[커서 ~]  // 마지막 코드블록 이후 일반 텍스트 유지
    RETURN 결과

PROCEDURE 식별자추출(코드):
    // 분리 기준: 영문자·한글·언더스코어(_)가 아닌 모든 문자 ([^a-zA-Z가-힣_]+)
    // → 구문 기호({, }, ;, (, ) 등)뿐 아니라 숫자(0-9)도 구분자로 처리됨
    // → 예: arr1 → "arr", "1" / HashMap<String → "HashMap", "String"
    토큰목록 ← 코드를 [영문자·한글·언더스코어가 아닌 문자] 기준으로 분리
    결과 ← 빈 집합 (중복 제거)

    FOR 각 토큰 IN 토큰목록:
        IF 토큰.길이 > 2:  // 3자 이상만 유지 — 1~2자 토큰(if, do, 단일 문자 등) 제거
                           // int(3자), for(3자) 등은 제거되지 않고 결과에 포함됨
            결과.추가(토큰)

    RETURN 결과를 공백으로 연결한 문자열
```

예시 변환:

```
// 입력
HashMap<String, Integer> scores = new HashMap<>();
scores.put("Alice", 95);
scores.containsKey("Dave");

// 출력
[java: HashMap String Integer scores containsKey Alice Dave]
```

**검증 (전처리 임베딩 품질 측정)**

#### 필요성

**전처리를 도입한 이유**

`NotePreprocessor.preprocessForEmbedding()`은 코드 블록을 `[java: HashMap containsKey fibonacci ...]` 형태의 식별자 텍스트로 변환하는 로직이다. 도입 당시의 설계 의도는 두 가지였다.

첫째, **구문 기호 노이즈 제거**다. 코드 블록에는 `{`, `}`, `;`, `(`, `)` 같은 구문 기호가 대량으로 포함된다. 이 기호들은 자연어 처리 관점에서 의미 없는 토큰이므로 임베딩 벡터가 의미보다 구문 패턴으로 분산될 수 있다고 판단했다. 구문 기호를 제거하면 모델이 실제 의미 있는 식별자에 집중할 것이라고 가정했다.

둘째, **식별자 중심 의미 압축**이다. 코드에서 실질적 의미를 담은 부분은 함수명·변수명·클래스명 같은 식별자다. `extractIdentifiers()`는 공백·기호로 분리한 뒤 3자 이상 토큰만 추출하여 코드를 "의미 있는 식별자 목록"으로 압축한다. 이 방식은 Word2Vec처럼 단어를 평균하거나 단순 연결해 벡터를 만들던 시대에는 유효한 접근이었다.

하지만 전처리가 실제로 유사도 검색 품질을 높이는지 `text-embedding-3-small` 기반에서 수치로 확인한 적이 없었다. 전처리가 오히려 유의미한 정보를 제거할 경우 코드 관련 노트의 검색 정밀도가 저하될 수 있다는 리스크가 있어 검증이 필요했다.

**가설**: "코드 블록의 구문 기호가 벡터를 희석시키므로, 전처리를 적용하면 Recall@4가 향상될 것이다."

#### 특징

Recall@4란 관련 노트 검색 결과 상위 4건 안에 정답 노트가 몇 개 포함됐는지를 나타내는 검색 정확도 지표로, 값이 높을수록 관련 노트를 더 잘 찾아낸다는 의미다. 전처리 적용 상태와 미적용 상태에서 동일한 쿼리를 실행하여 Recall@4를 직접 비교하는 수동 실험으로 진행했다.

#### 설정 과정

코드 블록이 포함된 CS 주제 노트 10개(qnote-1~10)와 각 노트에 1:1 대응하는 정답 쿼리 10개를 사용했다. 임베딩 모델은 text-embedding-3-small, 벡터 DB는 ChromaDB 1.0.0(Testcontainers)을 사용했으며, 평가 지표는 Recall@4(topK=4, similarityThreshold=0.0)로 설정했다.

| 항목 | 값 |
|---|---|
| 노트 수 | 10개 (qnote-1~10, 코드 블록 포함 CS 주제) |
| 쿼리 수 | 10개 (노트별 1:1 대응 정답 쿼리) |
| 임베딩 모델 | text-embedding-3-small |
| 벡터 DB | ChromaDB 1.0.0 (Testcontainers) |
| 평가 지표 | Recall@4 (topK=4, similarityThreshold=0.0) |

| 노트 ID | 주제 | 쿼리 (정답 검색어) |
|---|---|---|
| qnote-1 | HashMap 자료구조 | "HashMap put get containsKey 사용법" |
| qnote-2 | 재귀 함수 팩토리얼 | "재귀 호출 팩토리얼 기저 조건 구현" |
| qnote-3 | 이진 탐색 알고리즘 | "정렬된 배열 이진 탐색 left right mid 구현" |
| qnote-4 | SQL JOIN 쿼리 | "SQL INNER JOIN LEFT JOIN 테이블 조인 쿼리" |
| qnote-5 | 버블 정렬 알고리즘 | "버블 정렬 swap 인접 비교 알고리즘 구현" |
| qnote-6 | 스프링 의존성 주입 | "스프링 Autowired 빈 의존성 주입 Service Repository" |
| qnote-7 | 동적 프로그래밍 메모이제이션 | "메모이제이션 dp 피보나치 동적 프로그래밍 최적화" |
| qnote-8 | BFS 그래프 탐색 | "BFS 너비 우선 탐색 큐 Queue LinkedList 구현" |

| qnote-10 | 자바 예외 처리 | "자바 예외 처리 try catch finally IOException RuntimeException" |

**정답(HIT) 기준 및 쿼리 설계 근거**

정답은 "해당 쿼리로 검색했을 때 정답 노트가 Top-4 안에 포함되는 것"으로 정의했다. 이를 자기 검색(self-retrieval) 기반 정답이라고 한다. 학습자가 특정 개념을 복습하려 할 때 해당 개념의 핵심 키워드로 검색하면 그 노트가 반드시 상위 결과에 나타나야 한다는 전제를 기반으로 한다. 정답 노트가 Top-4에 없으면 실제 서비스에서 AI 튜터가 해당 노트를 맥락으로 활용하지 못하므로, Top-4 포함 여부가 시스템이 요구하는 최소 품질 기준과 직결된다.

정답은 개발자가 직접 정의한다. 테스트 코드에서 각 노트와 쿼리를 수동으로 쌍을 묶어 "이 쿼리를 입력했을 때 이 노트가 정답이다"를 사전에 레이블링한다. 정보 검색 분야에서는 이를 관련성 판단(Relevance Judgment)이라고 한다.

쿼리는 두 가지 원칙으로 설계했다. 첫째, 자연어 설명과 코드 식별자를 혼합하여 구성했다. "HashMap put get containsKey 사용법"처럼 학습자가 실제 복습 시 입력할 법한 표현을 반영했다. 둘째, 노트 제목이나 도입부 문장을 그대로 쓰지 않고 핵심 개념어 위주로 재구성했다. 쿼리가 노트 내용과 완전히 동일하면 임베딩 모델이 아닌 단순 텍스트 매칭으로도 HIT가 가능해 품질 측정의 의미가 사라지기 때문이다.

이 방식의 한계는 개발자가 정의한 쿼리가 실제 학습자의 검색 패턴과 다를 수 있다는 점이다. 예를 들어 qnote-1(HashMap)의 정답 쿼리를 "HashMap put get containsKey 사용법"으로 정의했지만, 실제 학습자는 "자바 해시맵 어떻게 써요?"처럼 다른 표현을 쓸 수 있다. 현재 테스트는 개발자 관점의 대표 쿼리 기준이므로, Recall@4 100%는 이 특정 쿼리 집합에서의 결과이며 실제 사용자 쿼리의 다양성을 보장하지는 않는다.

#### 시행착오

전처리 적용 시 Recall@4가 40%(4/10)로 하락했다. **가설 기각**. 10개 쿼리 중 6개에서 정답 노트가 Top-4에 포함되지 못했다.

| 쿼리 노트 | 결과 | Top-4 반환 |
|---|---|---|
| qnote-1 (HashMap) | miss | qnote-7, qnote-4, qnote-10, qnote-2 |
| qnote-2 (재귀) | miss | qnote-7, qnote-10, qnote-4, qnote-5 |
| qnote-3 (이진탐색) | miss | qnote-4, qnote-7, qnote-9, qnote-6 |
| qnote-4 (SQL) | **HIT** | qnote-4, qnote-7, qnote-9, qnote-2 |
| qnote-5 (버블정렬) | miss | qnote-7, qnote-9, qnote-4, qnote-10 |
| qnote-6 (스프링 DI) | miss | qnote-10, qnote-4, qnote-7, qnote-3 |
| qnote-7 (DP) | **HIT** | qnote-7, qnote-9, qnote-10, qnote-4 |
| qnote-8 (BFS) | miss | qnote-9, qnote-7, qnote-10, qnote-2 |
| qnote-9 (스택) | **HIT** | qnote-9, qnote-7, qnote-4, qnote-6 |
| qnote-10 (예외처리) | **HIT** | qnote-10, qnote-9, qnote-7, qnote-8 |

하락 원인은 두 가지다. 두 원인은 독립적이지 않고 서로를 증폭시키는 구조다.

첫째, **허브 오염 현상**이 발생했다. 허브 오염 현상이란 특정 단어가 너무 많은 문서에 공통으로 포함될 때 서로 주제가 다른 문서 사이의 유사도가 비정상적으로 높게 측정되는 문제를 말한다. 전처리 후 qnote-7(DP/메모이제이션)의 임베딩 대상 텍스트는 다음과 같이 변환됐다.

```
[java: HashMap memo containsKey fibonacci climbStairs result DynamicProgramming]
```

이 식별자들이 여러 노트와 교차했다. `HashMap`, `containsKey`는 qnote-1(HashMap)과, `fibonacci`는 qnote-2(재귀)와, `result`, `climbStairs`는 다수 노트와 겹쳤다. 결과적으로 qnote-7은 자기 자신을 제외한 9개 쿼리 모두의 Top-4에 등장했다. 이 중 6개(qnote-1, 2, 3, 5, 6, 8)는 qnote-7이 정답 노트를 Top-4 밖으로 밀어내어 miss를 유발했고, 나머지 3개(qnote-4, 9, 10)는 해당 쿼리의 정답이 qnote-7과 함께 Top-4 안에 공존하여 HIT로 집계됐다.

qnote-7이 허브가 된 이유는 DP 메모이제이션이라는 주제 자체가 여러 CS 개념의 교차점에 위치하기 때문이다. DP 메모이제이션의 대표 구현은 HashMap을 메모 테이블로 쓰고(`HashMap`, `containsKey`), 피보나치를 예제로 사용하며(`fibonacci`), 최적화 문제를 다룬다(`climbStairs`, `result`). 전처리 없이 원문을 읽으면 모델은 이 식별자들이 "DP라는 주제의 맥락 안에 있는 도구"임을 이해한다. 그러나 전처리로 식별자 목록만 남기면 모델은 "이 노트가 HashMap에 관한 것인지, 재귀에 관한 것인지, DP에 관한 것인지" 구분할 근거가 없다. qnote-7의 광범위한 식별자 집합이 오히려 모든 노트와 높은 유사도를 만들어내는 원인이 됐다.

둘째, **문맥 소실**이 발생했다. 임베딩 모델은 단어 하나가 어떤 맥락에서, 어떤 흐름으로 사용됐는지를 함께 학습한다. "HashMap을 메모 테이블로 초기화하고 피보나치 값을 저장한다"는 코드와 "HashMap에 학생 점수를 저장한다"는 코드는 둘 다 HashMap을 쓰지만 완전히 다른 맥락이다. 전처리 없이 원문을 읽으면 모델은 함수 이름, 매개변수 순서, 반환값의 흐름, 코드 전후 설명 텍스트를 종합하여 이 차이를 구분한다. 전처리로 `HashMap memo containsKey fibonacci`만 남기면 이 맥락 정보가 전부 사라지고 단어의 나열만 남는다.

공통 변수명 문제가 이를 더 악화시켰다. `result`는 거의 모든 알고리즘 구현에 등장하는 반환값 변수이고, `arr`은 배열 기반 알고리즘 어디에나 나오며, `temp`는 정렬 알고리즘의 swap 로직에 공통으로 쓰인다. 원문에서는 이 변수들이 어떤 자료구조 안에서, 어떤 로직의 일부로 쓰이는지가 명확하다. 전처리 후에는 주제가 전혀 다른 노트들이 `result`, `arr`, `temp`를 공유한다는 이유로 높은 유사도를 갖게 된다.

두 원인이 맞물리는 방식을 정리하면 다음과 같다. 문맥 소실이 먼저 발생하여 각 노트의 정체성이 흐려지고, 그 결과 qnote-7처럼 다양한 식별자를 가진 노트가 전방위적으로 유사도 상위에 올라가는 허브 오염 현상이 일어난다. 전처리를 적용하지 않으면 모델이 각 노트의 전체 맥락을 이해하므로 두 현상 모두 발생하지 않는다.

#### 테스트 결과

전처리를 제거하고 원본 마크다운을 그대로 임베딩한 결과 Recall@4가 100%(10/10)로 향상됐다.

| 쿼리 노트 | 결과 | Top-4 반환 |
|---|---|---|

각 노트별로 함께 등장한 노트들의 연결 이유는 아래와 같다.

**qnote-1 (HashMap) → 이진탐색, 스프링DI, BFS**
HashMap과 이진탐색은 둘 다 "무언가를 빠르게 찾는" 탐색 개념으로, HashMap은 O(1) 조회, 이진탐색은 O(log n) 조회를 다룬다. HashMap과 BFS는 BFS 구현 시 방문 여부를 HashSet이나 HashMap으로 관리하므로 코드 수준에서 직접 함께 쓰인다. HashMap과 스프링DI는 둘 다 Java 코드 기반이며, 스프링 컨테이너가 Bean을 내부적으로 Map 구조로 관리하는 패턴에서 연결된다.

**qnote-2 (재귀) → DP, 예외처리, 스프링DI**
재귀와 DP는 피보나치 예제를 직접 공유한다. "재귀로 구현하면 중복 계산이 발생하고, 이를 메모이제이션으로 최적화한 것이 DP"라는 학습 흐름이 임베딩 공간에 반영됐다. 재귀와 예외처리는 기저 조건이 없는 재귀가 StackOverflowError를 발생시킨다는 맥락으로 연결된다.

**qnote-3 (이진탐색) → 버블정렬, BFS, SQL**
이진탐색은 정렬된 배열을 전제로 동작하므로 버블정렬과 탐색·정렬 알고리즘 계열로 묶인다. 이진탐색과 BFS는 둘 다 탐색 알고리즘이라는 공통 맥락을 가진다. 이진탐색과 SQL은 DB 인덱스가 B-Tree 구조로 동작하며 이진탐색 원리를 사용한다는 점에서 연결된다.

**qnote-5 (버블정렬) → 이진탐색, DP, 스택**
버블정렬과 이진탐색은 정렬+탐색 알고리즘 계열로 항상 함께 다뤄진다. 버블정렬과 DP는 시간복잡도 최적화를 다루는 알고리즘이라는 공통 맥락을 가진다. 버블정렬의 O(n²)을 개선하는 방향과 DP의 메모이제이션으로 중복 계산을 줄이는 것은 알고리즘 학습 교재에서 같은 챕터에 등장하는 개념들이다. 버블정렬과 스택은 반복문 기반으로 원소를 순차 처리하는 구현 패턴을 공유한다.

**qnote-7 (DP) → 재귀, 버블정렬, 이진탐색**
DP와 재귀는 피보나치 예제를 공유한다. DP와 버블정렬·이진탐색은 세 개념 모두 시간복잡도 최적화를 다루는 알고리즘이다. 버블정렬의 O(n²), 이진탐색의 O(log n), DP의 메모이제이션은 알고리즘 학습 교재에서 같은 챕터에 함께 등장하는 개념들이다.

**qnote-8 (BFS) → 이진탐색, 스택, 버블정렬**
BFS와 스택은 BFS가 Queue로, DFS가 Stack으로 구현되는 그래프 탐색의 쌍 개념이다. 두 자료구조를 함께 배우는 맥락이 임베딩에 반영됐다. BFS와 이진탐색은 둘 다 탐색 알고리즘 계열로 묶인다.

**qnote-9 (스택) → DP, 이진탐색, BFS**
스택과 BFS는 위와 동일하게 그래프 탐색의 쌍 개념으로 연결된다. 스택과 DP는 괄호 매칭 같은 문제에서 스택이 DP와 함께 활용되는 구현 패턴을 공유한다.

#### 학습 결과 분석

**핵심 발견 1**: 가설 기각. 전처리는 임베딩 품질을 향상시키지 않고 오히려 -60%p 저하시켰다. 초기 가설("코드 블록의 구문 기호가 벡터를 희석시킨다")은 Word2Vec 시대의 단순 평균 임베딩에서는 유효했던 개념이지만, 문맥 전체를 바라보는 `text-embedding-3-small`에서는 코드 원문 유지가 오히려 더 정확한 표현을 만든다.

**핵심 발견 2**: 전처리 제거 후 함께 등장한 연관 노트들이 실제 학습 맥락에서 의미 있는 조합이다. 재귀↔DP(피보나치 공유), BFS↔스택(그래프 탐색 쌍), 이진탐색↔버블정렬(정렬·탐색 알고리즘 계열) 등 임베딩 모델이 노트의 실제 주제 관계를 올바르게 포착했다. TYPE_C(과거 학습 연계) 질문 생성 시 RAG로 주입되는 노트들이 학습적으로 의미 있음을 확인했다.

**한계**: 본 측정은 코드 블록이 포함된 CS 주제 노트 10개만 대상으로 했다. 코드 없는 순수 개념 노트에서의 청킹 방식 영향은 검증되지 않았으며 향후 측정이 필요하다. 또한 노트 규모가 커지면 정보 희석 우려가 현실화될 수 있으므로, `text-embedding-3-small`의 최대 입력 컨텍스트(8,191 토큰) 대비 노트 길이 분포를 주기적으로 모니터링해야 한다.

## 2.3.2 하이브리드 검색 알고리즘 (Dense + Sparse + RRF)

2.3.1에서 전체 청킹 방식을 확정했다. 다음 과제는 임베딩된 노트를 어떻게 검색할 것인가다. 초기 구현은 Dense 검색(벡터 유사도 기반)만 사용했으나, 코드 식별자와 짧은 한국어 CS 용어에서 구조적 누락이 발생할 것으로 예상됐다. 이 한계를 측정으로 확인하고, Sparse 검색을 추가하여 하이브리드 방식으로 고도화하는 과정을 서술한다.

**ChromaDB 인덱스 설정**

ChromaDB는 HNSW 인덱스를 사용하여 벡터 유사도 검색을 수행한다. HNSW(Hierarchical Navigable Small World)란 벡터들을 계층적 그래프 구조로 연결하여 유사한 벡터를 빠르게 탐색하는 알고리즘이다. 모든 벡터를 하나씩 비교하는 방식과 달리 그래프를 따라 이동하며 가까운 벡터를 찾으므로, 노트 수가 증가해도 검색 속도가 크게 느려지지 않는다. 거리 측정 기준으로는 코사인 유사도를 사용한다. 코사인 유사도는 두 벡터가 얼마나 같은 방향을 가리키는지를 0~1 사이 수치로 나타내며, 벡터의 크기가 아닌 방향을 기준으로 유사도를 계산하므로 노트 길이 차이에 영향받지 않는다.

**Dense 검색과 Sparse 검색의 역할**

Dense 검색은 두 벡터가 얼마나 같은 방향을 가리키는지를 0~1 사이 수치로 나타낸 코사인 유사도를 기반으로 의미적으로 유사한 노트를 검색한다. 값이 1에 가까울수록 두 노트의 의미가 유사하다는 뜻이다. 유사도가 0.55 미만인 문서는 관련성이 낮다고 판단하여 사전에 제거한다. 단, BFS↔DFS처럼 대립 개념 쌍은 코사인 유사도가 0.26으로 낮아 Dense 검색만으로는 상호 검색이 불가능하다. BFS와 DFS는 둘 다 그래프 탐색 알고리즘이지만 임베딩 모델은 단어가 어떤 맥락으로 함께 등장하는지를 학습하기 때문에 두 개념의 벡터가 서로 다른 방향을 가리키게 된다. BFS는 "최단 경로", "너비 우선", "큐(Queue)" 같은 단어와 함께 쓰이고, DFS는 "백트래킹", "깊이 우선", "스택(Stack)" 같은 단어와 함께 쓰인다. 사람 입장에서는 둘 다 그래프 탐색이라 관련 있어 보이지만, 임베딩 모델은 사용 맥락을 기준으로 벡터를 결정하므로 BFS 노트를 검색할 때 DFS 노트가 유사도 임계값 0.55에 미치지 못해 검색되지 않는다.

Sparse 검색은 키워드 기반 텍스트 매칭으로 정확한 어휘 일치를 확인한다. Dense가 의미 공간에서 찾지 못한 키워드 기반 관련 노트를 보완하는 역할을 한다.

**주요 설정값**

| 항목 | 값 | 근거 |
|---|---|---|
| Dense 유사도 임계값 | 0.55 | 임계값 최적화 측정 결과 (시행착오 1 참조) |
| Dense topK | 6 | 최종 반환 수 4건 + 2차 필터 탈락 여유분 2건 |
| Sparse 임계값 | 0.0 | 유사도 필터 없이 최대 후보 수집 (API 제약) |
| Sparse topK | 10 | 임계값 최적화 측정 실험값 그대로 운영 적용 |
| RRF k | 60 | Cormack et al.(2009) 논문 기본값 |
| 최종 반환 수 | 4건 | System Prompt 컨텍스트 길이 제한 고려 |

Sparse 검색의 임계값을 0.0으로 설정한 이유는 두 가지다. 첫째, 도구의 한계 때문이다. 원래는 특정 단어가 포함된 노트를 직접 찾고 싶었지만, 사용하는 라이브러리(Spring AI VectorStore)가 키워드 검색 기능을 별도로 제공하지 않는다. 임계값 0.0은 "아무것도 걸러내지 말고 전부 가져와라"는 의미로, 이후 키워드 포함 여부를 직접 걸러내는 방식으로 대체했다. 둘째, Dense 검색이 놓친 노트를 잡아내기 위함이다. Dense에도 같은 기준을 쓰면 두 검색이 동일한 노트만 반환하여 Sparse를 쓰는 의미가 없어진다.

최종 반환 수 4건은 AI 튜터가 답변을 만들 때 입력으로 받는 프롬프트 길이를 고려한 값이다. 과거 노트를 너무 많이 넣으면 AI가 핵심을 놓치고 답변 품질이 떨어질 수 있어 4건으로 제한했다.

**RRF 수식**

RRF(Reciprocal Rank Fusion)란 여러 검색 결과 목록의 순위를 점수로 변환하여 합산하고 하나의 통합 목록을 만드는 방식이다.

```
score(문서) = Σ [ 1 / (k + rank(문서, 결과목록)) ],  k = 60
```

k=60은 Cormack et al.(2009) RRF 논문의 기본값이다. k는 순위 간 점수 차이를 조절하는 완충값으로, 너무 작으면 1위와 2위 간 점수 차이가 커져 순위 역전이 어려워지고, 너무 크면 순위 차이가 무의미해진다. 소규모 환경(후보 6~10개)에서 k=60의 동작을 최악의 케이스로 검증했다.

```
양쪽 등장 문서(Dense 6위 + Sparse 6위) 점수:
    2 / (60 + 6) = 0.030

Dense 단독 1위 문서 점수:
    1 / (60 + 1) = 0.016

0.030 > 0.016  →  양쪽 목록에 등장한 문서가 단독 최상위 문서보다 항상 높은 점수를 가짐
```

**검색 파이프라인**

Sparse 검색의 키워드 필터는 키워드가 하나도 포함되지 않는 문서를 1차로 제거하는 관문 역할이며, 이후 2.3.3의 2차 필터가 오버랩 비율 기준으로 정밀하게 노이즈를 제거한다.

```
PROCEDURE 하이브리드검색(쿼리, 사용자ID, 제외노트ID):

    // 1단계: Dense 검색
    Dense후보 ← 벡터DB.유사도검색(
        쿼리,
        임계값=0.55,
        최대개수=6,
        필터=사용자ID 일치 AND 제외노트ID 불일치
    )

    // 2단계: Sparse 검색
    Sparse후보 ← 벡터DB.키워드검색(
        쿼리,
        임계값=0.0,
        최대개수=10,
        필터=사용자ID 일치 AND 제외노트ID 불일치
    )
    Sparse후보 ← Sparse후보 중 키워드를 하나라도 포함하는 문서만 유지

    // 3단계: RRF 병합
    병합결과 ← RRF병합(Dense후보, Sparse후보, k=60)

    // 4단계: 2차 필터
    최종결과 ← 주제관련성필터(병합결과, 오버랩임계값=0.1)

    RETURN 최종결과 상위 4건
```

**RAG 기반 할루시네이션 방지 전략**

할루시네이션이란 AI가 근거 없이 그럴듯한 내용을 만들어내는 현상을 말하는데, LLM 응답이 학습자 본인의 노트 내용에 근거하도록 RAG 검색 결과를 프롬프트에 주입하는 구조로 이를 구조적으로 차단한다.

과거 노트임을 명시하는 레이블을 포함하여 주입하는 이유는 초기 구현 경험에서 도출됐다. 레이블 없이 주입 시 LLM이 과거 노트를 현재 노트의 일부로 오해하여 직접 정답을 제공하는 현상이 발생했다. 레이블을 통해 과거 노트의 역할을 명시함으로써 System Prompt의 RAG 노이즈 거부 규칙과 함께 동작하도록 설계한다.

RAG 결과가 없는 경우 LLM은 현재 노트만을 근거로 응답을 생성하며, TYPE_C 질문은 TYPE_A로 폴백하여 맥락 없는 과거 학습 연계 질문 생성을 방지한다.

**검증 (임계값 최적화 → 하이브리드 Recall@4 측정)**

#### 필요성

Dense 단독 검색이 코드 식별자와 짧은 한국어 CS 용어 노트에서 관련 노트를 찾지 못하는 한계가 예상됐다. 두 가지 가설을 검증했다.

- **가설 1**: "Dense 유사도 임계값 0.75는 CS 노트 특성상 너무 높다"
- **가설 2**: "하이브리드(Dense + Sparse + RRF)가 Dense 단독보다 높은 Recall@4를 달성한다"

#### 특징

임계값 최적화(시행착오 1)는 서버 로그로 Dense 반환 건수를 관찰했고, 하이브리드 효과 측정은 `bm25-max-results=0` 설정으로 Dense-only 모드와 하이브리드 모드를 직접 비교했다.

쿼리 노트를 두 카테고리로 구분한 이유는 Dense의 두 가지 구조적 한계를 각각 검증하기 위함이다. 카테고리 A는 코드 식별자가 임베딩 공간에서 의미 거리를 제대로 표현하지 못하는 케이스, 카테고리 B는 짧은 한국어 CS 용어가 유사도 임계값을 넘지 못하는 케이스를 대상으로 했다.

## 2.3.3 2차 필터 키워드 오버랩 알고리즘

2.3.2의 하이브리드 검색으로 후보 범위가 넓어졌다. 넓어진 만큼 RRF 병합 결과에 주제와 무관한 문서가 포함될 가능성도 높아진다. 2차 필터는 최종 단계에서 현재 노트와 후보 문서 간 키워드 오버랩 비율이 10% 미만인 문서를 제거한다.

초기 가설은 "현재 파라미터(임계값 0.2, 키워드 1자 이상)가 설계 기준(평균 제거율 30% 이하)을 충족할 것이다"였다.

**알고리즘 동작 방식**

현재 노트와 후보 문서 각각에서 의미 있는 키워드를 추출한다. 키워드 추출 조건은 한국어 2자 이상, 영어 4자 이상이며, 최대 20개 상한을 적용한다. 두 집합의 교집합 크기를 현재 노트의 키워드 수로 나누어 오버랩 비율을 계산하고, 10% 미만이면 해당 문서를 제거한다.

한국어 1자 단어는 조사·접속사('의', '을', '과' 등)가 대부분이어서 주제 관련성 판단에 의미가 없다. 2자 이상으로 제한하면 실질적인 개념어만 추출된다. 영어 3자 이하 단어는 관사·전치사('the', 'for', 'and' 등) 및 약어가 많아 노이즈가 된다. 4자 이상으로 제한하면 실질적인 기술 용어만 추출된다.

```
PROCEDURE 주제관련성필터(후보목록, 오버랩임계값):
    결과 ← 빈 목록

    FOR 각 문서 IN 후보목록:
        쿼리키워드 ← 키워드추출(현재노트, 한국어최소=2자, 영어최소=4자, 최대=20개)
        문서키워드 ← 키워드추출(문서, 한국어최소=2자, 영어최소=4자, 최대=20개)

        IF 쿼리키워드 크기 == 0:
            결과.추가(문서)  // 키워드 추출 불가 시 분모가 0이 되는 예외 방지: 무조건 통과
            CONTINUE

        오버랩수 ← 쿼리키워드 AND 문서키워드 의 교집합 크기
        오버랩비율 ← 오버랩수 / 쿼리키워드 크기

        IF 오버랩비율 >= 오버랩임계값:
            결과.추가(문서)

    RETURN 결과
```

**검증 (2차 필터 수동 측정)**

#### 필요성

2차 필터는 "코사인 유사도는 높지만 실제 주제가 다른 문서"를 걸러내기 위해 설계됐으나, 실제 제거율을 측정한 적이 없었다. 임계값이 너무 높으면 유효한 과거 노트가 걸러져 TYPE_C 질문 생성 기회가 줄어들고, 너무 낮으면 노이즈가 프롬프트에 주입되어 AI 응답 품질이 저하될 수 있었다.

#### 특징

`retrieve()` 내부에 RRF 병합 후 건수와 2차 필터 후 건수를 기록하는 임시 로그를 추가하고, 대화 시작 API 10회 호출 후 로그를 수집하여 제거율을 계산했다.

#### 설정 과정

| 항목 | 값 |
|---|---|
| 대상 노트 | 한국어 CS 노트 20개 |
| 쿼리 노트 | 10개 (noteId=1~10) |
| 측정 지표 | 2차 필터 평균 제거율 |
| 합격 기준 | 평균 제거율 ≤ 30% |

#### 시행착오

1차 측정에서 평균 제거율이 90.0%로 설계 기준 30%를 크게 초과했다. **가설 기각**. 문제는 파라미터가 잘못된 것이 아니라 설계 전제 자체가 잘못됐다. 2차 필터는 짧은 쿼리(몇 개 키워드)를 가정하고 설계됐으나, 실제로는 노트 전문(약 150단어)이 쿼리로 들어오는 상황이었다.

| noteId | 노트 | RRF 후 | 2차 필터 후 | 제거율 |
|---|---|---|---|---|
| 1 | HashMap | 4건 | 0건 | 100.0% |
| 2 | 스택 | 4건 | 1건 | 75.0% |
| 3 | 큐 | 4건 | 1건 | 75.0% |

#### 학습 결과 분석

**핵심 발견 1**: 90% 제거율은 파라미터 오류가 아닌 설계 전제 불일치였다. "짧은 쿼리"를 가정한 필터에 "노트 전문"이 들어온 구조적 원인이다. 파라미터 수정 후 -45%p 개선됐으나 합격 기준(30%)은 여전히 미달이다.

**핵심 발견 2**: 제거율 편차가 노트마다 0%~100%까지 크다. 퀵정렬(noteId=7)은 정렬·알고리즘 계열 노트와 키워드가 많이 겹쳐 전부 통과(0% 제거)한 반면, 힙(noteId=10)은 전문 용어("최대힙", "최소힙", "heapify")가 다른 노트에 거의 없어 전부 탈락(100% 제거)했다. 제거율이 낮을수록 관련 과거 노트가 많은 주제, 높을수록 관련 노트가 적은 주제임을 나타낸다.

**핵심 발견 3**: 부가 발견으로, 1차 측정에서 TYPE_F로 분류됐던 퀵정렬 노트가 파라미터 수정 후 RAG 컨텍스트가 살아나면서 TYPE_B(설계 의도 탐침)로 분류됐다. 2차 필터 파라미터 변경이 질문 유형 라우팅에도 간접적으로 영향을 미칠 수 있음을 보여준다.

**한계**: 현재 설정에서도 평균 제거율 45%는 기준(30%)을 초과한다. 노트 수 20개라는 소규모 환경이 원인으로, 노트 수가 50개 이상이 되면 관련 개념을 다루는 노트가 더 많아져 제거율이 자연히 낮아질 것으로 예상한다. 향후 노트 50개 수준에서 재측정이 필요하다.
