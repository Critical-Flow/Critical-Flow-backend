## 2.3.1 청킹 전략 비교 및 선택 근거

임베딩이란 텍스트의 의미를 수백 개의 숫자로 이루어진 벡터로 변환하는 과정으로, 의미가 비슷한 텍스트일수록 벡터가 서로 가깝게 위치한다. 노트를 임베딩할 때 텍스트를 어떤 단위로 처리하느냐에 따라 벡터의 품질과 검색 정확도가 달라진다. 두 가지 방식을 검토한 결과 전체 청킹 방식을 채택했다. 전체 청킹은 노트 원문 전체를 하나의 단위로 임베딩하는 방식으로, 임베딩 모델이 코드와 자연어 혼합 문서를 원문 그대로 처리하도록 훈련된 특성을 최대한 활용한다.

**청킹 방식 비교**

| 방식 | 설명 | 장점 | 단점 |
|---|---|---|---|
| 전체 청킹 | 노트 전체를 하나의 단위로 임베딩 | 모델의 문맥 이해를 최대한 활용 | 노트가 길수록 임베딩 벡터에 정보가 희석될 가능성 |
| 설명·코드 분리 청킹 | 설명 텍스트와 코드 블록을 별도 단위로 분리 후 임베딩 | 코드와 설명을 독립적으로 검색 가능 | 임베딩 모델이 문맥 정보를 활용하지 못하고 식별자 단위로 처리 |

**검증 (전처리 임베딩 품질 측정)**

#### 필요성

`NoteEmbeddingService.embed()` 내부에서 코드 블록을 `[python: fibonacci return ...]` 형태의 식별자 텍스트로 변환한 뒤 ChromaDB에 임베딩하는 전처리 로직이 있었다. 이 로직은 코드 블록의 구문 기호(`{`, `;`, `}`)가 임베딩 벡터를 희석시킨다는 가설을 기반으로 설계됐지만, 전처리가 실제로 유사도 검색 품질을 높이는지 수치로 확인한 적이 없었다. 미검증 상태에서 전처리가 오히려 유의미한 정보를 제거할 경우 코드 관련 노트의 검색 정밀도가 저하될 수 있다는 리스크가 있었다.

#### 특징

Recall@4란 관련 노트 검색 결과 상위 4건 안에 정답 노트가 몇 개 포함됐는지를 나타내는 검색 정확도 지표로, 값이 높을수록 관련 노트를 더 잘 찾아낸다는 의미다. 전처리 적용 상태와 미적용 상태에서 동일한 쿼리를 실행하여 Recall@4를 직접 비교하는 수동 실험으로 진행했다.

#### 설정 과정

코드 블록이 포함된 CS 주제 노트 10개(qnote-1~10)와 각 노트에 1:1 대응하는 정답 쿼리 10개를 사용했다. 임베딩 모델은 text-embedding-3-small, 벡터 DB는 ChromaDB 1.0.0(Testcontainers)을 사용했으며, 평가 지표는 Recall@4(topK=4, similarityThreshold=0.0)로 설정했다.

| 노트 ID | 주제 |
|---|---|
| qnote-1 | HashMap 자료구조 |
| qnote-2 | 재귀 함수 팩토리얼 |
| qnote-3 | 이진 탐색 알고리즘 |
| qnote-4 | SQL JOIN 쿼리 |
| qnote-5 | 버블 정렬 알고리즘 |
| qnote-6 | 스프링 의존성 주입 |
| qnote-7 | 동적 프로그래밍 메모이제이션 |
| qnote-8 | BFS 그래프 탐색 |
| qnote-9 | 스택 자료구조 |
| qnote-10 | 자바 예외 처리 |

#### 시행착오

전처리 적용 시 Recall@4가 40%(4/10)로 하락했다. 10개 쿼리 중 6개에서 정답 노트가 Top-4에 포함되지 못했다.

| 쿼리 노트 | 결과 | Top-4 반환 |
|---|---|---|
| qnote-1 (HashMap) | miss | qnote-7, qnote-4, qnote-10, qnote-2 |
| qnote-2 (재귀) | miss | qnote-7, qnote-10, qnote-4, qnote-5 |
| qnote-3 (이진탐색) | miss | qnote-4, qnote-7, qnote-9, qnote-6 |
| qnote-4 (SQL) | **HIT** | qnote-4, qnote-7, qnote-9, qnote-2 |
| qnote-5 (버블정렬) | miss | qnote-7, qnote-9, qnote-4, qnote-10 |
| qnote-6 (스프링 DI) | miss | qnote-10, qnote-4, qnote-7, qnote-3 |
| qnote-7 (DP) | **HIT** | qnote-7, qnote-9, qnote-10, qnote-4 |
| qnote-8 (BFS) | miss | qnote-9, qnote-7, qnote-10, qnote-2 |
| qnote-9 (스택) | **HIT** | qnote-9, qnote-7, qnote-4, qnote-6 |
| qnote-10 (예외처리) | **HIT** | qnote-10, qnote-9, qnote-7, qnote-8 |

하락 원인은 두 가지다.

첫째, **허브 오염 현상**이 발생했다. 허브 오염 현상이란 특정 단어가 너무 많은 문서에 공통으로 포함될 때 서로 주제가 다른 문서 사이의 유사도가 비정상적으로 높게 측정되는 문제를 말한다. 전처리 후 qnote-7(DP/메모이제이션)의 임베딩 대상 텍스트는 다음과 같이 변환됐다.

```
[java: HashMap memo containsKey fibonacci climbStairs result DynamicProgramming]
```

이 식별자들이 여러 노트와 교차했다. `HashMap`, `containsKey`는 qnote-1(HashMap)과, `fibonacci`는 qnote-2(재귀)와, `result`, `climbStairs`는 다수 노트와 겹쳤다. 결과적으로 qnote-7이 10개 쿼리 중 6개의 Top-4에 잘못 등장했다.

둘째, **문맥 소실**이 발생했다. `text-embedding-3-small`은 코드와 자연어 혼합 문서를 원문 그대로 처리하도록 훈련된 모델이다. 코드 블록을 식별자 목록으로 압축하면 함수 시그니처, 자료 흐름 등 모델이 활용하는 문맥 정보가 소실된다. 또한 공통 변수명(`result`, `temp`, `arr`)이 여러 노트에 반복 등장하면서 주제와 무관한 노트 간 거짓 유사도를 유발했다.

#### 테스트 결과

#### 학습 결과 분석

전처리 방식이 임베딩 품질을 저하시킨다는 사실을 확인하고 전체 청킹 방식을 채택했다. 청킹 방식 비교 표에서 명시한 정보 희석 우려보다 허브 오염 현상과 문맥 소실로 인한 Recall@4 하락(100% → 40%)이 실측으로 확인된 점이 채택의 결정적 근거다.

초기 가설("코드 블록의 구문 기호가 벡터를 희석시킨다")은 Word2Vec 시대의 단순 평균 임베딩에서는 유효했던 개념이지만, 문맥 전체를 바라보는 `text-embedding-3-small`에서는 코드 원문 유지가 오히려 더 정확한 표현을 만든다.

현재 노트 규모에서는 노트 길이가 임베딩 품질에 미치는 영향이 제한적이다. `text-embedding-3-small`의 최대 입력 컨텍스트는 8,191 토큰이며, 일반적인 개발자 학습 노트는 200~500단어(약 300~700 토큰) 수준으로 최대 컨텍스트의 10% 이내에 해당하여 정보 희석 문제가 발생하지 않는다. 단, 본 측정은 코드 블록이 포함된 CS 주제 노트 10개를 대상으로 수행했으며, 코드 없는 개념 노트에 대한 검증은 포함되지 않았다.

## 2.3.2 하이브리드 검색 알고리즘 (Dense + Sparse + RRF)

관련 과거 노트를 검색할 때 단일 검색 방식만으로는 모든 유형의 관련성을 포착하기 어렵다. Dense 검색은 텍스트의 의미 벡터 간 유사도를 기준으로 의미가 비슷한 노트를 찾고, Sparse 검색은 키워드가 직접 포함된 노트를 찾는다. 두 방식을 함께 사용하는 하이브리드 방식을 설계했으며, 각 결과는 RRF 알고리즘으로 병합하여 최종 Top-4를 반환한다. RRF란 여러 검색 결과 목록의 순위를 점수로 변환하여 합산하고 하나의 통합 목록을 만드는 방식이다.

**ChromaDB 인덱스 설정**

ChromaDB는 HNSW 인덱스를 사용하여 벡터 유사도 검색을 수행한다. HNSW(Hierarchical Navigable Small World)란 벡터들을 계층적 그래프 구조로 연결하여 유사한 벡터를 빠르게 탐색하는 알고리즘이다. 모든 벡터를 하나씩 비교하는 방식과 달리 그래프를 따라 이동하며 가까운 벡터를 찾으므로, 노트 수가 증가해도 검색 속도가 크게 느려지지 않는다. 거리 측정 기준으로는 코사인 유사도를 사용한다. 코사인 유사도는 두 벡터가 얼마나 같은 방향을 가리키는지를 0~1 사이 수치로 나타내며, 벡터의 크기가 아닌 방향을 기준으로 유사도를 계산한다. 이 때문에 노트 길이가 달라도 내용의 의미가 비슷하면 높은 유사도가 나온다.

**Dense 검색과 Sparse 검색의 역할**

Dense 검색은 두 벡터가 얼마나 같은 방향을 가리키는지를 0~1 사이 수치로 나타낸 코사인 유사도를 기반으로 의미적으로 유사한 노트를 검색한다. 값이 1에 가까울수록 두 노트의 의미가 유사하다는 뜻이다. 유사도가 0.55 미만인 문서는 관련성이 낮다고 판단하여 사전에 제거한다. 단, BFS↔DFS처럼 코사인 유사도가 낮은(0.26) 대립 개념 쌍은 의미 공간에서 서로 멀리 위치하여 Dense 검색만으로는 상호 검색이 불가능하다.

임베딩 공간에서 각 노트는 하나의 점으로 표현된다. 의미가 비슷한 노트일수록 두 점이 가깝고(코사인 유사도 높음), 의미가 다를수록 멀다(코사인 유사도 낮음). BFS와 DFS는 사람이 보기엔 "그래프 탐색 알고리즘"이라는 공통점이 있지만, 텍스트 내용 자체는 크게 다르다. BFS 노트는 "가까운 정점부터 방문, 큐 사용, 최단 경로"를 설명하고, DFS 노트는 "한 방향으로 끝까지 탐색, 스택·재귀 사용, 사이클 감지"를 설명한다. 동작 방식, 사용 자료구조, 활용 목적이 모두 달라 임베딩 모델이 계산하는 텍스트 의미 유사도가 0.26에 불과하다. Dense 검색 임계값 0.55에 크게 못 미치므로 BFS 노트를 쿼리로 넣어도 DFS 노트는 결과에 나타나지 않는다.

Sparse 검색은 키워드 기반 텍스트 매칭으로 정확한 어휘 일치를 확인한다. 임계값 없이 후보를 넓게 수집한 뒤 키워드 포함 여부로 후처리 필터를 적용한다. Dense가 의미 공간에서 찾지 못한 키워드 기반 관련 노트를 보완하는 역할을 한다.

두 방식을 결합하는 이유는 의미적 유사도와 어휘적 일치라는 서로 다른 유형의 관련성을 동시에 확보하기 위함이다. Dense는 "비슷한 개념"을 찾고, Sparse는 "동일한 용어가 등장하는 노트"를 찾는다. 두 방식은 서로 다른 유형의 누락을 보완한다.

최종 반환 수를 4건으로 설정한 이유는 System Prompt의 컨텍스트 길이 제한 때문이다. RAG로 주입하는 과거 노트가 많아질수록 프롬프트가 길어져 AI 튜터 응답 품질이 저하될 수 있다. 4건은 유의미한 과거 학습 맥락을 제공하면서 프롬프트 길이를 적정 수준으로 유지하는 균형점이다.

Dense 검색의 후보 수(topK=6)는 최종 반환 수 4건에 여유분 2건을 더한 값(`max-results + 2`)이다. RRF 병합 이후 2차 필터(키워드 오버랩 10% 미만 제거)가 적용되므로, Dense 단계에서 정확히 4건만 가져오면 2차 필터로 일부가 탈락했을 때 최종 결과가 4건에 미치지 못할 수 있다. 여유분 2건은 이 탈락을 보상하여 최종 반환 수 4건을 안정적으로 확보하기 위한 값이다.

Sparse 검색의 후보 수(topK=10)는 임계값 최적화 측정에서 상위 10건 기준으로 실험하여 충분한 후보를 확보했기 때문에 그대로 운영값으로 사용했다.

Sparse 검색의 임계값을 0.0으로 설정한 이유는 두 가지다.

첫째, **API 제약** 때문이다. 현재 사용하는 Spring AI의 VectorStore는 `similaritySearch` 하나만 제공하며 BM25나 역색인 기반의 순수 키워드 검색 API가 없다. 임계값 0.0은 "유사도 필터 없이 상위 N개 후보를 수집"하는 유일한 방법이다.

둘째, **Dense 검색과 후보 범위가 겹치지 않도록** 하기 위함이다. Sparse 검색에도 0.55 임계값을 적용하면 Dense와 동일한 후보 풀이 생성되어 Sparse가 Dense를 보완하는 의미가 없어진다. 임계값을 0.0으로 낮춰야 Dense가 유사도 기준으로 제외한 문서들까지 후보에 포함되고, 그 중 키워드 필터를 통해 실제 관련 문서를 찾을 수 있다.

**RRF 수식**

```
score(문서) = Σ [ 1 / (k + rank(문서, 결과목록)) ],  k = 60
```

k 값은 순위 간 점수 차이를 조절하는 완충 역할을 한다. k가 작으면(예: 10) 순위 1위 문서가 압도적으로 높은 점수를 받아 순위 역전이 거의 불가능해지고, k가 크면(예: 100) 순위 간 점수 차이가 줄어들어 Dense와 Sparse 각각의 순위 신호가 균등하게 반영된다.

**검증 (RRF k=60 최적값 검증)**

#### 필요성

k=60은 Cormack et al.(2009) 논문의 기본값으로 대규모 문서 검색 환경에서 도출된 경험값이다. 이 시스템은 사용자당 노트 수가 적고(수십 건), Dense와 Sparse 후보가 각각 최대 6개/10개에 불과한 소규모 환경이다. 소규모 환경에서 k=60이 최적인지 검증한 적이 없어, k 값 변화에 따른 Top-4 구성 변화 여부와 양쪽 목록 등장 문서의 우선순위 보장 여부를 확인해야 했다.

#### 특징

두 가지 방식으로 검증했다. 첫째, 고정 입력으로 k 값(10, 30, 60, 100)에 따른 순위 변화를 비교했다. 둘째, 이 시스템의 실제 후보 규모(Dense 최대 6개, Sparse 최대 10개)에서 최악의 케이스와 단독 최상위 케이스를 수식으로 직접 계산했다.

#### 설정 과정

고정 입력으로 Dense 4개, Sparse 4개(일부 겹침)를 사용했다.

```
Dense  = [A, B, C, D]    // C가 3위
Sparse = [C, A, E, F]    // C가 1위
검증 목표: C(양쪽 등장 문서)가 최종 Top-1이어야 함
```

k=10, 30, 60, 100에서 C(양쪽 등장)와 A(Dense 단독 1위)의 점수를 각각 계산하여 비교했다.

#### 테스트 결과

**k 값별 점수 비교**

| k | C 점수 (Dense 3위 + Sparse 1위) | A 점수 (Dense 1위만) | C > A |
|---|---|---|---|
| 10 | 1/(10+3) + 1/(10+1) = 0.0769 + 0.0909 = **0.1678** | 1/(10+1) = 0.0909 | ✅ |
| 30 | 1/(30+3) + 1/(30+1) = 0.0303 + 0.0323 = **0.0626** | 1/(30+1) = 0.0323 | ✅ |
| 60 | 1/(60+3) + 1/(60+1) = 0.0159 + 0.0164 = **0.0323** | 1/(60+1) = 0.0164 | ✅ |
| 100 | 1/(100+3) + 1/(100+1) = 0.0097 + 0.0099 = **0.0196** | 1/(100+1) = 0.0099 | ✅ |

모든 k 값에서 양쪽 등장 문서 C가 Dense 단독 1위 문서 A보다 높은 점수를 받았다. k 값에 따른 Top-4 순위 구성 변화도 없었다.

**이 시스템 실제 후보 규모 최악의 케이스 계산 (k=60)**

```
양쪽 등장 문서(Dense 6위 + Sparse 6위) 점수:
    1/(60+6) + 1/(60+6) = 0.0152 + 0.0152 = 0.030

Dense 단독 1위 문서 점수:
    1/(60+1) = 0.016

0.030 > 0.016  →  최악의 케이스에서도 양쪽 등장 문서가 단독 1위보다 높은 점수를 가짐
```

#### 학습 결과 분석

k 값(10~100)에 따른 Top-4 구성 변화가 없음을 확인했다. k=60은 논문 기본값이 소규모 환경(6~10개 후보)에서도 안정적으로 동작함을 의미한다. 양쪽 목록에 등장한 문서가 단독 최상위보다 항상 높은 점수를 받는 조건이 k=60뿐 아니라 k=10~100 전 범위에서 성립하므로, k값 재조정 없이 논문 기본값을 그대로 유지한다.

**검색 파이프라인**

Sparse 검색의 키워드 필터는 키워드가 하나도 포함되지 않는 문서를 1차로 제거하는 관문 역할이며, 이후 2.3.3의 2차 필터가 오버랩 비율 기준으로 정밀하게 노이즈를 제거한다.

```
PROCEDURE 하이브리드검색(쿼리, 사용자ID, 제외노트ID):

    // 1단계: Dense 검색
    Dense후보 ← 벡터DB.유사도검색(
        쿼리,
        임계값=0.55,
        최대개수=6,
        필터=사용자ID 일치 AND 제외노트ID 불일치
    )

    // 2단계: Sparse 검색
    Sparse후보 ← 벡터DB.키워드검색(
        쿼리,
        임계값=0.0,
        최대개수=10,
        필터=사용자ID 일치 AND 제외노트ID 불일치
    )
    Sparse후보 ← Sparse후보 중 키워드를 하나라도 포함하는 문서만 유지

    // 3단계: RRF 병합
    병합결과 ← RRF병합(Dense후보, Sparse후보, k=60)

    // 4단계: 2차 필터
    최종결과 ← 주제관련성필터(병합결과, 오버랩임계값=0.1)

    RETURN 최종결과 상위 4건
```

**RAG 기반 할루시네이션 방지 전략**

LLM 응답이 학습자 본인의 노트 내용에 근거하도록 RAG 검색 결과를 프롬프트에 주입하는 구조로 설계한다. 할루시네이션이란 AI가 근거 없이 그럴듯한 내용을 만들어내는 현상을 말하는데, 이를 별도 감지 로직 없이 구조적으로 차단한다.

과거 노트임을 명시하는 레이블을 포함하여 주입하는 이유는 초기 구현 경험에서 도출됐다. 레이블 없이 주입 시 LLM이 과거 노트를 현재 노트의 일부로 오해하여 직접 정답을 제공하는 현상이 발생했다. 레이블을 통해 과거 노트의 역할을 명시함으로써 System Prompt의 RAG 노이즈 거부 규칙과 함께 동작하도록 설계한다.

RAG 결과가 없는 경우 LLM은 현재 노트만을 근거로 응답을 생성하며, TYPE_C 질문은 TYPE_A로 폴백하여 맥락 없는 과거 학습 연계 질문 생성을 방지한다.

**검증 (임계값 최적화 측정 / 하이브리드 Recall@4 측정)**

#### 필요성

Dense 검색에 경험적으로 설정한 초기 임계값 0.75가 이 프로젝트의 노트 특성과 임베딩 모델에 적합한지 검증한 적이 없었다. 임계값이 너무 높으면 연관 노트가 Dense 검색에서 누락되어 의미 기반 연결이 작동하지 않고, 너무 낮으면 관련 없는 노트가 프롬프트에 주입되어 AI 응답 품질이 저하될 수 있다. 또한 하이브리드 검색의 실제 효과를 수치로 확인할 필요가 있었다.

#### 특징

`threshold=0.0`으로 전체 후보를 한 번에 조회한 뒤 Java 단에서 각 임계값 통과 여부를 비교하는 방식으로 진행했다. 서버를 임계값별로 재시작하지 않고 한 번의 측정으로 여러 임계값을 비교할 수 있었다. 하이브리드 Recall@4 측정은 `bm25-max-results=0` 설정으로 Dense-only 모드와 하이브리드 모드를 직접 비교했다.

#### 설정 과정

CS 개념·알고리즘·프레임워크 노트 20개를 ChromaDB에 임베딩하고 쿼리 노트 10개(noteId=1~10)를 사용했다. 임베딩 모델은 text-embedding-3-small이며, 하이브리드 Recall@4 측정에서는 쿼리 노트를 카테고리 A(기술 식별자 포함)와 카테고리 B(한국어 CS 용어)로 구분했다.

카테고리 A는 `HashMap`, `factorial` 같은 코드 식별자가 임베딩 공간에서 의미 거리를 제대로 표현하지 못하는 케이스를, 카테고리 B는 "큐", "스택" 같은 짧은 한국어 CS 용어가 유사도 임계값을 넘지 못하는 케이스를 대상으로 했다.

> ⚠️ noteId=10(힙): Sparse가 10건 후보를 찾았으나 2차 필터에서 전부 제거됨

**카테고리별 향상폭**

| 카테고리 | Dense-only | 하이브리드 | 향상폭 |
|---|---|---|---|
| A (기술 식별자 포함) | 0.12 | 0.47 | **+0.35** |
| B (한국어 CS 용어) | 0.23 | 0.38 | **+0.15** |

두 카테고리 모두 10%p 기준을 초과하여 하이브리드 검색의 유효성을 확인했다.

#### 학습 결과 분석

임계값 0.55를 채택하고 하이브리드 검색(Dense + Sparse + RRF) 구조를 유지한다. 이 값은 노트 20개 기준 측정값이므로 노트 수가 크게 증가하면 유사도 분포가 변화하여 재검토가 필요하다.

유사도 임계값, 검색 정책, 또는 2차 필터 설정(오버랩 임계값·키워드 추출 조건)을 변경할 경우 반드시 Recall@4 회귀 측정을 수행한다(REQ-AIV-010). 회귀 측정의 목표치는 전체 평균 Recall@4 ≥ 0.35로 설정한다. 현재 기준선은 0.42(2026-06-02 재측정)이며, 목표치 미달 시 변경 사항을 재검토한다. 측정 절차는 `docs/테스트/REQ_AIV_010_회귀_Recall_측정.md`를 따른다.

## 2.3.3 2차 필터 키워드 오버랩 알고리즘

RRF 병합 결과는 유사도 기준을 통과했으나 실제로는 주제와 무관한 문서를 포함할 수 있다. 2차 필터는 현재 노트와 후보 문서 간 키워드 오버랩 비율이 10% 미만인 문서를 최종 결과에서 제거한다. Sparse 검색으로 후보 범위가 넓어졌기 때문에 최종 단계의 노이즈 제거 역할이 중요하다.

Dense 검색과 Sparse 검색을 병행하면 후보 범위가 넓어지는 만큼 주제와 무관한 문서도 함께 포함될 가능성이 높아진다. RRF 병합 이후 최종 단계에서 키워드 오버랩 비율을 기준으로 관련성이 낮은 문서를 제거하는 2차 필터를 설계했다.

**알고리즘 동작 방식**

현재 노트와 후보 문서 각각에서 의미 있는 키워드를 추출한다. 키워드 추출 조건은 한국어 2자 이상, 영어 4자 이상이며, 최대 20개 상한을 적용한다. 두 집합의 교집합 크기를 현재 노트의 키워드 수로 나누어 오버랩 비율을 계산하고, 10% 미만이면 해당 문서를 제거한다.

한국어 1자 단어는 조사·접속사('의', '을', '과' 등)가 대부분이어서 주제 관련성 판단에 의미가 없다. 2자 이상으로 제한하면 실질적인 개념어만 추출된다. 영어 3자 이하 단어는 관사·전치사('the', 'for', 'and' 등) 및 약어가 많아 주제 관련성 판단에 노이즈가 된다. 4자 이상으로 제한하면 실질적인 기술 용어만 추출된다. 영어 최소 길이는 2차 필터 수동 측정에서 3자에서 4자로 변경됐다.

```
PROCEDURE 주제관련성필터(후보목록, 오버랩임계값):
    결과 ← 빈 목록

    FOR 각 문서 IN 후보목록:
        쿼리키워드 ← 키워드추출(현재노트, 한국어최소=2자, 영어최소=4자, 최대=20개)
        문서키워드 ← 키워드추출(문서, 한국어최소=2자, 영어최소=4자, 최대=20개)

        IF 쿼리키워드 크기 == 0:
            결과.추가(문서)  // 키워드 추출 불가 시 분모가 0이 되는 예외 방지: 무조건 통과
            CONTINUE

        오버랩수 ← 쿼리키워드 AND 문서키워드 의 교집합 크기
        오버랩비율 ← 오버랩수 / 쿼리키워드 크기

        IF 오버랩비율 >= 오버랩임계값:
            결과.추가(문서)

    RETURN 결과
```

**검증 (2차 필터 수동 측정)**

#### 필요성

2차 필터는 경험적으로 "코사인 유사도는 높지만 실제 주제가 다른 문서"를 걸러내기 위해 설계됐으나, 실제로 얼마나 많은 노이즈를 제거하고 있는지, 또는 얼마나 많은 유효 문서를 잘못 제거하는지 측정한 적이 없었다. 임계값이 너무 높으면 유효한 과거 노트가 걸러져 TYPE_C 질문 생성 기회가 줄어들고, 너무 낮으면 노이즈가 프롬프트에 주입되어 AI 응답 품질이 저하될 수 있었다.

#### 특징

`retrieve()` 내부에 RRF 병합 후 건수와 2차 필터 후 건수를 기록하는 임시 로그를 추가하고, 대화 시작 API 10회 호출 후 로그를 수집하여 제거율을 계산했다.

#### 설정 과정

한국어 CS 노트 20개와 쿼리 노트 10개(noteId=1~10)를 사용했다. 측정 지표는 2차 필터 평균 제거율로 설정했으며, 제거율 30% 초과 시 임계값 조정이 필요하다고 판단했다.

#### 시행착오

수정 전 평균 제거율이 90%로 기준을 크게 초과했다. 문제는 임계값이 높은 것이 아니라 구조적 설계 문제였다. 2차 필터는 짧은 쿼리(몇 개 키워드)를 가정하고 설계됐으나, 실제로는 노트 전문(약 150단어)이 쿼리로 들어오는 상황이었다.

#### 학습 결과 분석

현재 설정(한국어 2자, 영어 4자, 최대 20개 상한, 임계값 0.1)을 유지한다. 45%는 기준(30%)을 초과하지만 현재 노트 수(20개)에서는 정상 범위다. 노트 수가 적으면 유사 노트도 상위에 진입하므로 제거율이 높아지며, 노트 수가 50개 이상으로 늘어나면 제거율이 자연히 낮아질 것으로 예상한다.

힙(`noteId=10`)처럼 전문 용어("최대힙", "최소힙", "heapify")가 많은 노트는 다른 노트에 해당 용어가 거의 등장하지 않아 2차 필터가 과도하게 작동했다. 반대로 퀵정렬(`noteId=7`)은 정렬·알고리즘 계열 노트와 키워드가 많이 겹쳐 전부 통과했다. 이처럼 필터 제거율의 노트별 편차는 의미 있는 정보를 담고 있으며, 제거율이 낮을수록 관련 과거 노트가 더 많이 존재하는 주제임을 나타낸다.

부가 발견: 1차 측정에서 TYPE_F로 분류됐던 퀵정렬 노트가 수정 후 RAG 컨텍스트가 살아나면서 TYPE_B(설계 의도 탐침)로 분류됐다. "피벗 선택 전략"과 "병합 정렬 vs 캐시 효율 비교" 트레이드오프가 RAG 컨텍스트를 통해 라우터에 반영된 결과다.
