## 2.3.1 청킹 전략 비교 및 선택 근거

노트를 임베딩할 때 텍스트를 어떤 단위로 처리하느냐에 따라 벡터의 품질과 검색 정확도가 달라진다. 두 가지 방식을 검토한 결과 전체 청킹 방식을 채택했다. 전체 청킹은 노트 원문 전체를 하나의 단위로 임베딩하는 방식으로, 임베딩 모델이 코드와 자연어 혼합 문서를 원문 그대로 처리하도록 훈련된 특성을 최대한 활용한다.

**청킹 방식 비교**

| 방식 | 설명 | 장점 | 단점 |
|---|---|---|---|
| 전체 청킹 | 노트 전체를 하나의 단위로 임베딩 | 모델의 문맥 이해를 최대한 활용 | 노트가 길수록 임베딩 벡터에 정보가 희석될 가능성 |
| 설명·코드 분리 청킹 | 설명 텍스트와 코드 블록을 별도 단위로 분리 후 임베딩 | 코드와 설명을 독립적으로 검색 가능 | 임베딩 모델이 문맥 정보를 활용하지 못하고 식별자 단위로 처리 |

**검증 (전처리 임베딩 품질 측정)**

#### 필요성

코드 블록을 식별자 목록으로 변환하는 전처리 방식이 임베딩 품질에 미치는 영향을 검증해야 했다. 전처리를 적용하면 코드와 자연어를 분리하여 임베딩 벡터의 품질이 향상될 것이라는 가설이 있었으나, 실제 검색 정확도에 미치는 영향은 측정되지 않은 상태였다.

#### 특징

전처리 적용 상태와 미적용 상태에서 동일한 쿼리를 실행하여 Recall@4를 직접 비교하는 수동 실험으로 진행했다.

#### 설정 과정

코드 블록이 포함된 CS 주제 노트 10개와 각 노트에 대응하는 정답 쿼리 10개를 사용했다. 임베딩 모델은 text-embedding-3-small을 사용했으며, 평가 지표는 Recall@4(topK=4)로 설정했다.

#### 시행착오

전처리 적용 시 Recall@4가 40%로 하락했다. 하락 원인은 두 가지다.

첫째, **허브 오염 현상**이 발생했다. 식별자 목록으로 압축하면 여러 주제에서 공통으로 쓰이는 식별자(`HashMap`, `fibonacci` 등)가 노트 간 거짓 유사도를 생성한다. 실제로 DP/메모이제이션 노트(qnote-7)가 `HashMap`, `fibonacci` 같은 식별자를 포함하게 되어 10개 쿼리 중 6개의 Top-4에 잘못 등장하는 현상이 관찰됐다.

둘째, **문맥 소실**이 발생했다. 사용 임베딩 모델(`text-embedding-3-small`)은 코드와 자연어 혼합 문서를 원문 그대로 처리하도록 훈련되어 있어 원문 유지가 유리하다. 코드 블록을 식별자 목록으로 압축하면 함수 시그니처·자료 흐름 등 모델이 활용하는 문맥 정보가 소실된다.

#### 테스트 결과

| 청킹 방식 | Recall@4 |
|---|---|
| 설명·코드 분리 청킹 (전처리 적용) | 40% |
| 전체 청킹 (원본 그대로) | **100%** |

#### 학습 결과 분석

전처리 방식이 임베딩 품질을 저하시킨다는 사실을 확인하고 전체 청킹 방식을 채택했다. 청킹 방식 비교 표에서 명시한 정보 희석 우려보다 허브 오염 현상과 문맥 소실로 인한 Recall@4 하락(100% → 40%)이 실측으로 확인된 점이 채택의 결정적 근거다. 현재 노트 규모에서는 노트 길이가 임베딩 품질에 미치는 영향이 제한적이다. text-embedding-3-small의 최대 입력 컨텍스트는 8,191 토큰이며, 일반적인 개발자 학습 노트는 200~500단어(약 300~700 토큰) 수준이다. 정보 희석 문제는 문서 길이가 모델의 컨텍스트 한계에 근접하거나 초과할 때 두드러지는데, 현재 노트 길이는 최대 컨텍스트의 10% 이내에 해당하여 모델이 전체 내용을 손실 없이 처리할 수 있다. 단, 본 측정은 코드 블록이 포함된 CS 주제 노트 10개를 대상으로 수행했으며, 코드 없는 개념 노트에 대한 검증은 포함되지 않았다.

## 2.3.2 하이브리드 검색 알고리즘 (Dense + Sparse + RRF)

관련 과거 노트를 검색할 때 단일 검색 방식만으로는 모든 유형의 관련성을 포착하기 어렵다. 의미적으로 유사한 노트는 Dense 검색으로, 동일한 키워드가 등장하는 노트는 Sparse 검색으로 각각 보완하는 하이브리드 방식을 설계했다. 두 결과는 RRF 알고리즘으로 병합하여 최종 Top-4를 반환한다.

**ChromaDB 인덱스 설정**

ChromaDB는 HNSW 인덱스를 사용하여 벡터 유사도 검색을 수행한다. HNSW(Hierarchical Navigable Small World)란 벡터들을 계층적 그래프 구조로 연결하여 유사한 벡터를 빠르게 탐색하는 알고리즘이다. 모든 벡터를 하나씩 비교하는 방식과 달리 그래프를 따라 이동하며 가까운 벡터를 찾으므로, 노트 수가 증가해도 검색 속도가 크게 느려지지 않는다. 거리 측정 기준으로는 코사인 유사도를 사용한다. 코사인 유사도는 두 벡터가 얼마나 같은 방향을 가리키는지를 0~1 사이 수치로 나타내며, 벡터의 크기가 아닌 방향을 기준으로 유사도를 계산한다. 이 때문에 노트 길이가 달라도 내용의 의미가 비슷하면 높은 유사도가 나온다.

**Dense 검색과 Sparse 검색의 역할**

Dense 검색은 임베딩 벡터 간 코사인 유사도를 기반으로
의미적으로 유사한 노트를 검색한다. 유사도 임계값 0.55를
적용하여 관련성이 낮은 문서를 사전에 제거한다. 단,
BFS↔DFS처럼 대립 개념 쌍은 코사인 유사도가 0.26으로
낮아 Dense 검색만으로는 상호 검색이 불가능하다. BFS와
DFS는 둘 다 그래프 탐색 알고리즘이지만 임베딩 모델은
단어가 어떤 맥락으로 함께 등장하는지를 학습하기 때문에
두 개념의 벡터가 서로 다른 방향을 가리키게 된다. BFS는
"최단 경로", "너비 우선", "큐(Queue)" 같은 단어와 함께
쓰이고, DFS는 "백트래킹", "깊이 우선", "스택(Stack)"
같은 단어와 함께 쓰인다. 사람 입장에서는 둘 다 그래프
탐색이라 관련 있어 보이지만, 임베딩 모델은 사용 맥락을
기준으로 벡터를 결정하므로 BFS 노트를 검색할 때 DFS
노트가 유사도 임계값 0.55에 미치지 못해 검색되지 않는다.

Sparse 검색은 키워드 기반 텍스트 매칭으로 정확한 어휘 일치를 확인한다. 임계값 없이 후보를 넓게 수집한 뒤 키워드 포함 여부로 후처리 필터를 적용한다. Dense가 의미 공간에서 찾지 못한 키워드 기반 관련 노트를 보완하는 역할을 한다.

두 방식을 결합하는 이유는 의미적 유사도와 어휘적 일치라는 서로 다른 유형의 관련성을 동시에 확보하기 위함이다. Dense는 "비슷한 개념"을 찾고, Sparse는 "동일한 용어가 등장하는 노트"를 찾는다. 두 방식은 서로 다른 유형의 누락을 보완한다.

최종 반환 수를 4건으로 설정한 이유는 System Prompt의 컨텍스트 길이 제한 때문이다. RAG로 주입하는 과거 노트가 많아질수록 프롬프트가 길어져 AI 튜터 응답 품질이 저하될 수 있다. 4건은 유의미한 과거 학습 맥락을 제공하면서 프롬프트 길이를 적정 수준으로 유지하는 균형점이다.

Dense 검색의 후보 수(topK=6)는 최종 반환 수 4건에 여유분 2건을 더한 값(`max-results + 2`)이다. RRF 병합 이후 2차 필터(키워드 오버랩 10% 미만 제거)가 적용되므로, Dense 단계에서 정확히 4건만 가져오면 2차 필터로 일부가 탈락했을 때 최종 결과가 4건에 미치지 못할 수 있다. 여유분 2건은 이 탈락을 보상하여 최종 반환 수 4건을 안정적으로 확보하기 위한 값이다.

Sparse 검색의 후보 수(topK=10)는 임계값 최적화 측정에서 상위 10건 기준으로 실험하여 충분한 후보를 확보했기 때문에 그대로 운영값으로 사용했다.

Sparse 검색의 임계값을 0.0으로 설정한 이유는 두 가지다.
첫째, API 제약 때문이다. Sparse 검색의 원래 목적은 특정 키워드가 포함된 노트를 직접 찾는 것이지만, 현재 사용하는 Spring AI는 유사도 검색 기능만 제공하고 키워드 검색 기능을 별도로 제공하지 않는다. 임계값을 0.0으로 설정하면 유사도 기준 없이 상위 N개 후보를 전부 가져올 수 있어, 이후 키워드 포함 여부를 직접 확인하는 방식으로 키워드 검색을 대체했다.
둘째, Dense 검색이 놓친 노트를 잡아내기 위함이다. Dense 검색은 유사도 0.55 이상인 노트만 가져온다. Sparse 검색에도 같은 기준을 적용하면 두 검색이 동일한 노트만 반환하여 Sparse가 Dense를 보완하는 의미가 없어진다. 임계값을 0.0으로 설정해야 Dense가 유사도 기준으로 제외한 노트까지 후보에 포함되고, 그 중 키워드가 일치하는 노트를 건져낼 수 있다.
최종 반환 수 4건은 AI 튜터가 답변을 생성할 때 사용하는 프롬프트 길이를 고려하여 설정했다. 과거 노트를 많이 포함할수록 프롬프트가 길어져 AI 응답 품질이 떨어질 수 있어 4건으로 제한했다.

**RRF 수식**

```
score(문서) = Σ [ 1 / (k + rank(문서, 결과목록)) ],  k = 60
```

k=60은 Cormack et al.(2009) RRF 논문의 기본값이다. k 값은 순위 간 점수 차이를 조절하는 완충 역할을 한다. k가 너무 작으면 1위와 2위 간 점수 차이가 커져 순위 역전이 어려워지고, 너무 크면 순위 차이가 무의미해진다.

**검증 (RRF k=60 최적값 검증)**

#### 필요성

k=60은 대규모 문서 검색 환경에서 도출된 경험값이다. 이 시스템은 사용자당 노트 수가 적고(수십 건), Dense와 Sparse 각각 최대 6개/10개의 후보만 병합하는 소규모 환경이다. 소규모 환경에서 k=60이 최적인지 검증한 적이 없어, k 값 변화에 따른 Top-4 구성 변화 여부와 양쪽 목록 등장 문서의 우선순위 보장 여부를 확인해야 했다.

#### 특징

두 가지 방식으로 검증했다. 첫째, 고정 입력으로 k 값(10, 30, 60, 100)에 따른 순위 변화를 비교했다. 둘째, 이 시스템의 실제 후보 규모(Dense 최대 6개, Sparse 최대 10개)에서 최악의 케이스와 단독 최상위 케이스를 수식으로 직접 계산했다.

#### 설정 과정

고정 입력으로 Dense 4개, Sparse 4개(일부 겹침)를 사용했다.

```
Dense  = [A, B, C, D]    // C가 3위
Sparse = [C, A, E, F]    // C가 1위
검증 목표: C(양쪽 등장 문서)가 최종 Top-1이어야 함
```

k=10, 30, 60, 100에서 C(양쪽 등장)와 A(Dense 단독 1위)의 점수를 각각 계산하여 비교했다.

#### 테스트 결과

**k 값별 점수 비교**

| k | C 점수 (Dense 3위 + Sparse 1위) | A 점수 (Dense 1위만) | C > A |
|---|---|---|---|
| 10 | 1/(10+3) + 1/(10+1) = 0.0769 + 0.0909 = **0.1678** | 1/(10+1) = 0.0909 | ✅ |
| 30 | 1/(30+3) + 1/(30+1) = 0.0303 + 0.0323 = **0.0626** | 1/(30+1) = 0.0323 | ✅ |
| 60 | 1/(60+3) + 1/(60+1) = 0.0159 + 0.0164 = **0.0323** | 1/(60+1) = 0.0164 | ✅ |
| 100 | 1/(100+3) + 1/(100+1) = 0.0097 + 0.0099 = **0.0196** | 1/(100+1) = 0.0099 | ✅ |

모든 k 값에서 양쪽 등장 문서 C가 Dense 단독 1위 문서 A보다 높은 점수를 받았다. k 값에 따른 Top-4 순위 구성 변화도 없었다.

**이 시스템 실제 후보 규모 최악의 케이스 계산 (k=60)**

```
양쪽 등장 문서(Dense 6위 + Sparse 6위) 점수:
    1/(60+6) + 1/(60+6) = 0.0152 + 0.0152 = 0.030

Dense 단독 1위 문서 점수:
    1/(60+1) = 0.016

0.030 > 0.016  →  최악의 케이스에서도 양쪽 등장 문서가 단독 1위보다 높은 점수를 가짐
```

#### 학습 결과 분석

k 값(10~100)에 따른 Top-4 구성 변화가 없음을 확인했다. k=60은 논문 기본값이 소규모 환경(6~10개 후보)에서도 안정적으로 동작함을 의미한다. 양쪽 목록에 등장한 문서가 단독 최상위보다 항상 높은 점수를 받는 조건이 k=60뿐 아니라 k=10~100 전 범위에서 성립하므로, k값 재조정 없이 논문 기본값을 그대로 유지한다.

**검색 파이프라인**

Sparse 검색의 키워드 필터는 키워드가 하나도 포함되지 않는 문서를 1차로 제거하는 관문 역할이며, 이후 2.3.3의 2차 필터가 오버랩 비율 기준으로 정밀하게 노이즈를 제거한다.

```
PROCEDURE 하이브리드검색(쿼리, 사용자ID, 제외노트ID):

    // 1단계: Dense 검색
    Dense후보 ← 벡터DB.유사도검색(
        쿼리,
        임계값=0.55,
        최대개수=6,
        필터=사용자ID 일치 AND 제외노트ID 불일치
    )

    // 2단계: Sparse 검색
    Sparse후보 ← 벡터DB.키워드검색(
        쿼리,
        임계값=0.0,
        최대개수=10,
        필터=사용자ID 일치 AND 제외노트ID 불일치
    )
    Sparse후보 ← Sparse후보 중 키워드를 하나라도 포함하는 문서만 유지

    // 3단계: RRF 병합
    병합결과 ← RRF병합(Dense후보, Sparse후보, k=60)

    // 4단계: 2차 필터
    최종결과 ← 주제관련성필터(병합결과, 오버랩임계값=0.1)

    RETURN 최종결과 상위 4건
```

**RAG 기반 할루시네이션 방지 전략**

LLM 응답이 학습자 본인의 노트 내용에 근거하도록 RAG 검색 결과를 프롬프트에 주입하는 구조로 설계한다. 근거 없는 내용 생성(할루시네이션)을 별도 감지 로직 없이 구조적으로 차단한다.

과거 노트임을 명시하는 레이블을 포함하여 주입하는 이유는 초기 구현 경험에서 도출됐다. 레이블 없이 주입 시 LLM이 과거 노트를 현재 노트의 일부로 오해하여 직접 정답을 제공하는 현상이 발생했다. 레이블을 통해 과거 노트의 역할을 명시함으로써 System Prompt의 RAG 노이즈 거부 규칙과 함께 동작하도록 설계한다.

RAG 결과가 없는 경우 LLM은 현재 노트만을 근거로 응답을 생성하며, TYPE_C 질문은 TYPE_A로 폴백하여 맥락 없는 과거 학습 연계 질문 생성을 방지한다.

**검증 (임계값 최적화 측정 / 하이브리드 Recall@4 측정)**

#### 필요성

Dense 단독 검색이 코드 식별자 및 짧은 한국어 CS 용어를 포함하는 노트에서 관련 노트를 찾지 못하는 한계가 확인됐다. 하이브리드 검색의 실제 효과와 Dense 유사도 임계값의 적정 수준을 수치로 검증해야 했다.

#### 특징

두 측정을 순차적으로 수행했다. 임계값 최적화 측정은 서버 로그로 Dense 반환 건수를 관찰했고, 하이브리드 Recall@4 측정은 `bm25-max-results=0` 설정으로 Dense-only 모드와 하이브리드 모드를 직접 비교했다.

#### 설정 과정

노트 20개를 ChromaDB에 임베딩했다. 임베딩 모델은 text-embedding-3-small을 사용했으며, 쿼리 노트 10개를 카테고리 A(기술 식별자 포함)와 카테고리 B(한국어 CS 용어)로 구분하여 측정했다.

카테고리를 이렇게 구분한 이유는 Dense 검색의 두 가지 구조적 한계를 각각 검증하기 위함이다. 카테고리 A는 `HashMap`, `factorial` 같은 코드 식별자가 임베딩 공간에서 의미 거리를 제대로 표현하지 못하는 케이스를 대상으로 했고, 카테고리 B는 "큐", "스택" 같은 짧은 한국어 CS 용어가 유사도 임계값을 넘지 못하는 케이스를 대상으로 했다. 두 카테고리 모두 Dense 단독 검색이 실패할 것으로 예상되는 유형이며, 하이브리드 검색이 이를 얼마나 보완하는지 확인하는 것이 측정의 핵심 목적이었다.

#### 시행착오 1 — Dense 유사도 임계값 조정

임계값 최적화 측정에서 임계값 0.75 적용 시 Dense 검색 평균 반환 건수가 0건이었다. `text-embedding-3-small` 모델의 CS 노트 간 유사도 분포가 최대 0.71 수준으로 0.75 임계값에 도달하지 못했기 때문이다.

| 임계값 | Dense 평균 반환 건수 | 판단 |
|---|---|---|
| 0.75 | 0건 | 사용 불가 |
| 0.60 | 5.3건 | 일부 노트 결과 부족 |
| **0.55** | **5.8건** | 채택 |

#### 시행착오 2 — Dense 단독 한계 파악 및 하이브리드 고도화

임계값을 0.55로 조정한 후 Dense 단독으로 먼저 측정했다. 두 가지 케이스에서 구조적 검색 누락이 발생했다.

첫째, **코드 식별자 기반 노트**에서 누락이 발생했다. `HashMap`, `factorial` 같은 고유 식별자는 임베딩 공간에서 일반 단어와 의미 거리 구분이 어렵다. HashMap 노트(noteId=1)는 관련 노트가 0건 반환됐고 개별 Recall@4가 0.00이었다.

둘째, **짧은 한국어 CS 용어**가 포함된 노트에서 누락이 발생했다. "큐", "스택" 같은 1자 단어는 임베딩 벡터에서 의미 구분이 뭉개져 유사도 임계값 0.55를 넘지 못했다. BFS↔DFS처럼 대립 개념 쌍도 코사인 유사도가 0.26으로 낮아 서로를 관련 노트로 인식하지 못했다.

10개 쿼리 노트에 대한 전체 평균 Recall@4는 0.18이었고, 그 중 5개 노트에서 관련 노트를 전혀 반환하지 못했다.

Dense의 핵심 한계는 의미 기반 검색이라는 특성 자체에서 비롯된다. 코드 식별자처럼 의미보다 형태가 중요한 단어, 또는 짧은 용어처럼 벡터 공간에서 구분이 어려운 단어는 Dense로는 찾을 수 없다. 이 한계를 보완하기 위해 단어가 직접 포함된 노트를 찾는 Sparse 검색을 추가로 측정했다. Sparse 단독 Recall@4는 0.21로 Dense(0.18)보다 소폭 높았다. 코드 식별자 기반 노트에서 키워드 매칭이 더 잘 작동했기 때문이다. 그러나 Sparse 단독으로도 한국어 CS 용어 카테고리에서는 Dense와 동일한 수준에 그쳤다. 두 방식이 각각 서로 다른 유형의 노트에서 강점을 보인다는 점에서 두 결과를 RRF로 병합하는 하이브리드 방식으로 고도화했다.

#### 테스트 결과

Dense 단독, Sparse 단독, 하이브리드 순서로 측정하여 각 방식의 기여를 확인했다.

| 검색 방식 | 전체 평균 Recall@4 |
|---|---|
| Dense-only | 0.18 |
| Sparse-only | **0.21** |
| 하이브리드 (Dense + Sparse + RRF) | **0.43** |

Sparse 단독(0.21)은 Dense 단독(0.18)보다 소폭 높다. 코드 식별자 기반 노트(카테고리 A)에서 Sparse가 키워드 매칭으로 더 잘 찾아내기 때문이다. 그러나 두 방식 모두 단독으로는 한계가 있으며, RRF 병합으로 하이브리드(0.43)에서 유의미한 향상을 확인했다.

**카테고리별 향상폭**

| 카테고리 | Dense-only | Sparse-only | 하이브리드 |
|---|------------|-------------|-------|
| A (기술 식별자 포함) | 0.12       | 0.18        | 0.47  |
| B (한국어 CS 용어) | 0.23       | 0.23        | 0.38  |

두 카테고리 모두 10%p 기준을 초과하여 하이브리드 검색의 유효성을 확인했다.

#### 학습 결과 분석

임계값 0.55를 채택하고 하이브리드 검색(Dense + Sparse + RRF) 구조를 유지한다. 이 값은 노트 20개 기준 측정값이므로 노트 수가 크게 증가하면 유사도 분포가 변화하여 재검토가 필요하다.

유사도 임계값, 검색 정책, 또는 2차 필터 설정 (오버랩 임계값·키워드 추출 조건)을 변경할 경우 반드시 Recall@4 회귀 측정을 수행한다(REQ-AIV-010). 회귀 측정의 목표치는 전체 평균 Recall@4 ≥ 0.35로 설정한다. 현재 기준선은 0.42(2026-06-02 재측정)이며, 목표치 미달 시 변경 사항을 재검토한다. 측정 절차는 `docs/테스트/REQ_AIV_010_회귀_Recall_측정.md`를 따른다.

## 2.3.3 2차 필터 키워드 오버랩 알고리즘

RRF 병합 결과는 유사도 기준을 통과했으나 실제로는 주제와 무관한 문서를 포함할 수 있다. 2차 필터는 현재 노트와 후보 문서 간 키워드 오버랩 비율이 10% 미만인 문서를 최종 결과에서 제거한다. Sparse 검색으로 후보 범위가 넓어졌기 때문에 최종 단계의 노이즈 제거 역할이 중요하다.

Dense 검색과 Sparse 검색을 병행하면 후보 범위가 넓어지는 만큼 주제와 무관한 문서도 함께 포함될 가능성이 높아진다. RRF 병합 이후 최종 단계에서 키워드 오버랩 비율을 기준으로 관련성이 낮은 문서를 제거하는 2차 필터를 설계했다.

**알고리즘 동작 방식**

현재 노트와 후보 문서 각각에서 의미 있는 키워드를 추출한다. 키워드 추출 조건은 한국어 2자 이상, 영어 4자 이상이며, 최대 20개 상한을 적용한다. 두 집합의 교집합 크기를 현재 노트의 키워드 수로 나누어 오버랩 비율을 계산하고, 10% 미만이면 해당 문서를 제거한다.

한국어 1자 단어는 조사·접속사('의', '을', '과' 등)가 대부분이어서 주제 관련성 판단에 의미가 없다. 2자 이상으로 제한하면 실질적인 개념어만 추출된다. 영어 3자 이하 단어는 관사·전치사('the', 'for', 'and' 등) 및 약어가 많아 주제 관련성 판단에 노이즈가 된다. 4자 이상으로 제한하면 실질적인 기술 용어만 추출된다. 영어 최소 길이는 2차 필터 수동 측정에서 3자에서 4자로 변경됐다.

```
PROCEDURE 주제관련성필터(후보목록, 오버랩임계값):
    결과 ← 빈 목록

    FOR 각 문서 IN 후보목록:
        쿼리키워드 ← 키워드추출(현재노트, 한국어최소=2자, 영어최소=4자, 최대=20개)
        문서키워드 ← 키워드추출(문서, 한국어최소=2자, 영어최소=4자, 최대=20개)

        IF 쿼리키워드 크기 == 0:
            결과.추가(문서)  // 키워드 추출 불가 시 분모가 0이 되는 예외 방지: 무조건 통과
            CONTINUE

        오버랩수 ← 쿼리키워드 AND 문서키워드 의 교집합 크기
        오버랩비율 ← 오버랩수 / 쿼리키워드 크기

        IF 오버랩비율 >= 오버랩임계값:
            결과.추가(문서)

    RETURN 결과
```

**검증 (2차 필터 수동 측정)**

#### 필요성

RRF 병합 후에도 주제와 무관한 문서가 포함될 수 있어 2차 필터의 임계값과 키워드 추출 조건이 적절한지 검증해야 했다.

#### 특징

서버 로그 관찰과 수동 실험(대화 시작 API 10회 호출) 방식으로 진행했다. RRF 병합 후 건수와 2차 필터 후 건수를 직접 관찰하여 제거율을 계산했다.

#### 설정 과정

한국어 CS 노트 20개와 쿼리 노트 10개(noteId=1~10)를 사용했다. 측정 지표는 2차 필터 평균 제거율로 설정했다.

#### 시행착오

수정 전 평균 제거율이 90%로, 설계 기준(30% 초과 시 조치 필요)을 크게 초과했다. 문제는 구조적이었다. 2차 필터에 전달되는 쿼리가 노트 전문(약 150단어)이어서, 한국어 최소 길이 1자 기준으로 약 150개의 키워드가 추출됐다. 20% 임계값을 통과하려면 과거 노트가 그 중 30개 이상의 키워드를 포함해야 했고, 다른 주제의 노트가 이를 만족하기는 구조적으로 불가능했다.

| 항목 | 수정 전 | 수정 후 |
|---|---|---|
| 한국어 최소 길이 | 1자 | **2자** |
| 영어 최소 길이 | 3자 | **4자** |
| 키워드 최대 개수 | 제한 없음 (~150개) | **20개 상한** |
| 오버랩 임계값 | 0.2 (20%) | **0.1 (10%)** |
| 평균 제거율 | 90% | — |

#### 테스트 결과

수정 후 평균 제거율은 45%로 낮아졌다. 한국어 2자 이상, 영어 4자 이상 기준으로 의미 있는 키워드만 20개 이하로 추출하게 됐으며, 10% 기준으로 2개 이상 일치하면 통과하므로 필터가 원래 의도대로 노이즈 문서만 제거하도록 동작한다.

#### 학습 결과 분석

현재 설정(한국어 2자, 영어 4자, 최대 20개 상한, 임계값 0.1)을 유지한다. 힙(`noteId=10`)처럼 전문 용어("최대힙", "최소힙", "heapify")가 많은 노트는 다른 노트에 해당 용어가 거의 등장하지 않아 2차 필터가 과도하게 작동하여 Recall@4가 0.00이 됐다. 노트 수가 50개 이상으로 늘어나면 관련 개념을 다루는 노트가 더 많아지므로 제거율이 자연히 낮아질 것으로 예상한다.
