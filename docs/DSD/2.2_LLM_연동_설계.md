## 2.2.1 질문 유형 정의 (TYPE A~E)

소크라테스식 튜터링의 핵심은 학습자의 현재 인지 수준보다 한 단계 높은 사고를 자극하는 질문을 던지는 것이다. 이를 구현하려면 "지금 어떤 종류의 질문이 적절한가"를 노트 내용만으로 판단할 수 있어야 한다. 질문 유형 분류 체계는 이 판단을 위한 기준이다.

질문 유형은 Bloom's Taxonomy를 기반으로 설계했다. Bloom's Taxonomy는 단순 기억부터 평가까지 인지 단계를 체계적으로 구분하는 교육학 표준 프레임워크로, 계층 구조가 "어떤 수준의 질문을 던져야 하는가"라는 설계 목적에 직접 대응한다. 개발자 노트의 코드 블록 특성은 Bloom's Taxonomy 어느 단계에도 직접 대응하지 않아 TYPE_E를 별도로 추가했다.

| TYPE | 설명 | 적용 조건 | Bloom's 대응 |
|---|---|---|---|
| TYPE_A | 개념 정의 확인 및 적용 탐구 | 새로운 용어·개념이 등장하거나, 코드 없이 이론·개념만 서술된 순수 텍스트 노트 | Knowledge (기억) + Application (적용) |
| TYPE_B | 설계 의도 탐구 | 트레이드오프·기술 선택 근거가 포함된 경우 | Evaluation (평가) |
| TYPE_C | 과거 학습 연계 | RAG로 관련 과거 노트가 존재할 때만 선택 가능 | Comprehension (이해) |
| TYPE_D | 심층 사고 탐구 | 엣지케이스·경계 조건을 탐색할 수 있는 경우 | Analysis (분석) |
| TYPE_E | 코드 추적 | 코드 블록이 포함된 노트 (최우선 적용) | — |

초기 설계에서는 TYPE_A(개념 정의 확인)와 TYPE_F(실제 적용 탐구)를 별도 유형으로 분리했다. 그러나 LLM 분류 정확도 측정에서 TYPE_F 전용 테스트 케이스 3개 중 2개가 TYPE_A로 오분류됐다. 텍스트만으로는 "개념 설명이 부족한 노트"와 "이론만 있는 순수 텍스트 노트"를 구분할 근거가 없어 LLM 입장에서 두 유형의 경계가 실질적으로 동일한 입력 공간에 위치했다. 이를 근거로 TYPE_F를 TYPE_A에 통합하고 TYPE_A의 적용 조건과 질문 템플릿에 적용 탐구 질문을 추가했다. 상세 측정 결과는 본 절 [검증] 항목을 참고한다.

## 2.2.2 프롬프트 설계

**설계 원칙**

프롬프트는 영어로 작성했다. gpt-4o는 인터넷 텍스트, 논문, 코드 등 방대한 데이터로 학습됐는데 그 대부분이 영어다. 사람이 AI 답변의 좋고 나쁨을 평가하여 모델을 개선하는 과정(RLHF)도 영어 기반으로 진행됐다. 결과적으로 gpt-4o는 영어 지시 사항을 더 정확히 따르도록 훈련되어 있으며, TYPE_A처럼 정해진 레이블만 출력해야 하는 분류 태스크에서 한국어보다 영어 프롬프트의 오분류율이 낮다.

TYPE 정의 블록의 When 조건은 한국어로 작성했다. 학습자가 작성하는 노트가 한국어·영어 혼용이기 때문에, LLM이 노트 내용과 TYPE 조건을 직접 비교할 때 같은 언어로 쓰인 조건이 매칭 정확도를 높인다. 프롬프트의 지시 사항("Respond with ONLY the type label"등)은 LLM이 따라야 할 규칙이므로 영어로 작성하고, 노트 내용과 대조하는 분류 기준은 노트와 동일한 언어인 한국어로 작성하는 역할 분리 방식을 택했다.

프롬프트는 세 가지 구성 요소로 이루어진다. 첫째, TYPE 정의 블록에 5종의 적용 조건을 명시하여 LLM이 판단 기준을 명확히 이해하도록 한다. 둘째, 한국어 CS 개발 노트 맥락에서 분류 기준을 보여주는 few-shot 예시를 포함한다. 셋째, 출력 형식을 `TYPE_A` 형태의 단일 레이블로 제한한다. LLM이 "TYPE_A라고 생각한다" 같은 문장으로 답하면 코드가 응답에서 유형을 읽어내지 못할 수 있다. 레이블 하나만 출력하도록 강제하면 이런 오류를 방지할 수 있다.


**type-router.st 템플릿**

## 2.2.3 요청/응답 파이프라인

라우팅은 3단계로 처리된다.

1단계에서는 코드 블록 존재 여부를 규칙으로 판단한다. 코드 블록이 포함된 노트는 LLM을 호출하지 않고 즉시 TYPE_E를 반환한다. 코드 블록이 있는 노트는 구현 내용 파악이 학습의 핵심이므로 코드 동작 추적 질문이 항상 우선한다는 설계 원칙에 따른다.

2단계에서는 코드 블록이 없는 경우 LLM을 호출하여 TYPE을 결정한다. 이때 노트 내용과 RAG 결과 존재 여부만 전달한다. RAG 청크 내용 전체를 라우터에 넘기면 현재 노트와 무관한 청크가 분류를 오염시킬 수 있으므로 `true/false` 플래그로 압축하여 전달한다. 라우터의 역할은 어떤 유형의 질문을 생성할지 결정하는 것이며, 과거 노트 내용은 실제 질문 생성 단계에서만 필요하다.

3단계에서는 LLM 응답에 대한 폴백 처리를 수행한다. TYPE_C로 분류됐으나 실제 RAG 결과가 없으면 TYPE_A로 전환한다. LLM이 정의된 5종 외의 값을 반환하거나 매칭에 실패한 경우에도 TYPE_A를 기본값으로 반환한다.

```
PROCEDURE 질문유형결정(노트, RAG결과):

  // 0단계: 입력 검증 — REQ-AIV-001
  IF 노트 길이 > 허용 최대값:
    오류반환("입력 길이 초과")  // 처리 중단

  // 1단계: 규칙 필터
  IF 노트에 코드 블록 존재:
    대화기록.질문유형 ← TYPE_E
    RETURN TYPE_E  // LLM 호출 없음

  // 2단계: LLM 분류
  RAG존재여부 ← NOT RAG결과.isEmpty()
  LLM응답 ← LLM호출(type-router 프롬프트, 노트내용, RAG존재여부)

  // 3단계: 폴백 처리 — REQ-AIV-006
  결정된유형 ← TYPE_A  // 기본값 설정

  FOR 각 유형 IN [TYPE_A, TYPE_B, TYPE_C, TYPE_D, TYPE_E]:
    IF LLM응답에 유형 포함:
      IF 유형 == TYPE_C AND RAG결과 없음:
        결정된유형 ← TYPE_A  // RAG 없으면 과거 연계 질문 불가
        BREAK
      결정된유형 ← 유형
      BREAK
  // → 정의되지 않은 유형이 출력되지 않음을 보장

  // 결과 저장 후 반환
  대화기록.질문유형 ← 결정된유형
  RETURN 결정된유형
```

결정된 TYPE을 대화 기록 DB에 저장하는 목적은 두 가지다. 첫째, 최초 질문 생성 시 결정된 TYPE을 저장하고 후속 LLM 호출에서 재사용하여 동일 대화 내 이중 분류 호출을 방지한다. 둘째, 누적된 `(노트 내용 → TYPE)` 쌍이 향후 Fine-tuning의 학습 데이터로 활용된다.

**무의미 발화 처리**

학습자가 짧거나 의미 없는 발화를 입력한 경우 LLM을 호출하여 새로운 질문을 생성하지 않는다. 대신 대화 기록에서 직전 AI 질문을 조회하여 "조금 막히는 것 같네. 다시 한 번 — [직전 AI 질문]" 형태로 재제시한다. LLM 호출 없이 처리하므로 불필요한 API 비용이 발생하지 않는다. 이 처리는 학습자의 후속 메시지를 처리하는 `respond()` 단계에서만 동작하며, 완전히 빈 메시지는 컨트롤러 레이어에서 별도로 차단된다.

두 가지 기준 중 하나라도 해당하면 무의미 발화로 판단한다.

- 입력 문자열의 공백 제거 후 길이가 5자 미만인 경우
- 고정 키워드 목록에 포함된 경우: `아`, `어`, `음`, `몰라`, `모르겠어`, `모름`, `..`, `...`, `idk`, `?`

```
PROCEDURE 후속질문생성(대화ID, 사용자입력):

  IF 무의미발화(사용자입력):
    이전AI질문 ← 대화기록에서 마지막 AI 메시지 조회
    재제시메시지 ← "조금 막히는 것 같네. 다시 한 번 — " + 이전AI질문
    대화기록.저장(USER, 사용자입력)
    대화기록.저장(AI, 재제시메시지)
    RETURN 재제시메시지  // LLM 호출 없음

  // 이하 일반 응답 생성 흐름...
```

대화 시작 직후 AI 메시지가 아직 없는 상태에서 무의미 발화가 들어오면, 직전 AI 질문 조회 결과가 빈 값이 된다. 이 경우 고정 fallback 메시지 `"어떤 부분이 막히는지 조금 더 구체적으로 말해줄 수 있어?"`를 반환한다.

**REQ-AIV-001 — 입력 길이 초과 처리**

노트 본문의 허용 최대 길이는 2,000자이다. 검증은 Service 레이어에서 수행하며, 노트 저장과 수정 양쪽에 동일하게 적용된다. 본문 길이가 2,000자를 초과하면 예외가 발생하고 GlobalExceptionHandler가 이를 400 Bad Request로 변환하여 반환한다.

2,000자로 설정한 이유는 이 시스템의 임베딩 방식과 직결된다. 노트 전체를 하나의 벡터로 저장하는 전체 청킹 방식을 사용하기 때문에, 노트가 지나치게 길면 여러 개념이 하나의 벡터에 혼재하여 검색 정확도가 떨어진다. 개발자 학습 노트의 일반적인 형태인 개념 정의, 동작 원리, 예시, 주의사항을 모두 담기에 2,000자는 충분한 분량이며, 이를 넘어서는 경우 단일 주제가 아닌 여러 개념을 묶어 작성했을 가능성이 높다. 하나의 노트가 하나의 개념을 담는 구조를 유도함으로써 임베딩 품질과 검색 정확도를 동시에 확보하려는 설계 원칙이다.

**REQ-AIV-006 — 질문 유형 분류기 폴백**

폴백이 발생하는 케이스는 세 가지다.

1. **TYPE_C 분류 + RAG 결과 없음 → TYPE_A**: TYPE_C는 과거 노트 연계 질문이므로 참조할 과거 노트가 없으면 질문의 전제가 성립하지 않는다. `ragContext.isEmpty()`가 true이면 TYPE_A로 전환한다.
2. **LLM 응답이 5종 외의 값**: `QuestionType.values()` 순회에서 매칭되는 유형이 없으면 루프를 탈출하여 기본값 TYPE_A가 반환된다.
3. **LLM 응답 파싱 실패**: 빈 응답이거나 파싱 불가능한 경우 동일하게 TYPE_A로 폴백한다.

TYPE_A를 기본값으로 선택한 이유는 모든 노트에 일반적으로 적용 가능한 가장 기본적인 질문 유형이기 때문이다. 어떤 내용의 노트든 개념을 묻는 질문은 항상 유효하다. 현재 폴백 발생 여부는 별도로 기록하지 않는다.

**REQ-AIV-007 — LLM 오류 응답 처리**

`AiTutorService`의 `generateFirstQuestion()`과 `respond()` 양쪽 chatClient 호출부를 try-catch로 감싼다. 예외 발생 시 `DomainException(ErrorCode.AI_RESPONSE_FAILED)`를 throw하고, GlobalExceptionHandler가 502 Bad Gateway로 변환하여 반환한다. 빈 응답(`null` 또는 공백)은 예외가 아니므로 별도 분기로 처리하며, 재질문 유도 메시지를 200으로 반환한다.

| 케이스 | 동작 | HTTP 코드 |
|---|---|---|
| LLM 예외 (타임아웃·API 오류 등) | `AI_RESPONSE_FAILED` throw | 502 Bad Gateway |
| LLM 빈 응답 (null / 공백) | 재질문 유도 메시지 반환 | 200 OK |

네트워크 오류나 OpenAI API 응답 코드별 세분화는 현재 구현 범위에 포함하지 않는다. 모든 예외는 단일 `catch (Exception e)` 블록으로 처리한다.

## 2.2.4 컨텍스트 관리 전략

**TYPE_C RAG 연동 조건**

LLM이 TYPE_C로 분류하면 RAG 검색 결과가 실제로 존재하는지 확인한다. RAG 결과가 없으면 TYPE_A로 폴백한다. TYPE_C는 "과거에 학습한 개념과 현재 노트가 어떻게 연결되는가"를 묻는 질문 유형이므로, 참조할 과거 노트가 없으면 질문의 전제 자체가 성립하지 않는다.

**과거 학습 맥락 복원 전략**

ChromaDB에서 검색된 관련 과거 노트를 프롬프트에 주입하여 현재 노트와 과거 학습을 연결하는 질문을 생성한다. 이때 과거 노트임을 명시하는 레이블을 포함하여 주입한다.

레이블을 포함하는 이유는 초기 구현 경험에서 도출됐다. 레이블 없이 과거 노트 내용만 주입했을 때 LLM이 해당 내용을 현재 노트의 일부로 오해하여 과거 노트 내용을 근거로 직접 정답을 제공하는 현상이 발생했다. 현재는 아래 형식으로 과거 노트 출처를 명시한다.

```
[참고용 과거 노트 — 현재 노트 학습 보조 목적으로만 활용]

--- [Note: "노트 제목" | session_id: 42 | similarity: 0.83] ---
과거 노트 내용...
```

이 레이블이 System Prompt의 RAG 노이즈 거부 규칙과 함께 동작하여 LLM이 과거 노트를 현재 학습의 보조 맥락으로만 활용하도록 유도한다.

## 2.2.5 분류 방법 비교 및 채택 근거

TYPE 분류기를 설계할 때 세 가지 방법을 순서대로 검토하고 기각했다.

**코사인 유사도 기반 — 기각**

노트 내용과 TYPE 시드 문장 사이의 코사인 유사도로 분류하는 방식을 먼저 검토했다. 그러나 노트("JWT는 Header.Payload.Signature 구조다")와 TYPE 시드("새로운 개념이나 용어가 처음 등장한 노트")는 서로 다른 의미 공간에 위치한다. 노트는 도메인 지식 벡터 공간에, TYPE 시드는 교육학 메타 설명 벡터 공간에 위치하므로 유사도 계산이 의미 없는 값을 반환한다. 구현 없이 설계 단계에서 기각했다.

**규칙 기반 — 부분 채택 (전처리 필터로 한정)**

키워드 기반 규칙으로 TYPE을 결정하는 방식을 검토했다. 코드 블록 존재 여부(TYPE_E)처럼 구조적으로 명확한 케이스에는 정확하다. 그러나 복합적인 내용을 가진 노트는 규칙으로 정확히 판단하기 어렵다. "HashMap은 평균 O(1)이지만 해시 충돌 시 O(n)이 될 수 있다"는 노트가 대표적인 예다. 이 문장은 HashMap의 시간복잡도 개념이 처음 등장하는 것으로 볼 수 있어 TYPE_A(개념 정의 확인)로 해석할 수 있고, 동시에 일반 경우(O(1))와 예외 상황(O(n))을 함께 언급하고 있어 TYPE_D(심층 사고 탐구)로도 해석할 수 있다. 두 해석의 차이는 텍스트 자체가 아니라 학습자의 이해 수준에 달려 있는데, 키워드만으로는 학습자가 이 개념을 처음 접하는지 이미 알고 예외를 탐구하는 단계인지 판단할 수 없다. 규칙 기반은 TYPE_E 감지에 한정하여 전처리 필터로만 사용한다.

**Fine-tuned 모델 — 미래 과제**

한국어 CS 개발 노트 도메인에 특화된 학습 데이터가
현재 존재하지 않아 즉시 적용이 불가능하다.
공개 데이터셋으로는 PLOS ONE(2020)과 BloomNet(2021)이
있다. PLOS ONE 데이터셋은 여러 웹사이트와 이전 연구에서
수집한 영어 시험 문제 141개와 600개로 구성되어 있으며,
BloomNet은 스리랑카 여러 국립대학교 시험 문제
16,584개를 Bloom's Taxonomy 6단계로 수동 레이블링한
데이터셋이다. Bloom's Taxonomy 6단계는 단순 암기부터
새로운 결과물 생성까지 학습자의 인지 수준을 계층적으로
분류한 교육학 표준 체계로, 기억(배운 내용을 그대로
떠올린다)·이해(개념의 의미를 설명할 수 있다)·적용
(배운 개념을 실제 상황에 사용한다)·분석(개념을 분해하고
관계를 파악한다)·평가(기준을 세워 판단하고 근거를 댄다)·
창조(새로운 것을 설계하거나 만들어낸다)로 구성된다.
두 데이터셋 모두 영어 기반의 대학 시험 문제 도메인으로,
한국어로 작성된 개발자 학습 노트와는 언어와 도메인이
모두 불일치한다. 시험 문제는 교수자가 출제한 정형화된
문장 구조를 가지는 반면, 개발자 학습 노트는 코드 블록·
식별자·한국어 CS 용어가 혼합된 비정형 텍스트로 같은
Bloom's Taxonomy 레이블이라도 분류 기준이 다르다.
LLM 분류 결과를 DB에 저장하여 `(노트 내용 → TYPE)`
학습 데이터를 축적하고, 5 TYPE × 약 40건 = 200건
확보 시 Fine-tuned 모델로 전환할 계획이다.

**LLM 분류 — 현재 채택**

도메인 특화 학습 데이터 없이 즉시 적용 가능한 유일한 고정확도 방법이다. 한국어·영어 혼용 노트와 CS 개발 맥락을 동시에 이해하여 분류할 수 있다.

| 방법 | 정확도 | 구현 난이도 | 비용 | 채택 여부 |
|---|---|---|---|---|
| 코사인 유사도 기반 | 낮음 (설계 결함) | 낮음 | 무료 | ❌ 기각 |
| 규칙 기반 | 중간 | 낮음 | 무료 | △ 전처리 필터로만 |
| LLM 분류 | 높음 | 중간 | 호출당 소액 | ✅ 채택 |
| Fine-tuned 모델 | 최고 | 높음 | 학습 비용 | ⏳ 데이터 축적 후 |

## [검증] QuestionTypeRouter — LLM 질문 유형 분류 정확도 측정

#### 필요성

QuestionTypeRouter는 설계된 TYPE 기준에 따라 LLM이 노트를 올바르게 분류하는지를 전제로 동작한다. 그러나 LLM이 실제로 의도대로 분류하는지 측정한 적이 없었다. 특히 초기 설계에 포함된 TYPE_F(실제 적용 탐구)가 TYPE_A(개념 정의 확인)와 경계가 명확한지 확인이 필요했다. 합격 기준 미달 시 TYPE 설계 자체를 수정할 근거를 마련하기 위해 측정을 수행했다.

#### 특징

일반적인 단위 테스트는 외부 서비스(LLM, DB 등)를
가짜로 대체해서 테스트한다. 그런데 이 테스트의 목적은
LLM이 TYPE을 올바르게 분류하는지 확인하는 것이므로,
LLM만큼은 실제 OpenAI API를 호출해야 한다.
LLM을 가짜로 대체하면 테스트 자체가 의미 없어진다.
반면 ChromaDB(과거 노트 검색 DB)는 이 테스트에서
필요하지 않다. TYPE 분류는 현재 노트 내용만으로
판단하기 때문이다. 따라서 ChromaDB는 가짜로 대체하여
실제 DB 연결 없이 테스트했다.
그래서, LLM은 실제로 호출하고
ChromaDB는 가짜로 대체하는 방식으로
두 외부 서비스를 분리하여 테스트했다.
