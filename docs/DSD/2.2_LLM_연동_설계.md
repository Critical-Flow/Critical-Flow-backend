## 2.2.1 질문 유형 정의 (TYPE A~E)

질문 유형은 Bloom's Taxonomy를 기반으로 설계하였으며, 개발자 노트의 특성을 반영하여 TYPE E를 별도 추가했다.

| TYPE | 설명 | 적용 조건 | Bloom's 대응 |
|---|---|---|---|
| TYPE_A | 개념 정의 확인 및 적용 탐구 | 새로운 용어·개념이 등장하거나, 코드 없이 이론·개념만 서술된 순수 텍스트 노트 | Knowledge (기억) + Application (적용) |
| TYPE_B | 설계 의도 탐구 | 트레이드오프·기술 선택 근거가 포함된 경우 | Evaluation (평가) |
| TYPE_C | 과거 학습 연계 | RAG로 관련 과거 노트가 존재할 때만 선택 가능 | Comprehension (이해) |
| TYPE_D | 심층 사고 탐구 | 엣지케이스·경계 조건을 탐색할 수 있는 경우 | Analysis (분석) |
| TYPE_E | 코드 추적 | 코드 블록이 포함된 노트 (최우선 적용) | — |

질문 유형이 5종인 이유는 Bloom's Taxonomy의 4개 인지 단계(기억·이해·분석·평가)에 대응하는 4종(TYPE A, B, C, D)과 개발자 노트 특화 유형 1종(TYPE E)을 합친 구조이기 때문이다. Bloom's Taxonomy를 채택한 이유는 학습자의 인지 수준에 따라 질문 난이도를 단계적으로 설계하기 위함이다. 단순 개념 암기부터 심층 분석·평가까지 인지 단계를 체계적으로 구분하는 교육학 표준 프레임워크로, AI 튜터링 연구에서 질문 유형 분류에 가장 널리 활용된다. 소크라테스식 튜터링의 핵심인 "사고 유도형 질문"을 설계하려면 학습자의 현재 인지 수준을 파악하고 한 단계 높은 사고를 자극하는 질문이 필요한데, Bloom's Taxonomy의 계층 구조가 이 목적에 직접 대응한다.

TYPE E는 개발자 노트의 코드 블록 특성에 맞게 별도 추가된 유형으로, Bloom's Taxonomy에 직접 대응하는 항목이 없다. 코드 블록은 Bloom's Taxonomy의 어느 단계에도 직접 대응하지 않으며, 코드 동작 추적은 개발자 학습 노트에 특화된 질문 유형이다.

TYPE_A는 초기 설계에서 "개념 정의 확인"과 "실제 적용 탐구(TYPE_F)"를 별도 유형으로 분리하였으나, LLM 분류 정확도 측정(2026-06-02) 결과 두 유형의 경계가 LLM에게 불명확하여 TYPE_F 전용 테스트 케이스 3개 중 2개가 TYPE_A로 오분류되었다. 텍스트만으로는 "개념 설명이 부족한 노트"와 "이론만 있고 실제 맥락이 없는 노트"를 구분할 근거가 없어, TYPE_F를 TYPE_A에 통합하고 TYPE_A의 질문 템플릿에 적용 탐구 질문을 추가하였다. 자세한 측정 결과는 [검증] QuestionTypeRouter — LLM 질문 유형 분류 정확도 측정 항목을 참고한다.

## 2.2.3 요청/응답 파이프라인

라우팅은 3단계로 처리된다.

1단계에서는 코드 블록 존재 여부를 규칙으로 판단한다. 코드 블록이 포함된 노트는 LLM을 호출하지 않고 즉시 TYPE_E를 반환한다. 코드 블록이 있는 노트는 반드시 코드 추적 질문이 적합하다는 판단 아래 설계한 전처리 필터다. 코드 블록이 포함된 노트는 구현 내용 파악이 학습의 핵심이므로 코드 동작 추적 질문이 항상 우선한다는 설계 원칙에 따른다.

2단계에서는 코드 블록이 없는 경우 LLM을 호출하여 TYPE을 결정한다. 이때 노트 내용과 RAG 결과 존재 여부만 전달한다. RAG 청크 내용 전체를 라우터에 넘기면 현재 노트와 무관한 청크가 분류를 오염시킬 수 있으므로 `true/false` 플래그로 압축하여 전달한다. 라우터의 역할은 어떤 유형의 질문을 생성할지 결정하는 것이며, 과거 노트 내용은 실제 질문 생성 단계에서만 필요하다. 불필요한 정보를 라우터에 전달하면 토큰 비용이 증가하고 분류 정확도가 저하될 수 있다.

3단계에서는 LLM 응답에 대한 폴백 처리를 수행한다. TYPE_C로 분류됐으나 실제 RAG 결과가 없으면 TYPE_A로 전환한다. LLM이 정의된 5종 외의 값을 반환하거나 매칭에 실패한 경우에도 TYPE_A를 기본값으로 반환한다.

```
PROCEDURE 질문유형결정(노트, RAG결과):

  // 0단계: 입력 검증 — REQ-AIV-001
  IF 노트 길이 > 허용 최대값:
    오류반환("입력 길이 초과")  // 처리 중단

  // 1단계: 규칙 필터
  IF 노트에 코드 블록 존재:
    대화기록.질문유형 ← TYPE_E
    RETURN TYPE_E  // LLM 호출 없음

  // 2단계: LLM 분류
  RAG존재여부 ← NOT RAG결과.isEmpty()
  LLM응답 ← LLM호출(type-router 프롬프트, 노트내용, RAG존재여부)

  // 3단계: 폴백 처리 — REQ-AIV-006
  결정된유형 ← TYPE_A  // 기본값 설정

  FOR 각 유형 IN [TYPE_A, TYPE_B, TYPE_C, TYPE_D, TYPE_E]:
    IF LLM응답에 유형 포함:
      IF 유형 == TYPE_C AND RAG결과 없음:
        결정된유형 ← TYPE_A  // RAG 없으면 과거 연계 질문 불가
        BREAK
      결정된유형 ← 유형
      BREAK
  // → 정의되지 않은 유형이 출력되지 않음을 보장

  // 결과 저장 후 반환
  대화기록.질문유형 ← 결정된유형
  RETURN 결정된유형
```

**무의미 발화 처리**

학습자가 짧거나 의미 없는 발화를 입력한 경우 LLM을 호출하여 새로운 질문을 생성하지 않는다. 대신 대화 기록에서 직전 AI 질문을 조회하여 "조금 막히는 것 같네. 다시 한 번 — [직전 AI 질문]" 형태로 재제시한다. LLM 호출 없이 처리하므로 불필요한 API 비용이 발생하지 않는다. 이 처리는 최초 질문 생성(`generateFirstQuestion`) 단계가 아닌, 학습자의 후속 메시지를 처리하는 `respond()` 단계에서만 동작한다. 완전히 빈 메시지는 컨트롤러 레이어에서 별도로 차단된다.

**무의미 발화 감지 기준**

두 가지 기준 중 하나라도 해당하면 무의미 발화로 판단한다.

- 입력 문자열의 공백 제거 후 길이가 5자 미만인 경우
- 고정 키워드 목록에 포함된 경우: `아`, `어`, `음`, `몰라`, `모르겠어`, `모름`, `..`, `...`, `idk`, `?`

**수도코드**

```
PROCEDURE 후속질문생성(대화ID, 사용자입력):

  IF 무의미발화(사용자입력):
    이전AI질문 ← 대화기록에서 마지막 AI 메시지 조회
    재제시메시지 ← "조금 막히는 것 같네. 다시 한 번 — " + 이전AI질문
    대화기록.저장(USER, 사용자입력)
    대화기록.저장(AI, 재제시메시지)
    RETURN 재제시메시지  // LLM 호출 없음

  // 이하 일반 응답 생성 흐름...
```

**직전 AI 질문이 없는 예외 케이스**

대화 시작 직후(AI 메시지가 아직 없는 상태)에 무의미 발화가 들어오면, 직전 AI 질문 조회 결과가 빈 값이 된다. 이 경우 고정 fallback 메시지 `"어떤 부분이 막히는지 조금 더 구체적으로 말해줄 수 있어?"`를 사용한다.

결정된 TYPE을 대화 기록 DB에 저장하는 목적은 두 가지다. 첫째, 최초 질문 생성 시 결정된 TYPE을 저장하고 후속 LLM 호출에서 재사용하여 동일 대화 내 이중 분류 호출을 방지한다. 둘째, 누적된 `(노트 내용 → TYPE)` 쌍이 향후 Fine-tuning의 학습 데이터로 활용될 수 있다..

**REQ-AIV-001 — 입력 길이 초과 처리 구현 내용**

노트 본문의 허용 최대 길이는 2,000자이다. 검증은 Service 레이어에서 수행하며, 노트 저장과 수정 양쪽에 동일하게 적용된다. 본문 길이가 2,000자를 초과하면 예외가 발생하고 GlobalExceptionHandler가 이를 400 Bad Request로 변환하여 반환한다.

2,000자로 설정한 이유는 이 시스템의 임베딩 방식과 직결된다. 노트 전체를 하나의 벡터로 저장하는 전체 청킹 방식을 사용하기 때문에, 노트가 지나치게 길면 여러 개념이 하나의 벡터에 혼재하여 검색 정확도가 떨어진다. 개발자 학습 노트의 일반적인 형태인 개념 정의, 동작 원리, 예시, 주의사항을 모두 담기에 2,000자는 충분한 분량이며, 이를 넘어서는 경우 단일 주제가 아닌 여러 개념을 묶어 작성했을 가능성이 높다. 하나의 노트가 하나의 개념을 담는 구조를 유도함으로써 임베딩 품질과 검색 정확도를 동시에 확보하려는 설계 원칙이다.

**REQ-AIV-006 — 질문 유형 분류기 폴백 구현 내용**

폴백이 발생하는 케이스는 세 가지다.

1. **TYPE_C 분류 + RAG 결과 없음 → TYPE_A**: TYPE_C는 과거 노트 연계 질문이므로 참조할 과거 노트가 없으면 질문의 전제가 성립하지 않는다. `ragContext.isEmpty()`가 true이면 TYPE_A로 전환한다.
2. **LLM 응답이 5종 외의 값**: `QuestionType.values()` 순회에서 매칭되는 유형이 없으면 FOR 루프를 탈출하여 기본값 TYPE_A가 그대로 반환된다.
3. **매칭 실패**: LLM 응답이 비어있거나 파싱 불가능한 경우도 동일하게 TYPE_A로 폴백한다.

TYPE_A("개념 정의 확인")를 기본값으로 선택한 이유는 모든 노트에 일반적으로 적용 가능한 가장 기본적인 질문 유형이기 때문이다. 어떤 내용의 노트든 새로운 개념을 묻는 질문은 항상 유효하다.

현재 폴백 발생 여부는 별도로 기록하지 않는다. `parseType()` 내부에 로깅 코드가 없으며, 모니터링 로직도 존재하지 않는다.

정의되지 않은 유형이 출력되지 않음을 보장하는 메커니즘: `QuestionType.values()` 열거형 순회와 `BREAK` 조건을 통해 반환값은 반드시 5종 중 하나가 되도록 설계되어 있다. 루프를 탈출한 후에는 초기값으로 설정된 TYPE_A가 반환되므로, 정의되지 않은 값이 외부로 노출될 수 없다.

**REQ-AIV-007 — LLM 오류 응답 처리**

외부 LLM 응답이 빈 값이거나 오류인 경우, 학습자에게 재시도 안내 메시지를 반환한다. 빈 응답이 학습자에게 노출되어서는 아니된다.

`AiTutorService`의 `generateFirstQuestion()`과 `respond()` 양쪽 chatClient 호출부를 try-catch로 감싼다. 예외 발생 시 `DomainException(ErrorCode.AI_RESPONSE_FAILED)`를 throw하고, `GlobalExceptionHandler`가 `ErrorCode`에 정의된 HTTP 상태 코드로 변환하여 반환한다. `AI_RESPONSE_FAILED`는 502 Bad Gateway로 정의되어 있다. 빈 응답(`null` 또는 공백)은 예외가 아니므로 try-catch가 아닌 별도 분기로 처리하며, 재질문 유도 메시지("잠시 응답을 생성하지 못했어. 다시 한 번 메시지를 보내줄 수 있어?")를 200으로 반환한다.

케이스별 동작:

| 케이스 | 동작 | HTTP 코드 |
|---|---|---|
| LLM 예외 (타임아웃·API 오류 등) | `AI_RESPONSE_FAILED` throw | 502 Bad Gateway |
| LLM 빈 응답 (null / 공백) | 재질문 유도 메시지 반환 | 200 OK |

네트워크 오류나 OpenAI API 응답 코드별 세분화는 현재 구현 범위에 포함하지 않는다. 모든 예외는 단일 `catch (Exception e)` 블록으로 처리하여 학습자에게 일관된 재시도 안내를 반환한다.

## 2.2.4 컨텍스트 관리 전략

**TYPE_C 스페이스드 리콜 RAG 연동 조건**

LLM이 TYPE_C로 분류하면 RAG 검색 결과가 실제로 존재하는지 확인한다. RAG 결과가 없으면 TYPE_A로 폴백한다. TYPE_C는 "과거에 학습한 개념과 현재 노트가 어떻게 연결되는가"를 묻는 질문 유형이므로, 참조할 과거 노트가 없으면 질문의 전제 자체가 성립하지 않는다.

**과거 학습 맥락 복원 전략**

ChromaDB에서 검색된 관련 과거 노트를 프롬프트에 주입하여 현재 노트와 과거 학습을 연결하는 질문을 생성한다. 이때 과거 노트임을 명시하는 레이블을 포함하여 주입한다.

레이블을 포함하는 이유는 초기 구현 경험에서 도출됐다. 레이블 없이 과거 노트 내용만 주입했을 때 LLM이 해당 내용을 현재 노트의 일부로 오해하여 과거 노트 내용을 근거로 직접 정답을 제공하는 현상이 발생했다. 현재는 아래 형식으로 과거 노트 출처를 명시한다.

```
[참고용 과거 노트 — 현재 노트 학습 보조 목적으로만 활용]

--- [Note: "노트 제목" | session_id: 42 | similarity: 0.83] ---
과거 노트 내용...
```

이 레이블이 System Prompt의 RAG 노이즈 거부 규칙과 함께 동작하여 LLM이 과거 노트를 현재 학습의 보조 맥락으로만 활용하도록 유도한다.

## 2.2.5 분류 방법 비교 및 발전 전략

**방법별 비교**

| 방법 | 정확도 | 구현 난이도 | 비용 |
|---|---|---|---|
| 코사인 유사도 기반 | 낮음 (설계 결함) | 낮음 | 무료 |
| 규칙 기반 | 중간 | 낮음 | 무료 |
| LLM 분류 | 높음 | 중간 | 호출당 소액 |
| Fine-tuned 모델 | 최고 | 높음 | 학습 비용 |

**LLM 채택 근거**

코사인 유사도 기반 라우팅은 채택하지 않았다. 노트 내용("JWT는 Header.Payload.Signature 구조다")과 TYPE 시드 문장("새로운 개념이나 용어가 처음 등장한 노트")은 서로 다른 의미 공간에 위치한다. 노트는 도메인 지식 벡터 공간에, TYPE 시드는 교육학 메타 설명 벡터 공간에 위치하므로 유사도 계산이 의미 없는 값을 반환한다.

규칙 기반 분류는 단독으로 사용하기에 정확도 한계가 존재한다. 코드 블록 존재 여부처럼 구조적으로 명확한 케이스에는 정확하지만, 복합적인 내용을 가진 노트는 키워드 기반 규칙으로 정확히 판단하기 어렵다. 예를 들어 "HashMap은 평균 O(1)이지만 해시 충돌 시 O(n)이 될 수 있다"는 노트는 새 개념을 설명하는 TYPE A와 엣지케이스를 다루는 TYPE D 두 가지 해석이 모두 가능하며, 키워드만으로는 학습자의 현재 이해 수준을 기반으로 한 판단이 불가능하다. 또한 TYPE B(설계 의도 탐구)와 TYPE D(심층 사고 탐구)의 경계는 "왜"라는 질문이 선택 근거를 묻는 것인지 경계 조건을 탐구하는 것인지에 따라 달라지는데, 이 맥락 판단은 규칙으로 표현하기 어렵다. 따라서 규칙 기반은 전처리 필터 역할에 한정하여 사용한다.

Fine-tuned 모델은 한국어 CS 개발 노트 도메인에 특화된 학습 데이터가 현재 존재하지 않아 즉시 적용이 불가능하다. 공개 데이터셋(PLOS ONE, BloomNet)은 영어 기반이며 스리랑카 대학 시험 도메인으로 한국어 개발자 노트와 도메인이 불일치한다.

LLM은 도메인 특화 학습 데이터 없이 즉시 적용 가능한 유일한 고정확도 방법이다. 한국어·영어 혼용 노트와 CS 개발 맥락을 동시에 이해하여 분류할 수 있다.

**현재 구현 (1단계)**

코드 블록 규칙 필터와 LLM 분류를 혼합하여 사용한다. 코드 블록이 있는 노트는 규칙 필터가 처리하고, 나머지는 LLM이 판단한다.

※ 비고: 노트 200~300개 축적 후 Fine-tuned 모델 전면 교체 예정

OpenAI Fine-tuning 권장 최소 학습 데이터는 수백 건 이상이며, 도메인 특화 분류 모델의 경우 200~300개 이상의 레이블된 데이터가 확보되면 유의미한 성능 향상이 기대된다. 200~300개를 기준으로 설정한 이유는 5종 분류 태스크에서 클래스 균형을 고려한 최소 데이터 요건에서 도출됐다. 클래스당 최소 40~50개 수준이면 각 TYPE의 다양한 노트 스타일을 학습 데이터에 반영할 수 있으며, OpenAI 공식 문서는 분류 태스크에서 클래스당 수십 건 이상의 고품질 예시를 권장한다. 5 TYPE × 약 40건 = 200건이 현실적인 시작점으로 판단했다.

LLM 분류 결과를 DB에 저장함으로써 Fine-tuning을 위한 `(노트 → TYPE)` 학습 데이터가 자연스럽게 축적된다.

**TYPE_A vs TYPE_F 혼동 (2케이스 실패)**

**TYPE_D vs TYPE_F 혼동 (1케이스 실패)**

"동기 처리는 순서가 보장되지만 앞 작업이 끝나야 다음이 시작되어 블로킹 문제가 생긴다"는 TYPE_D(엣지케이스 탐구)로 기대하였으나 TYPE_F(순수 이론 설명)로 분류됐다. 문장 자체가 설명적 구조여서 LLM이 이론 설명 유형으로 판단하였다.
